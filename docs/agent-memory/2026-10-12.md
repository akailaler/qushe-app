## 第十四轮：操作栏换边 / 旋转 / 消除闪烁 / 双击不再闪暂停 → 出 1.0.10

用户提了 5 点，其中「视频左下角显示位置」**含义不明确，已向用户追问**，本轮未实现。

**1. 操作栏可放左或右**
- `Prefs.railOnRight`（默认 true）+ 设置页开关
- `VideoSessionScreen` 加 `railOnRight` 参数，侧栏 `.align(BottomEnd / BottomStart)` 整组换边
- 侧栏现在 5 个动作（收藏 / 删除 / 分享 / 旋转 / 静音），底部 padding 从 140dp 收到 128dp、
  间距 16dp → 14dp，避免顶到顶栏

**2. 顺时针旋转按钮**
- `rotationSteps` 状态，每点 +1 取模 4；`rotationDegrees = steps * 90f`
- 作用在「缩略图 + 播放器」外层 Box 的 `graphicsLayer { rotationZ = ... }`，两者始终对齐
- **只旋转、不缩放就能成立**：竖屏 W×H 里横屏视频 Fit 后占 W × (W·9/16)，
  转 90° 变成 (W·9/16) × W，仍然完全落在屏幕内 ✓
- 图标用 core 里的 `Icons.Filled.Refresh`（本身逆时针）+ `scaleX = -1` 镜像成顺时针
  —— core 里没有 rotate 类图标，没必要为此引入 extended

**3. 上下滑闪烁（两个原因）**
- 换页时 ExoPlayer 要重新 `prepare`，空窗期播放器是白的。
  改：`Player.Listener.onRenderedFirstFrame()`（**已 javap 确认 media3 1.4.1 存在此回调**）
  → 首帧就绪前 `alpha = 0` 露出下面的缩略图，就绪后显示。
  因为首帧内容 == 缩略图，切换是无缝的。
- 加 `beyondViewportPageCount = 1`，提前组相邻页让缩略图先 load。
  （这个参数在 Compose Foundation 1.7 有，之前担心版本不敢用，现在有编译环境可以验证 ✓）

**4. 双击收藏总会先闪一下暂停**
- 根因在 `ui/common/Gestures.kt` 的 `detectTapsWithoutConsuming`：
  双击的第一下被当成单击**当场执行**，第二下才识别为双击。
  之前的"补偿式写法"（双击时再切回来一次）那一放一收本身就是可见停顿。
- 改法：**只要 `onDoubleTap != null`，单击就延后 `doubleTapWindowMillis` 再执行**，
  第二下到来时 `pendingSingleTap?.cancel()`。
  因为 `PointerInputScope` 不是 CoroutineScope（老坑），外层套了 `coroutineScope { }` 才能 `launch`。
- 代价：单击（暂停/播放）晚 280ms 生效。**存在双击手势时这是无法回避的取舍**，
  换成"每次双击闪一下"不划算。
- 顺带：视频页的 `onDoubleTap` 去掉了补偿式播放切换；照片页的双击缩放也不再顺带切胶片条。

**结果**：assembleDebug + lintDebug 全绿（0 错误 0 警告）。
`qushe-v1.0.10-debug.apk`（33MB，versionCode 11）。**一次编译通过。**

## 第十五轮：视频显示拍摄地点 → 出 1.0.11

**API 核对（javap 确认，没猜）**
- `MediaStore.Video.VideoColumns.LATITUDE / LONGITUDE` 存在 ✓
- `MediaStore.Images.ImageColumns.LATITUDE / LONGITUDE` 存在 ✓
- `Geocoder.getFromLocation(double, double, int)` 同步版（throws IOException）
  与 `getFromLocation(double, double, int, GeocodeListener)` 异步版（API 33+）都在 ✓

**新增 `core/GeoLocation.kt`**
- `readPoint()`：单独查这一条的 Uri 拿经纬度。(0,0) 视为"无位置"。
- `describe()`：Geocoder 反查地名，取「省 市 区」去重拼接。按坐标缓存。

  **视频**的 GPS 支持不可靠，而这里主要就是给视频用的 → 保留并 `@Suppress("DEPRECATION")`，
  在注释里写明理由。（不加 suppress 会有 4 个编译警告，加上后 0 警告）

**权限**
- Manifest 加 `ACCESS_MEDIA_LOCATION`
- `hasLocationPermission(context)` 放在 Permissions.kt
- **在 `startSession(VIDEO)` 时才申请**，不在应用启动时 —— 和用户当下的动作直接相关。
  拒绝也不影响其他功能，只是不显示地点那一行。

**其他**：`Prefs.showVideoLocation`（默认开）+ 设置页开关；
`MediaRepository.resolveLocationLabel()` 带按条目缓存，`invalidate()` 时一并清掉。

**结果**：assembleDebug + lintDebug 全绿（**0 错误 0 警告**）。
`qushe-v1.0.11-debug.apk`（33MB，versionCode 12）。跑 2 轮编译（第 1 轮 4 个 deprecated 警告）。

**已知局限（要告诉用户）**：下载来的视频本来就没有 GPS 信息，那一行不会显示；
只有相机拍摄且当时开了定位的视频才有。

## 第十六轮：开组彻底重构 + 六项调整 → 出 1.0.12

用户反馈六点，第一点（开组还是慢）是重点，做了一次**结构性重构**。

**1. 开组慢的真正解法（重点）**
- 1.0.8 只是"不再每次强制重扫"，但只要缓存过期或应用重启，仍要读整张 images 表。
  **几万行 × 10 列，光填充 CursorWindow 就是一两秒**。
- 这次改成：
  - `MediaRepository.idIndex`：每个分类只缓存 **ID 列表**，查询**只投影 `_ID` 一列**
  - **截屏判定下推到 SQLite**：把 7 个关键词 × 3 个字段拼成
    `(BUCKET LIKE ? OR RELATIVE_PATH LIKE ? OR DISPLAY_NAME LIKE ?) OR ...`，
    照片用 `NOT (...)`。SQLite 的 LIKE 对 ASCII 天然忽略大小写，语义与原 ignoreCase 一致。
  - `sampleItems()`：在 ID 列表上 `shuffled()`（几万个 Long 洗牌只要几毫秒）
    取十几条 → `byKeys()` 只取这十几条的完整信息
  - **代价与库的大小彻底解耦**
  - `Mutex` + 双检：防止启动预热与用户点开组并发跑两次全量查询
- **删除了 `all(kind)` 和 `allImages()`**（不再需要"整表读进内存"这条路），
  AppRoot 的计数改用 `idsOf(kind).size`。
- ⚠️ 注意：`parseItems` 里仍保留 Kotlin 版 `looksLikeScreenshot`（给 byKeys 用，最多几百条），
  **两处规则必须保持一致**，否则会出现"ID 列表说是截屏、取回来却是照片"的矛盾。

**2. 收藏页照片/视频分类 + 纯观看模式**
- 顶部两个胶囊（照片 / 视频，`showVideos` 状态），网格与预览都走 `shown`
- 纯观看模式：`Prefs.favoritesViewOnly`，打开后隐藏预览里的操作按钮、长按也不移除

**3. 横滑误触发缩略图栏（重要教训）**
- 根因：`detectTapsWithoutConsuming` 靠 `change.isConsumed` 判断"是拖拽还是点击"，
  但 **Main 阶段是子节点先于父节点拿到事件** —— 子节点读到的 `isConsumed` 还是 false，
  横滑于是被判成点击。
- 修法：**自己算位移**（`(change.position - down.position).getDistance() > touchSlop`），
  不再依赖事件消费的可见性。这条对以后所有"父子都有手势"的场景都成立。

**4. 切后台暂停 / 切回自动播**
`pausedForBackground` 标志：ON_STOP 时若正在播则记下并暂停；
ON_START 时只在标志为真时恢复 —— 用户自己按的暂停不该被强行恢复。

**5. 左右滑动快进快退**
`detectHorizontalDragGestures` 与 Pager 的竖直手势互不干扰。
跳转量 = `(dx / 屏宽) × min(时长, 3分钟)`，拖动时居中显示"快进/快退 + 目标时间/总时长"。

**6. 删掉旋转，改横屏全屏**
- 用户反馈旋转"没写成功"，直接删掉。
- 换成全屏：`requestedOrientation = SENSOR_LANDSCAPE` + `WindowCompat.getInsetsController`
  隐藏系统栏；**只对横屏视频（width > height）显示按钮**。
- `DisposableEffect.onDispose` 里务必还原方向与系统栏 —— 否则整个应用卡在横屏。
- 自绘 `FullscreenIcons.kt`（四角括号，只用直线段；core 里没有这类图标）。
- 新增 `Context.findActivity()` 扩展（tailrec 拆 ContextWrapper）—— Compose 拿到的
  Context 可能被包装过，直接 `as? Activity` 不可靠。

**结果**：assembleDebug + lintDebug 全绿（0 错误 0 警告）。
`qushe-v1.0.12-debug.apk`（33MB，versionCode 13）。跑 2 轮编译
（第 1 轮：MINIMAL_PROJECTION 重复声明 + dropFromCache 里可空类型赋值）。

## 第十八轮：全屏交互重做 + 位置功能自检 → 出 1.0.14

用户反馈两点：①「没有找我要过位置权限，也没有显示过地理位置」②全屏按钮要挪到视频下方、
参考抖音、全屏后隐藏侧边栏、用返回手势退出。

**1. 位置功能为什么不生效 —— 无法定位（这是问题本身）**
排查了：Manifest 里 `ACCESS_MEDIA_LOCATION` **声明是有的**；
`startSession` 里的申请逻辑也是对的。但**三种失败的表现完全一样**：
- 没授权
- 授权了但系统拒绝读 LATITUDE/LONGITUDE 列（同 XMP 那类敏感列）
- 内容本身没有位置信息

这三种情况界面上都是"不显示地点那一行"，**用户和我都无法分辨**。又是老毛病：失败被藏起来。

**修法：把结论直接显示在设置页**
- `GeoLocation.lastReadFailed`：区分"读失败"和"确实没值"
- `MediaRepository.probeLocationAvailability(kind)`：抽查 30 条，返回
  `(hasPermission, scanned, withPoint, readFailed)`
- 设置页「显示拍摄地点」的副标题按结论分五种文案；未授权时整行变成可点的授权入口
- **同时去掉了申请上的开关判断**：原写法 `showMediaLocation && !hasLocationPermission`，
  只要开关状态和预期不一致就永远不弹窗 —— 改成无条件申请
- `SettingBlock` 加了可选的 `onClick`（`Modifier.then(if (onClick == null) Modifier else Modifier.clip().clickable())`）

**2. 全屏交互重做（按抖音）**
- 全屏按钮从侧边栏挪到**进度条这一行的右端**（视频下方）——
  它和"播放控制"是一类操作，和收藏/删除/分享不是一类
- 全屏时 `if (!fullscreen)` 同时收起**侧边栏**和**底部文字信息**，只留进度条 + 全屏按钮
- `BackHandler { if (fullscreen) applyFullscreen(false) else finish() }`
  —— 返回手势先退全屏，再按一次才收尾，所以不需要常驻的退出按钮
- 侧边栏和底部信息两处都需要 `if (!fullscreen)` 包裹，重排了缩进

**结果**：assembleDebug + lintDebug 全绿（0 错误 0 警告）。
`qushe-v1.0.14-debug.apk`（33MB，versionCode 15）。**一次编译通过。**

## 第二十轮：实况照片兜底被早退挡死 → 出 1.0.16

用户反馈：收藏视频改上下滑；位置自检是"第三种，n=30"；**实况照片还是不支持**。

**1. 实况照片的根因（重要）**
`MediaRepository.resolveMotionOffset` 里：
```kotlin
if (!probe.isMotionPhoto) return@withContext null   // ← 早退
val scanned = MotionPhoto.findByMp4Signature(...)   // 永远执行不到
```
`MotionPhoto` 设计了三层检测，第三层是**不依赖任何厂商元数据的 MP4 `ftyp` 签名扫描**，
专门用来兜"厂商 XMP 认不出来"的情况。**而那句早退恰好把它挡死了**：
XMP 认不出来 → isMotionPhoto=false → 直接返回 → 兜底从没跑过。

**教训：兜底逻辑绝不能挂在它要兜底的那个判断之下。**
这是一个"看起来在防御、实际把退路封死"的写法。
现在改成：元数据拿不到偏移量就**无条件扫签名**。

**2. probe 加尾部扫描**
原来只有"读文件头解析 XMP"一条路。新增：头部失败时读**文件尾部 4MB** 找 MP4 签名
（实况片段一定追加在末尾，ftyp 盒子必然在尾部窗口内）。
`findByMp4Signature` 因此加了 `fromOffset` 参数（传 0 = 全文扫描）。
这样既不必为每张照片读整个文件，又覆盖了"元数据完全不可用"的机型。

**3. 收藏视频改上下滑**
`MediaPreviewOverlay` 里把页面内容抽成 `val previewPage: @Composable (Int) -> Unit`，
然后 `if (allVideos) VerticalPager else HorizontalPager`。
**抽出 lambda 而不是复制整块 body，是为了不让缩进变化**（只改首尾 4 行）。
判据：`items.all { it.kind == MediaKind.VIDEO }` —— 混着照片时仍左右滑。

**4. 位置自检抽样纠偏（用户答"第三种，n=30"）**
`idsOf(kind).take(30)` 取的是**最旧的 30 张**，最旧的往往是截图和下载图 → 结论是假的。
改成 `shuffled().take(60)`。**"取前 N 条"在这类统计里几乎总是错的。**

**结果**：assembleDebug + lintDebug 全绿（0 错误 0 警告）。
`qushe-v1.0.16-debug.apk`（33MB，versionCode 17）。**一次编译通过。**

## 第二十一轮：位置第二条路径 + 照片页交互重做 → 出 1.0.17

用户反馈：位置还是不显示；要按「去留」重做照片页交互（下滑收藏→小按钮收藏、点 ⓘ 展开详情）。

**1. 位置：加了第二条独立读取路径（重点）**
之前只有一条路：读 MediaStore 的经纬度列。它受 `ACCESS_MEDIA_LOCATION` 约束，
而且**部分 ROM 干脆不返回这两列** —— 一旦如此就彻底没辙。

现在两条路（`GeoLocation.readPoint`）：
- MediaStore 的经纬度列（便宜）
- **直读原始文件的 EXIF GPS**（`MediaStore.setRequireOriginal` + `ExifInterface.getLatLong()`）
  ——不依赖 MediaStore 有没有填、甚至有没有这两列

自检也分得更细：新增 `GeoLocation.lastColumnMissing` + `LocationProbe.columnMissing`，
把「系统没返回这两列」和「返回了但是空值」分开报。**之前这两件事混在一起，
"系统不返回"被误报成了"照片没有位置信息"。**

**2. `core/PhotoExif.kt`（新增）**
读 EXIF：设备（Make/Model，型号已含厂商就不重复拼）、光圈、快门、ISO、焦距、GPS。
- `setRequireOriginal` 拿原始文件，EXIF 才完整
- EXIF 有理数是 `"1/100"` 这种分数，**必须自己解析**（`parseRational`）
- 快门按摄影习惯显示：<1 秒写 `1/100 s`，否则 `2 s`
- `getLatLong(FloatArray)` 已弃用 → 用无参的 `getLatLong(): DoubleArray`（精度还好）

**3. 照片页按「去留」重做**
- **下滑收藏 → 左下角圆形按钮**。理由写成注释了：**手势经济学** ——

## 第二十三轮：滑动闪烁的真正根因（SurfaceView）→ 出 1.0.19

用户反馈：①全屏提示太靠下 ②收藏页视频也要全屏 ③**整理视频和收藏页上滑都闪烁**。

**1. 闪烁的真正根因（重要）**
1.0.10 我以为根因是"首帧没渲染"+"相邻页缩略图没预载"，加了 `onRenderedFirstFrame`
和 `beyondViewportPageCount`。有用，但**不是根因**。真正的根因是视图类型：

> **Media3 的 `PlayerView` 默认用 SurfaceView。**
> SurfaceView 由系统在**独立图层**合成，屏幕位置更新和 Compose 的滚动不同步 ——
> 滑动时画面与页面脱节、闪烁。**列表/翻页场景必须用 TextureView。**

修法：新增 `res/layout/view_video_player.xml`（`app:surface_type="texture_view"`）
+ `createVideoPlayerView()`。**只能靠 XML 指定**——`PlayerView` 没有 surface_type 的 setter。
两处（整理视频页、收藏预览）都换掉。

**2. 全屏胶囊贴视频画面下边缘**
按当前视频实际渲染高度算：`rendered = min(屏高, 屏宽 × h/w)`，
`top = (屏高 + rendered)/2 + 14dp`。横屏视频在竖屏里是居中横带，胶囊要贴横带下沿
（抖音的摆法）。之前固定在底部信息区上方，离横带太远。

**3. 收藏页视频也支持全屏**
抽出 `ui/common/VideoSurface.kt` 共享：`createVideoPlayerView`、
`findActivity`、`applyFullscreenOrientation`、`FullscreenPill`。
返回手势先退全屏再关预览；`onDispose` 一定还原方向与系统栏。

**踩到的坑（这轮特别多，值得记）**
- **`sed` 把 `import ...layout.Box` 直接替换成了 `BoxWithConstraints`**（应该追加），
  导致 `Box` 全线 unresolved
- **Kotlin 局部变量/局部函数必须"先声明后使用"** —— `BackHandler` 写在
  `var fullscreen` 之前就报 Unresolved reference（类成员可以随便放，局部的不行）
- `FullscreenPill(onClick, modifier = ...)` 把 `modifier` 放在最后，
  于是尾随 lambda `FullscreenPill { ... }` **绑到了 modifier 上** →
  签名改成 `(modifier, onClick)`（Compose 的惯例就是这个顺序）
- `BoxWithConstraints` 的作用域在**存成 val 的 @Composable lambda** 里不生效 →
  预览页改用 `LocalConfiguration.current.screenHeightDp/screenWidthDp`（对全屏预览等价）
- Media3 的 `UnstableApi` 用**老式 opt-in 机制**，`@OptIn` 无效 →
  必须 `@androidx.annotation.OptIn(UnstableApi::class)`（项目里已有先例）
- `LayoutInflater.inflate(layout, null)` 触发 `InflateParams` 警告 → `@SuppressLint`

**结果**：assembleDebug + lintDebug 全绿（0 错误 0 警告）。
`qushe-v1.0.19-debug.apk`（33MB，versionCode 20）。跑 5 轮编译。

## 第三十五轮：闪烁的最后一层原因 → 出 1.0.29

## 第三十八轮：闪烁真正根因（宽高比未定时的首帧）→ 出 1.0.32

**用户的关键描述**：
> 1. 「感觉是**视频的某一帧被拉伸到了整个界面那么大**然后闪了一下」
> 2. 整个预览界面
> 3. **横屏不是必要条件，竖屏视频也闪；图片不闪**
> 4. 不确定上下滑的闪和点开的闪是不是同一种
> 5. 预览页闪，整理视频页也闪，**但整理视频页没有拉伸到整个屏幕**

**根因（终于对上了）**：
播放器刚启动时**还不知道视频宽高比**（`videoSize` 是 0×0），
这时 `AspectRatioFrameLayout` 会先按"填满整个视图"渲染 ——
于是出现一帧被拉伸填满整屏，拿到真实尺寸后才跳回正确比例。

**三条证据全部吻合**：
- "某一帧被拉伸到整个界面" ✓ 就是宽高比为 0 时的填满
- **图片不闪** ✓ 图片不走播放器
- **整理视频页不拉伸** ✓ 因为那里早就有 `playerVisible = isCurrent && firstFrameReady`
  的门控，**预览页没有** —— 这就是为什么"同源但表现不同"

**修法**：给 `MediaPreviewOverlay` 补上和整理视频页一样的门控 ——
`firstFrameReady`（`Player.Listener.onRenderedFirstFrame`）+ 翻页时重置，
播放器 `alpha = if (isCurrent && firstFrameReady) 1f else 0f`，
首帧就绪前露出下面的缩略图。

**方法论教训（重要）**：
前四轮我改的都是真实缺陷，但**一直没问"闪的到底是什么"**。
一旦拿到"被拉伸的某一帧"这个描述，根因立刻唯一确定。
**症状描述里的形状/颜色/是否变形，比"闪了一下"这种概括有价值得多 ——
应该在第一轮就追问，而不是开始改代码。**

**结果**：assembleDebug + lintDebug 全绿（0 错误 0 警告）。

## 第四十轮：上轮的可见性改动是错的，已回退 → 出 1.0.34

**用户反馈**：「整理视频页面视频被首图覆盖了，**声音还有，但画面不动**」

**这是我上轮（1.0.33）改坏的**，因果非常清楚：
```kotlin
update = { view -> view.visibility = if (isCurrent && playerVisible) ... }  // ✗
```
**`update` 只在重组时被调用，不会因为"首帧就绪"再跑一次。**
于是视图一直停在 `INVISIBLE` → 缩略图（首图）盖在上面，声音照常播放、画面不动。
**完全对应"被首图覆盖、有声音、画面不动"。**

**已回退**，并把这个教训写进代码注释：
> 显隐一律交给 `graphicsLayer { alpha = ... }`（带 lambda 的版本，**绘制时读状态**），
> 不要在 `update` 里设 `visibility`。

**这里还有个通用结论**：`AndroidView.update` 不是"响应式"的，
它只在 AndroidView 所在的那一段**重组**时执行。任何"需要随状态立刻变化"的
属性（显隐、尺寸、颜色）都不能写在那里。

### apk-installer 第二轮：用户反馈两个问题，全部修复

用户反馈：①exe 打开后 cmd 一直闪烁 ②检测不到手机。

**问题 1 根因：子进程控制台窗口（经典坑）**
- PyInstaller `--windowed` 程序没有控制台，每次调用 `subprocess` 启动
  控制台程序（adb.exe）时，Windows 默认弹一个新控制台窗口。
- 设备轮询每 2 秒一次 → "一直闪"。
- **修法：所有 subprocess 调用（run + Popen）加 `creationflags=CREATE_NO_WINDOW`。**
- 验证极严谨：写了窗口监控脚本 + **对照组实验**——
  对照组（不加 flag）12 秒 9 次弹窗（复现症状），修复版 0 次。✓

**问题 2 根因：设备解析 bug（我写的，非常隐蔽）**
- 用户手机其实连上了（小米 2304FPN6DC / Android 16 / SDK 36），
  但 GUI 检测不到。命令行 `diagnose` 却正常 —— 两个路径的差异暴露了 bug。
- `adb devices -l` 输出格式是 `product:ishtar model:2304FPN6DC`（**冒号**分隔），
  而 `devices()` 解析写的是 `token.split("=")` → ValueError →
  被 poller 的 except 静默捕获 → 每 2 秒崩一次 → 永远检测不到。
- **无设备时不触发解析，所以一直没暴露。这就是为什么"只有插上手机才出问题"。**
- 修法：`partition(":")` / `partition("=")` 兼容两种分隔符，且绝不抛异常。
- 教训：**"解析外部命令输出"的代码必须用真实输出验证，不能凭想象写样例。**
  我写代码时按 `key=value` 臆想了格式（adb 实际用 `key:value`）。

**新增能力**
- 「诊断」按钮：`kill-server + start-server` 重启服务 + 输出诊断报告
  （adb 路径/版本/原始输出 + 三种结论：未检测到/未授权/已就绪）
- poller 异常去重（同类错误只提示一次，不刷屏）

**Windows 环境新知识（重要，以后都用得上）**
- 这台机器默认终端是 **Windows Terminal**（不是传统 conhost）：
  控制台窗口类名是 `CASCADIA_HOSTING_WINDOW_CLASS` + `PseudoConsoleWindow`，
  **不是** `ConsoleWindowClass`。监控弹窗必须匹配这些类名 + 20ms 高频采样
  （窗口只存活约 100-200ms，0.5 秒采样会漏）。
- 验证方法论：**修一个"界面现象"类 bug，最好做对照组实验**
  （故意不修 → 应复现；修了 → 应消失）。只测"修了之后是好的"不够，
  因为可能是监控方法失灵。

**结论**：两个问题都是代码 bug 不是环境问题。重打包交付（11.6MB），
用户手机连着时预期打开即显示"已连接：Xiaomi 2304FPN6DC"。

## 新项目方向：微博收藏备份（放弃自建，改用成熟方案）

### 背景：自建的 weibo-fav-downloader 判定为失败

`weibo-fav-downloader/`（9/16 做的，157 项测试全绿）**用户从未跑起来过** ——
现场证据：`downloads/` 和 `cookies.txt` 都不存在。**问题不在代码质量，在架构选型。**

失败根因（对以后所有"带风控的站点采集"都成立）：
1. 要用户手动从 F12 复制 Cookie，且微博 `SUB` 字段极易复制错、几天就过期
2. 收藏夹 `containerid` 是**我根据搜索资料推测的**，从未用真实账号验证过
3. **最致命**：独立 Python HTTP 客户端没有浏览器指纹，微博风控（432/403）专治这种请求

**结论：有强风控的站点，正确解法是在用户浏览器会话里跑（油猴脚本），
或者用模拟正常访问节奏的桌面客户端。用独立 HTTP 客户端硬刚接口是逆风局。**

### 方案调研结论（三个候选，按贴合度）

| 方案 | 形态 | 是否覆盖「我的收藏」 | 产出物 |
|---|---|---|---|
| **WeiBack-rs** | Tauri 桌面客户端 | ✅ **唯一专做收藏备份的** | 网页归档 HTML + 本地数据库 |
| WeiBack（油猴） | 油猴脚本 | ✅（功能是桌面版的子集） | zip(HTML+图片) |
| weibo-image-downloader | 油猴脚本 | ❌ **不含收藏页**，只能逐条微博点 | 干净的图片文件 |

- WeiboImageDownloader 虽然最活跃（2026-09-18 更新）且下载的是"纯图片文件"，
  但支持的页面里**没有收藏列表**（只有首页 feed/用户主页/搜索/详情页）→ 不满足需求。
- **WeiBack-rs 的关键优势**：本地数据库 + `favorited_posts` 表，
  支持「备份 → 导出 → 对已备份的取消收藏」完整工作流，还能批量**取消收藏**。
