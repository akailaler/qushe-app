### ★★★★★ ④ 超长图看不清楚/拖不动的真正根因：`drawnSizePx` 把宽高写反了
`
容器 1080×2400、图 828×30656、ratio=0.027
正确 Fit：64.8 × 2400
实际代码：2400 × 64.8   ← 两个分支都反了

因为 `panLimit` 和 `snapScale` 全用 `drawn()` 的结果：

  ⇒ 放大上限锁死在 8 倍，而 828 宽的图要 16.6 倍才能铺满 ⇒ **看不清**

**更糟的是：我 1.3.62→1.3.65 据此得出过一条"长图不要传 contentRatio"的结论，写进了记忆。**

**Bug 修掉之后，两处调用点都必须传真实比例。**

### ⑤ `effectiveMax` 用 min 也是错的
`minOf(maxScale, snapScale)` 等于把"铺满屏幕"当成放大上限。
改成 `maxOf(...)`：`snapScale` 的语义变成**铺满所需的最小倍率**（回弹下限），
`maxScale`（8）才是最多能放多大。

offset 按 `target/scale` 等比放大（否则正在看的那段会被推走）。

## 1.3.80（收藏页漏传 + 性能回归）

### ① 「收藏里打开还是不清楚」= 第三处调用点漏传参数
`ZoomableImage` 有三个调用点：整理页、瀑布流、**收藏/喜欢的预览层**。
1.3.79 我只给前两处补了 `contentRatio` / `sourceSize`，**收藏页那处漏了** ⇒
`drawn()` 退化成"绘制区=容器"、上限被算成 8 倍（828 宽要 16.6 倍）⇒ 依旧糊。
**这是"同一组件多个调用点"第三次出问题**（前两次：`contentRatio`、`focusDecodeSize`）。
**以后改 `ZoomableImage` 的参数，第一件事是 `grep -rn "ZoomableImage("` 数调用点。**

### ② 进"回到那天"一片空白 = 焦点格被大图尺寸拖累
链路：`ZoomableImage.decodeSize` → `onRequestSize` → `DayViewScreen.focusDecodeSize`
→ 瀑布流的焦点格用**同一个 size** 请求（为了"点开大图时缓存命中"）。
1.3.79 让 decodeSize 变成原图（828×30656 ≈ 100MB）⇒ **那一格去解 100MB 的图**
⇒ 整页卡住、缓存被挤爆 ⇒ 一进去一片空白。
修法：焦点格的 size **封顶到显示尺寸的 2 倍**（格子只是 264dp 缩略图）。
代价是点开大图不再命中同一份缓存，但那边有缩略图垫底，换来整页秒开。

### ③ 解码像素上限
加 `MAX_DECODE_PIXELS = 24_000_000`（≈96MB）。828×30656 只缩到 800×29600（差 3%）。
**单张图的解码内存不能把 Coil 缓存吃光**，否则同页缩略图全被淘汰、反复重解。

### ④ 缩放内核的结论（用户问"要不要像小米相册"）
功能上已经覆盖甚至超过小米相册（多了"捏合回退到回到那天"）。
**结构上的病**：`contentRatio` 一个参数同时管 Fit 计算 / 边界 / 解码尺寸；
`snapScale` 名字叫"吸合上限"实际是"铺满下限"（1.3.79 起）。
今天两个 bug（宽高反、上限用 min）都源于此。
**结论：不重写（1100 行、风险远大于收益），但应做一次"参数收敛"** ——
把 `contentRatio` 拆成 `aspect`（只管几何），`snapScale` 改名 `coverScale`，
并给几何计算加不变量检查（Fit 后至少一边贴边、比例不变）。

## 1.3.81（超长图整张解码 → 区域解码）

### ① 「828×30656 还是看不清」的根因
`ZoomableImage` 对长图仍然请求 `容器 × 放大上限`、再用 `sourceSize` 封顶
⇒ 对 828×30656 等于**请求整张 25MP ≈ 101MB**。Coil 的 `size()` 只影响
`inSampleSize`（2 的幂），这个目标尺寸只能采到 1 ⇒ 真去解 101MB，
解不出来就退回"按容器解"的那一层（宽 200 多 px）⇒ 怎么放大都是糊的。
**这条是 1.3.79/80 引入的**：为了让放大后清晰，把解码尺寸抬到了原图，
但长图的原图本身就是内存灾难。

### ② 修法：底图 + 区域解码两层
- 超长图（高宽比 > 3）**底图只解"够 1x 看"的一份**：
  宽 = 1x 显示宽 × 2（128~1024 封顶）⇒ 828×30656 只需要 207×7664 ≈ 6MB。
- 放大后用 `BitmapRegionDecoder` 只解**当前视口那一段**（一屏约 1.5MP），
  按 scale/offset 反算可见区域，多解半屏做缓冲，`conflate` 丢中间帧。
- 区域用 `withTransform { translate; scale }` **浮点**画，不能用整数 `IntOffset`
  —— 局部坐标里 65×288 舍入 0.5px，乘 16 倍就是屏幕上的 8px 糊边。

### ③ 瀑布流缩略图的细条与闪退（同一个根因）
`size(292, 1080)` 请求 828×30656：`inSampleSize` 只能降到 2
⇒ **每格解 414×15328 ≈ 25MB**，快速拖底部刻度条连解几格就 OOM 闪退；
解出来缩进格子还是一根 6px 宽的细条。
新增 `LongThumbnailFetcher`：只解原图**垂直居中、宽取满、高 = 宽×3/4** 的一块
（828×621 ≈ 2MB），格子固定按 4:3 摆 ⇒ 不拉伸、不裁细条。
阈值用用户定的 **高宽比 > 3**；旧的 `isLongImage`（≥2）继续只管"长图"角标。
**同一个 URI 走两种 fetcher，靠 ImageRequest parameter 区分 —— 缓存键含 parameters，不会串。**

### ④ 待验证（真机没连）
- 828×30656 放大后是否真的到"原图上限"（源宽 828、屏宽 1080，1.3x 插值就是物理上限）。
- 拖刻度条是否还闪退（若还闪，需要 logcat 的 `FATAL EXCEPTION` 堆栈）。

## 1.3.82（长图缩略图 2:1 + 缓存不命中是"闪"和"闪退"的真凶）

### ① 用户反馈
- 1.3.81 后 828×30656 放大**清楚了**（区域解码有效）。
- 但拖底部刻度条**还闪退**。
- 4:3 长图缩略图在左右滑时**会闪**；用户要求合并规则：高宽比 > 2 都算长图，缩略图统一 **高:宽 = 2:1**。
- 文案要求：删掉换行、结尾的句号/分号。

### ② 闪 + 闪退的真凶：Coil 缓存尺寸校验
反编译 `coil.memory.MemoryCacheService` 确认：
`isSizeValid` 会把**缓存里的 Bitmap 尺寸**和本次请求尺寸逐像素比（允许 ±1px），
`isSampled` 只在"请求原尺寸"分支里有用。
我们的区域解码返回 **828×1656**，请求却是格子的 **540×1080** ⇒ 每次格子重新进入组合
都判定"缓存无效"⇒ **重新解一遍**。表现：
- 左右滑：缩略图来不及出图 ⇒ 闪；
- 拖刻度条：瞬间进出几十格，每格都重新解 5.5MB ⇒ 内存雪崩 ⇒ 闪退。
修法：`decodeRegion` 后 **`Bitmap.createScaledBitmap` 缩到请求尺寸**（并把原图 recycle），
缓存键对上了，第二次进入直接命中。
**教训：自定义 Fetcher 返回的位图尺寸必须等于 `options.size`，否则 memory cache 形同虚设。**

### ③ 2:1 规则（用户定）
- `MediaItem.isLongImage` 改为 `height > width * 2`（合并旧 `>=2` 与新 `>3`，删 `isUltraLong`）。
- 瀑布流格子宽 = 行高 / 2；区域解码取原图**垂直居中、宽取满、高 = 宽×2**。
- `ZoomableImage` 的区域解码阈值也改成 `ratio < 0.5`（同一套规则）。
