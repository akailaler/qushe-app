# 2026-10-22

## 1.3.88（设置页「检查更新」+ 收藏同步的机型边界）

### ① 用户的第二台设备：红米 K20 Pro / MIUI 12.5.6（Android 11）

反馈三件事：收藏同步双向都无效、加载图片有时慢、想要手动检查更新。

**收藏同步的结论：这台设备的相册不写 MediaStore 的 `is_favorite`。**
- 反向（系统 → 应用）：`allSystemFavoriteKeys()` 读到 0 条 —— 相册里的收藏
  存在小米相册自己的库里，没有落到 MediaStore。
- 正向（应用 → 系统）：`createFavoriteRequest` 不报错、读回校验也能过
  （所以 UI 显示"已同步"），但相册 App 不读这一列 ⇒ 用户看不到。
- 这不是我们的 bug：同一个功能在 HyperOS 3.0 那台机器上 286 条逐条对齐。
- **验证方法**（给用户）：在相册里手动收藏一张 → 取舍里点「同步系统收藏到这里」→
  若提示"没有读到任何收藏"，就证实是相册不写这个标记。
- 代码层面能做的都做了（写后读回校验 + 如实提示），**没有可绕过的正规路径**。

### ② 新功能：检查更新

- `core/UpdateCheck.kt`：查 `api.github.com/repos/akailaler/qushe-app/releases/latest`，
  取 `tag_name` 与本地 `versionName` 按点分段比较（不能按字符串比，`1.3.9 > 1.3.10` 会错）。
- 设置页底部（"管理权限"之后）加一行：**检查中… / 已是最新 / 发现新版本 → 去下载**。
  点"去下载"直接开浏览器到 release 页。
- 清单加 `INTERNET` 权限，**只有这一个请求会联网**，不做后台轮询、不上报。
- 失败一律降级成文案（超时 / 403 限流 / 404 没有 release），不抛异常。

### ③ 加载慢：暂不改

K20 Pro 是骁龙 855 + UFS 2.1，慢的是**随机读 + 解码吞吐**，不是逻辑问题。
已经做了的：0.75 倍解码、系统缩略图垫底、长图区域解码。
再快只能牺牲清晰度（降到 0.6）—— 用户对糊很敏感，先不动。需要问清是哪个场景慢。

## 1.3.89（正式签名 + 数据导入导出 + 缩略图 0.6）

### ① 发布签名（keystore）
用户问"能不能帮我弄，还是必须自己弄" —— **可以代生成，但密码和文件必须他自己保管**。
- `keystore/qushe-release.jks`（RSA 4096 / 10000 天，alias `qushe`），密码随机 28 位，
  **只写进 `keystore.properties`，不打印到对话**。
- `.gitignore` 补 `keystore/`（`*.jks` 和 `keystore.properties` 本来就在）。
- `app/build.gradle.kts`：有 `keystore.properties` 就用正式签名，没有就退回 debug 签名
  （换机器 clone 下来也能 `assembleRelease`）。
- **坑**：`storeFile` 里写的是 `../keystore/…`（相对 app 模块），
  用 `rootProject.file()` 会少一层目录 → `validateSigningRelease` 报文件不存在。
  必须用 `file()`。
- 备份在 `D:/backup/qushe-signing/`（含 README.txt 写清"丢了就再也发不了覆盖升级"）。
- **换签名后旧包不能覆盖升级，必须卸载重装一次**。

### ② 数据导入导出（`core/Backup.kt`）
- 导出：收藏 / 喜欢 / 已看三个集合 + 设置 + 统计，JSON。
- 导入：集合**并集**（只加不删）、统计取 max（不倒退）、设置覆盖。
- 用 SAF（`CreateDocument` / `OpenDocument`），不申请存储权限。
- **只存 storeKey**，换设备 ID 对不上 —— 副标题里写清楚"只适合重装恢复"。
- 入口：设置页「管理权限」下面，导出 / 导入 / 检查更新 三行。

### ③ 瀑布流缩略图 0.6 倍
`THUMB_DECODE_SCALE: 0.75 → 0.6`（像素降到 36%）。
**只影响格子**：点开大图走 `ZoomableImage` 的独立请求（容器 × 8 倍，原图封顶），
长图走区域解码，都不看这个值。

### ④ 长图"不够清楚"的答复
不是 0.75 造成的（长图根本不走那条路）。是源图宽度上限：
1x 时 828×30656 被 Fit 到 64.8×2400，"铺满"= 16.6 倍 = **1.3 倍源像素**，
与系统相册同尺寸时是一样的。再放大就是纯插值。
