## 2.0.0 配色推翻重做：配色优先，一套成对（22:20）

用户否掉了「西湖景 + 浅深分开选」这一版，两个要求很关键：
1. **配色本身要好看协调，不能为了名字硬凑** —— 名字只是配色的注释，不是配色来源。
2. **回到"一套含浅深"，但色卡保持左右并排**：挑一次整套生效，不要分开选两道题。

### 做法
先定 8 套配色（绿 / 蓝 / 橙 / 紫 / 金 / 青 / 粉 / 橄榄），跑对比度，
**再用 AWT 画总览图看整体** —— 第一版的深色底明度全挤在 L* 8–12，八套缩在图里像一堆黑；
把底色明度分三档（#0A1A19 / #15101F / #241610）后才有层次。**这一步必须做，
只看单个色值判断不了"八套放在一起好不好看"。**

名字是最后配的，八个典故：空山新雨（王维）、雪夜访戴（王子猷）、落霞孤鹜（王勃）、
月下叩门（贾岛）、松风煮茗（陆羽）、寒江独钓（柳宗元）、疏影暗香（林逋）、
富春山居（黄公望）。一个名字给一幅画，但**名字服从配色**，不反过来。

### 架构
`QusheSkin(id, name, light, dark)` 回到成对；`Prefs.skinId` 单值（键改成 `skin_id_v2`，
避开 1.8 那版 `light_skin_id`/`dark_skin_id` 的残留）；
`QusheColors.skin` 单数；色卡页一张卡左右两半（`MiniSwatch`）。

⚠️ 教训：重写 `verify.py` 的 `check_skins()` 时，用于定位的结束标记

## 2.1.0 深色底降饱和 + 新增黑白灰默认（22:00）

用户看完 2.0.0 的反馈，四条都很具体：
1. 深色"单看背景色感觉有点浓，有一种雾蒙蒙的感觉"，只有蓝色那套稍好
2. 需要一个黑白灰的默认配色
3. 松风煮茗、富春山居"黄不拉几绿不拉几，不够纯，脏脏的"
4. 不必所有配色都温馨，温馨两三个就够
5. 名字：富春山居/雪夜访戴/月下叩门不好听；**雪夜访戴（蓝）更适合叫「寒江独钓」**

### ★ "浓/雾"的根因是深色底的饱和度，不是明度
旧深色底按色相实打实配（深绿 #0F1B12、深金 #1D1709），最暗通道只有 9~16 ——
色相全压在最暗处，满屏就是一坨洗不干净的深色。
现在统一成"深灰里带一丝色相"：最暗通道 ≥20、S≈0.30、V≈0.118，
底/卡对比从 1.13 提到 1.19（卡片能浮起来，不再糊成一片）。
**判断方法**：算 `max(rgb)-min(rgb)`，8~10/255 是"看得出色相但不浓"，
超过 18 就发脏；同时最暗通道低于 18 会失去层次。

### 删掉两套"脏"的
- 富春山居（橄榄 #77703A）直接删 —— 橄榄色相 60-70° 天生"黄绿不分"
- 松风煮茗重做成「秉烛夜游」：主色 #86682C（色相 40°，纯琥珀），不再往绿偏
- **金/黄系的色相必须压在 35-42°，一旦超过 50° 就滑进橄榄区间，看起来就脏**

### 八套（默认那套排第一）
见素抱朴（黑白灰）/ 空山新雨（绿）/ 寒江独钓（蓝）/ 沧浪之水（青）/
暮山凝紫（紫）/ 落霞孤鹜（橙）/ 秉烛夜游（金）/ 疏影暗香（粉）
温馨的只有 3 套（落霞/秉烛/疏影），其余偏冷静极简 —— 用户明确说不用都温馨。

命名：见素抱朴（老子）、空山新雨（王维）、寒江独钓（柳宗元）、沧浪之水（屈原）、
暮山凝紫（王勃"烟光凝而暮山紫"）、落霞孤鹜（王勃）、秉烛夜游（李白）、疏影暗香（林逋）。

## 微博备份工具：单条微博内「部分图片删除」（当晚开工，未完成）

用户的一句话需求：**把空间让出来给更多微博**。当天拆成 5 条决定，
其中两条推翻了我先前的裁决（记录在这里，因为都很有代表性）：

1. 删图后**下次进来重排**，当场不重排 ⇒ 我原来设计的"占位格按 position 拼回原位"整套作废
2. 要**徽标**证明这条微博的图被删过 ⇒ `PostInfo.deleted_pic_count`，0 时不渲染
3. 删掉的图和**缺失图分开** ⇒ 落库时就剥 `pic_ids`，补图检测天然读不到
4. 灯箱按钮 + `Delete` 键，**攒一批再提交**（200ms write-behind），回收站决定彻底删除/恢复
5. **删完最后一张图 → 整条微博一起删**

### 三条定下来的关键设计

- **墓碑表 `deleted_pictures(post_id, pic_id, scope, entries, deleted_at, purged_at)`**，
  复合主键：`post_id` 是"拥有这份 pic_ids 的那一行"，转发时是**原帖行**（转发自己的 pic_ids 是空的）。
  ★ 转发卡片上的图就是原帖的图 ⇒ 在转发里删图会同时影响原帖和所有转发（同一份数据，不是 bug）。
- **★ purge 不能删墓碑行**：删了黑名单，下次备份把图重新下回来，用户白删。
  改成 `purged_at` 标记（文件删了、记录留着）；`has_original = purged_at.is_none()`，不 stat。
- **删图 0 磁盘 I/O**：文件与 `picture` 行都不动，只有 purge 碰磁盘 ⇒「恢复」是纯 DB 操作，秒完成、不联网。

### 两处必须先问用户再设计的地方

- "当场能不能不重排" —— 用户说可以，于是整套位置重建逻辑（含 `original_position()`）直接不要了。
  **先问这句，比先设计占位便宜太多。**
- "删最后一张图要不要连帖子一起删" —— 用户要删。但 `delete_post(deep)` 有坑：
  `deep=false` 只 cancel favorite、留空壳；`deep=true` 连带删所有转发。
  ⇒ 按子转发数 `n` 分叉：`n==0` 直接删；`n>0` **第一次请求零写入**、返回 `requires_confirm_deletion`，
  确认后带 `force_delete` 才删。**这是整个连锁删除唯一的危险窗口。**

### 范围收窄（把不可逆风险面砍到最小）

只支持**九宫格**（`pic_ids`/`pic_infos`/`pic_num`）。封面、正文内联图、图文混排、
**实况照片**一律不可删 —— 实况照片最硬：静图删了 `.mov` 在 `video` 表、purge 也不碰
⇒ 永久孤儿，正好违背"腾空间"。

### 踩到的坑

- 前端报 `owner_post_id: i64` "丢精度" —— **误报**，结构体有 `#[serde_as(as="DisplayFromStr")]`。
  **教训：Rust 侧写 `i64` 不等于 JSON 是 number，先 grep `serde_as`。**
- `canDelete` 只判 `type === 'normal'` 会放行**正文内联图**（`PostDisplay.tsx:458` 把 inline_map 也标 normal）
  ⇒ 必须带 `standalone_pics` 归属判定，且扫全量 `postInfos`（转发卡片的 standalone_pics 来自原帖）。
- `async fn` trait 方法带 `&[String]` ⇒ `Send is not general enough` / `Acquire not general enough`。
  **改 owned `Vec<String>`，别在 async 块里调泛型 `Acquire<'c>` 助手（内联 SQL 最稳）。**
