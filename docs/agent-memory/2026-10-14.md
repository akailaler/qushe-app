## 1.3.15（间距统一 + 定位/卡顿/错位同根 + 长条图吸合）

**大根因（一个 bug 解释三个症状）**：`CellSlot` 用 `Modifier.width(w).padding(end = gap)`
——**padding 在盒子内部**，总宽被 `width(w)` 钉死成 `w`，gap 只压窄内容，总宽没变。
而 `cumPx` 模型按「宽度 + gap」步进 ⇒ 第 k 格实际位置少 `k × gap`，
且误差是 `(k − 区间起点) × gap` 这种**随可见区间平移跳变**的量：
进场定位往右偏 + 横滑卡一下 + 两排错位（两排区间起点不同）全由此来。
修：外层盒子占 `w + gap`、内层盒子放图片。
**教训：`Modifier.width(w).padding(...)` 不等于「盒子宽 w + padding」，
想让步进含间距必须让总宽真的加上。**

- `cumPx` 取整改 `roundToPx`（Compose 布局就是这么取整的），
  否则每格差零点几像素、一两百格累积成几十像素的定位漂移。
- 横竖间距统一：上下不再写死 `ROW_GAP`，与左右同取 `DayMetrics.gap`（屏宽 2.2%），
  「一致」要是结构保证而不是两个数字碰巧接近。
- 长条图吸死：`clamp()` 里 `if (scale <= 1.001f) return Offset.Zero` 与
  「1x 也要消费手势」自相矛盾 —— 事件被吃掉、位移被抹零。
  **消费了手势就必须让它真的能动**；边界交给溢出量算，不溢出那轴自然是 0。
- 长条图 1x 单指拖拽只吃竖直轴、横向放行（否则左右翻页被抢）。

## 1.3.16（定位居中 / 焦点图恒在上排 / 刻度条光标 / 长条图吸合时机）

- **居中要对齐"格子中心"不是"左边缘"**：`cumPx[k]` 是左边缘，直接当中心用
  ⇒ 整格偏左半个格宽（100~500px，肉眼明显）。要 `cumPx[k] + w/2`。
- **"在上排"和"在正中"曾经互斥**：分排固定 `index % 2`，奇数序号焦点图天然落下排。
  解法不是改滚动算式，而是**让哪一组上排由焦点图决定**（topParity）；
  局部序号也不能写死 `focusIndex / 2`，要在本排 indices 里查找。
- **`scroll.maxValue` 不能当刻度条分母**：多排共用一个 ScrollState 而各排总宽不同，
  Compose 每次布局用"最后那排"覆盖 maxValue ⇒ 它在两个值之间跳 ⇒ 指针乱跳。
  改法：各排 `SideEffect` 上报自己的总长（去重，别每帧写 state），外层取 max。
- **拖动定位别用 `animateScrollTo`**：动画让实际位置追着手指跑，
  **松手那帧指针从手指位置切回真实位置 ⇒ 猛跳**。用 `dispatchRawDelta` 瞬时定位
  （非挂起、不吃 Mutex；`scrollTo` 是 suspend，onSeek 回调里用不了）。
- **长条图：显示比例属于"没放大时"，吸合属于"放大后"，不能混**。
  上一版为解决"看着没放大"让 1x 走 `FillWidth` ⇒ 长图一进来就溢出、
  上下滑被吃掉、**上滑删除失灵**。1x 一律 `Fit` 且**一个事件都不消费**，
  `contentRatio` 只用于放大后算平移边界（Fit 的绘制矩形 = contain 内接）。

## 1.3.17（两排分开动 / 末尾闪退 / 取整统一）

- **多排共用 ScrollState 的隐藏代价：各排 maxValue 不同 ⇒ 会"分开动"**。
  每排 `horizontalScroll` 都按**自己那排**的内容宽夹 `scroll.value`，
  两排总宽不同 ⇒ 滑到末尾短排先到顶、长排还在走；共享状态被反复夹 = 闪退来源。
  修法：**短排用尾部垫片补到统一总长**（`padToPx = max(spanTop, spanBottom)`），
  maxValue 恒等 ⇒ 谁都不可能先到顶。垫片放在端部垫片外，不进 `cumPx`。
- **改用 `indices.indexOfFirst { }` 求局部序号后必须守卫 -1**：
  `BooleanArray/FloatArray.getOrElse(-1)` 会抛下标异常（末尾闪退的第二处根因）。
  用 `idx in arr.indices` 双重守卫。
- **取整规则要全链统一**：视口、半视口、错位半格、单格全宽、`cumPx` 全用 `roundToPx`，
  任何一处用 `toPx` 留小数就会破坏"模型与布局逐格恒等"。

## 1.3.19（照「去留」录屏重做：架构纠偏 + 吸合照实测 + 组合期读下沉）

**关键突破：拿到了「去留」录屏（31.6s / 43fps / 220x480），逐帧量了数据。**
ffmpeg 在隔离环境里：`C:/Users/<用户名>/.workbuddy/binaries/python/envs/default/
Lib\site-packages\imageio_ffmpeg\binaries\ffmpeg-win-x86_64-v7.1.exe`
（`imageio_ffmpeg.get_ffmpeg_exe()` 可直接拿到路径）。

### 三个实测结论（都是量出来的，不是推断）

1. **两排独立滚动**：16.07s 那一帧，上排逐像素变化 0.00、下排 26.7。
   ⇒ 「去留」不用共用 offset。**我们共用 offset 是自找的麻烦**，
   为此付出的三笔（互相来回夹 / 尾部垫片凑总长 / 分母取折中）全部可以删掉。
   ⇒ **"两排天然同步"从来不是「去留」的行为，正确行为是"手指落在哪排滚哪排"。**
2. **吸合上限 = 图宽等于屏宽**：1x 完整显示宽 65px（屏宽 220）→
   捏合 0.70s 到 187px 精确停住 → 继续到 219px 时 x=[1,219] 顶边后停住。
   ⇒ 上限由容器尺寸算出，不是固定倍数（之前 maxScale=8f / 双击 2.5x 都错）。
3. **双击缩回用动画**：25.17→25.83s 共 0.66s 平滑收回，不是瞬移。

### 组合期读 state：真正的卡顿根因（比架构问题更隐蔽）

- `DecisionOverlay(offsetX = offsetX.value, ...)` 这一行在 `if (current != null)`
  **主体作用域**里 → 读 `.value` 把整棵子树登记成观察者 → 拖动每帧整屏重组。
  `DraggablePhoto` 自己 `graphicsLayer { }` 的正确写法被这个调用点抵消了。
  **教训：写对了局部还不够，要检查调用点有没有把值取出来当参数传下去。**
- `slide.value >= threshold` 结果只有两种，但**读取动作在组合期**就等于每帧重组。
  ⇒ 任何"高频 state 的派生标量"都要包 `derivedStateOf`。
- `LaunchedEffect(container, scale, ...)`：把每帧变的 `scale` 当键 ⇒ 每次捏合约 18 次
  协程创建+取消，且与手势里的 clamp 重复劳动。**高频量只能在 effect 体内读，不能当键。**
- `RoundedCornerShape` 组合期现算：值相同不会重建裁剪路径（equals 比值），
  但每次重组 new 一个是白付的 GC 压力 ⇒ 热路径上的形状提顶层单例。

### 已正确处理、不要动

`ZoomableImage` 的 offset/scale 只在 `graphicsLayer{}` 内读；
`DraggablePhoto` 的位移读在 graphicsLayer；`CellSlot` 的 widthPx 必须在组合期
（要喂 Modifier.width）；`derivedStateOf` + 二分查找算可见区间；
`key(global)` 按全局索引；静态图给 Coil size 而动图不给；圆角共享实例。

### 1.3.19 引入的两个真 bug（都已修）

1. **长图和普通照片都不能放大**（用户说"长图改动出来了一堆bug"）：
   `snapScale` 写成"取绘制矩形**长边**那一项"。长图 1x 时`dh0 == 容器高`
   （高度已贴边）⇒ 上限算成 1.0；普通照片 ratio 传 null 时两个比值都是 1.0。
   正确公式是 `max(屏宽/图宽, 屏高/图高)`（铺满容器），
   且 `ratio == null` 时**不下限**、退回 maxScale —— 宁可放大过头也不能"不能放大"。
2. **滑到未加载的图出现"红色删除"**：上滑露底层被改成"始终存在、只靠 alpha 隐掉"。
   已加载的照片会盖住它，但 `AsyncImage` 未出图时像素全透明 ⇒ 红底+"删除"整片露出。
   判断必须放回组合期（`derivedStateOf { slide.value > 0f }`），
   光靠 alpha=0 不等于"看不见"。
3. 顺带：**补间动画从不取消** ⇒ 与新手势同时写offset/scale，画面抽搐。
   `offset` 是普通 state不像 `Animatable` 会自动取消前一个，必须自己管 Job。

### 首页计数闪0

`photoCount` 初值是 `0`，真实数量要等`LaunchedEffect` 扫完MediaStore 才写回。
⇒ 改成 `Int?`，`null` = "还在数" 显示 `…`，真的是 0 才显示 "0"。
另外三个计数原本**串行**扫三次 MediaStore（数字一个一个跳）⇒ 改并行。

## 1.3.23（五项）

1. **删"松手进入回到那天"**：留着不只是冗余 —— 退出日期视图后它会**留在屏幕上**，

## 1.3.26（三个用户报的问题）

1. **长图放大后糊** —— 根因：`AsyncImage(model = uri)` 自动挂 `ConstraintsSizeResolver`，
   请求尺寸 = **容器尺寸**；而放大是 `graphicsLayer` 缩放，**解码器不知道**。
   长图 1x 只显示成两百多 px 宽 → Coil 按这个算采样率 → 解出两三百 px 的小图 →
   放大到铺满屏幕就是硬拉四五倍。
   修：新增 `ZoomableImage.decodeSize` = **容器尺寸 × `effectiveMax`**，
   通过 `rememberDisplayRequest` 显式 `.size(w, h)`。
   **关键依据**（Coil 源码 `AsyncImagePainter.updateRequest`）：
   `if (request.defined.sizeResolver == null)` 才挂 canvas 尺寸 ⇒ 显式 size 不会被覆盖。
   **`ratio == null` 时必须返回 null 不猜** —— 那时 `snapScale` 会退回 `maxScale`(8)，
   照着算就是"容器 ×8"的白解一张巨图。
   （`PhotoSessionScreen` 只给长图传 `contentRatio`，普通照片是 null ⇒
   正好只有长图走这条，和用户报的场景吻合。）
   另：动图**不能**给 size（`ImageDecoderDecoder` 会翻成 `setTargetSize()`，动画源会闪退）。

2. **进场焦点定位偏左/偏右** —— 用户的关键线索："点一下定位按钮倒是能回到中间"。
   根因就是这句话：`scroll.scrollTo(x)` 内部走 `scrollBy`，
   会被 `ScrollState.maxValue` 夹；而**进场那一刻布局还没落地，maxValue 还是 0**
   （或另一排布局完留下的值）⇒ `scrollTo(5000)` 的结果是 0 = 完全没滚动。
   布局顺序换一下又夹到另一个值 ⇒ "有时候偏左有时候偏右"。
   **点按钮时布局早已稳定，所以那下总是准的。**
   修：`withTimeoutOrNull(500) { snapshotFlow { scroll.maxValue }.first { it >= target } }`
   等到就绪再滚。
   - 先试过 `scroll.value = x`（字节码确认 setter 只赋值不夹），
     但**setter 是 private**，编译报 `Cannot access 'value'`。此路不通。

3. **瀑布流上滑删除改成"飞出去"**（对齐整理照片页）。
   原来是滑够就当场 `markDelete` ⇒ CellSlot 立刻剔格，照片"啪"地消失。
   现在先播 200ms 向上飞出（`maxSlidePx * 2f` ≈ 格高 1.1 倍），落地再标记。
   两个坑：① **触发后一次都不许再写 `slide`** ——
   手指还按着，跟手的 `snapTo` 会把飞出动画取消、把照片拽回来（加 `!triggered` 守卫）；
   ② `markDelete` 放 `finally` —— 格子中途被移出组合时协程会取消，
   普通写法会让这一滑白滑。

## 1.3.27（焦点定位真因 + 飞入动效 + 两处小改）

### ★ 焦点图偏左偏右的**真正根因**（前两版都没修对）

**两排都在做进场定位，互相覆盖。** 两排共用一个 `ScrollState`，都去 `scrollTo`
就是互相盖，最后停在哪取决于**谁的 effect 后跑** ⇒ "有时候偏左有时候偏右"。

两个错处：
1. `DayFilmstrip` 里下排的调用**一直传着 `focusItem` + `ownsFocus = true`**
   —— 而函数头注释写的是"下排传 null"。注释和实现不符，就是这个 bug 的温床。
2. `seededTarget` 里留着 else 分支：焦点图不在本排就按 `focusIndex / 2`
   折算一个"对应格"去定位。**那是旧版 `index % 2` 交错分排时代的遗留** ——
   分排改成按宽度贪心均衡后，序号和排别已无固定关系，折出来的根本不是对应那张，
   只是碰巧落在下标范围内。

修：下排 `focusItem = null, ownsFocus = false`；`seededTarget` 只认本排焦点格。

**教训：改架构（分排方式）时要回头把依赖旧不变量的分支一起清掉，
只改主路径 = 留一颗定时炸弹。**

另外进场定位从"推一次"改成**每帧检查、没对上就再推**（上限 20 帧），
不再依赖 `maxValue` 何时就绪。

### 飞入动效

做法：**让焦点格自己**从照片页那张图的位置和大小插值回自己的位置。
- 不做"另画一张会飞的图"—— 那要再解一次码，解码慢于动画就会看到
  "格子已到位、飞行图才出现"的错位；让焦点格自己飞则是**一份图、一次解码**。
- 起点：整理照片页用 `onGloballyPositioned` 量容器 + `ContentScale.Fit` 算图占的矩形
  （`fitInside`），在 `openDayView` 那一刻**定格**。
- 终点：焦点格自己 `onGloballyPositioned` 上报的布局矩形（`boundsInWindow`，
  不受 graphicsLayer 变换影响）。
- 其余格子：前 55% alpha=0、后 45% 淡入 —— "飞过去成为焦点图，然后加载两边的图"。
- 有飞入时**不叠加**原来那套整屏缩放（`enter`），两层变换会打架。

三个实现坑：
1. **`DayViewScreen` 和 `DayFilmstrip` 是两个函数**（514 行处 `DayViewScreen` 就结束了）。
   动效状态定义在前者、`Column{FilmstripRow}` 在后者 ⇒ 跨函数不可见。
   状态必须放在 `DayFilmstrip` 里，`introFrom` 当参数传下去。
2. **`remember { { r -> x = r } }` 里写 `by` 委托属性编译不过**（未解析），
   内层 lambda 拿不到委托变量。改成显式 `val state = remember { mutableStateOf(...) }`
   + `state.value`。
3. **终点坐标没测到之前，焦点格必须 alpha=0，不能"无变换"画** ——
   否则会先在最终位置闪一帧再跳回起点。

### 其他

- 胶片条角标补 `长` / `截`，优先级与瀑布流对齐：视频 ▶ > 实况 > 动图 > 长图 > 截屏。
- 设置项「操作栏放在右侧」→「操作栏放在哪」+ 左/右两个 `Chip`。

## 1.3.28（深夜续：捏合触发 + 飞入黑屏/衔接）

### 捏合"要试好几次"的根因

触发量原来是**逐帧累加** `overPinch += (1 - zoom)`，往外张的帧再扣回去。
**真实手势根本不单调** —— 手指落下、调整姿势的时候有一堆往外张的帧，
它们把攒起来的量一次次扣掉，于是"明明捏了半天却没反应"。

修：改用**两指间距 / 起手间距**这个**单调量**：
`overPinch = 1 - span / pinchStartSpan`。
（`calculateCentroidSize` 在 Compose 1.7.5 里没有，直接
`(pressed[0].position - pressed[1].position).getDistance()`。）
阈值顺势 0.12 → **0.10** —— 12% 那个数本来就是"会被扣分"的算法下调出来的。
起手判定 `scale <= 1.001f` → **1.01f**，和别处"是否放大"的判定对齐
（浮点残留不该让整串手势作废）。

**教训：凡是"逐帧累加 + 反向扣减"的手势判定，都要先问一句
"真实手势是单调的吗" —— 不单调的输入必须换成单调量（首末对比），
否则用户实际要做出远超阈值的动作才能触发。**

### 飞入"黑屏一下"的两个来源

1. 日期视图那一层原来是**瞬间完全不透明**（有飞入时直接 `alpha = 1`）——
   一点下去整屏"啪"地全黑。改成**从透明淡入**（`enter` 从 0 起），
   底下那张照片一路透到被盖住为止；起点处两张图本来就重合，看起来就是同一张。
   **有飞入时只淡入、不缩放不位移**（两层变换叠加会让焦点格的起点算不准）。
2. 焦点格高清图要几十毫秒才解出来，而飞入第一帧就开始了 ⇒ 格子空的。
   修：给焦点格垫一张**系统缩略图**当 `placeholder`（1~2ms 就有），
   高清到了 Coil 自己淡入。**只给焦点格垫** —— 其余格子是在动画后半段淡入的，
   那点解码时间被动画盖住了，不必多付一次请求。

顺带：`AsyncImage(model = uri)` 的请求和照片页那个 size 不同 ⇒
**memory cache 必然 miss**，所以焦点格确实要重新解码 —— 这是"黑屏"的物理原因，
垫缩略图正是对症的。

## 1.3.29（三项）

1. **飞入"起手到飞行之间"的跳变** —— 起点原本按**1x** 的矩形算，

   焦点格先按 1x 出现、再"啪"地缩到画面里那张的大小。

### ★ 用抽帧分析"去留"录屏，定位我们的飞入"闪烁"根因

**工具链**（以后分析录屏照这个来）：

**先拼网格看流程、再对关键时间点抽原始尺寸帧** —— 网格太小看不清细节。

**"去留"的转场（t=0.5/1.5/2.5 三帧）**：
- 0.5s：单张查看，全屏满幅、完整比例
- 1.5s：照片已缩小+上移，周围格子**已排好位置但暗着**，照片**依然完整、依然清晰**
- 2.5s：日期视图成型

⇒ **全程是同一张照片、同一份像素在连续缩放位移，没有换图源**。
所以既没有黑一下、也没有清晰度跳变。

**我们的闪烁 = 换图源**：
照片页请求 size = 容器尺寸；焦点格请求 size = 格子尺寸
⇒ Coil memory cache key 不同 ⇒ **必然 miss** ⇒ 重新解码。
我上一版垫的**系统缩略图**正是闪烁来源：起手一刻从"高清"突变成"512px 糊图"，
几十毫秒后又变高清 —— 用户看到的就是这个闪烁，不是黑屏了。

**拟定方案（已讲解，等确认）**：让焦点格的请求 size 和照片页**完全相同**
（`ZoomableImage` 把实际解码尺寸回调出来 → 传给日期视图 → 焦点格照用）
⇒ 同 uri + 同 size ⇒ **缓存直接命中** ⇒ 第一帧就是同一张高清图。
代价：焦点格持有"照片页那个尺寸"的 bitmap，但那是缓存里已有的同一份，不产生新解码。

## 1.3.34（★ 黑屏的真正根子）

**`Modifier.background` 只影响它之后的那截链。**
`DayViewScreen` 原来写的是
`.fillMaxSize().background(Ink)...graphicsLayer { alpha = enter.value }`
—— background 在 graphicsLayer **前面**，等于画在 alpha 层**外面**，
**从头到尾不透明**：进场第一帧就把底下的整理页整个盖住，`alpha = 0` 等于没设。
移到 `graphicsLayer` **之后**，它才真正跟着淡入。
**这就是用户报了三轮的"捏合进去黑屏一下"的根子** ——
他自己那句"因为背景是黑色，所以闪一下都是黑屏"直接点到了。

⇒ **长期规则：要让一层整体（含背景）淡入，`.background()` 必须写在
`graphicsLayer { alpha }` 之后。写在前面等于背景永远不透明。**

另一处：**`ZoomableImage` 垫一层系统缩略图**。
高清解码要时间（超长图几十上百毫秒、动图更慢），空档期背景是黑的 ⇒ 闪黑。
缩略图 1~2ms 就有 ⇒ 闪的只剩"清晰度"不是"有没有"。
对动图尤其关键（动图不能给 size，只能按原分辨率解，最慢）。
用户猜"超长图是不是因为重新解码了更高清晰度"——对的，那正是 1.3.26
为"放大要看清楚"引入的，现在用垫底把空档补上。

## 1.3.35（三项细节）

1. **★ 滑到动图/超长图还闪 —— 因为没有预加载**。
   整理照片页的翻页是**自己实现**的（`DraggablePhoto` 拖拽 + 换 index），
   **没有 pager 的 `beyondBoundsPageCount`** —— 每张都是"滑到才开始请求 + 解码"，
   那一两帧画面是空的 ⇒ 背景纯黑 ⇒ 闪黑。
   修：`ZoomableImage` 加 `preloadNeighbors: List<MediaItem>`，
   在 index 变化时提前 `enqueue` 前后各一张（只请求不显示）。
   尺寸用**它自己算的那个**（`decodeSize ?: container`）才能命中缓存；
   动图**不给 size**（和主请求的 cache key 同样是"无 size"，也对得上）。
   ⇒ **自制的翻页/列表要自己实现预加载 —— pager 帮你做的那件事没有免费替代。**
2. **捏合提示"一闪而过"**：alpha 原来直接跟 `pinchToDateProgress` 走，
   而进度一到 1 就立刻跳页 ⇒ 永远停在"刚开始看清就没了"。
   改成 `(progress * 5f)` —— 两成进度就完全显现。
3. **横屏照片飞入"不顺畅"**：两头（原图 / 焦点格）宽高比不一定严丝合缝
   （格子宽度有 `CELL_MAX_WIDTH`/`CELL_MIN_WIDTH` 夹），
   分别按宽高算两个 scale 会**把图拉变形**。
   改取**几何平均**当统一缩放 ⇒ 全程不变形，位置仍按中心对齐。

## 1.3.36（★ 换思路：不让画面出现空档）

**用户问"你有更好的方案吗"——有，而且前几版方向就偏了。**

前几版都在做同一件事：**往"图还没就绪"的那一两帧里塞东西**
（系统缩略图、预加载相邻页）—— 但**都是在赌"来得及"**。
解码只要慢一点，那一两帧照样是空的；背景是纯黑 ⇒ 空 = 黑。

**新方案：根本不让画面出现空档** ——
新图没就绪之前，把**上一张**继续画在最下面。
它**已经在内存缓存里**，组合完第一帧就有（不需要 IO、不需要解码），
比任何"提前请求"都可靠。

`ZoomableImage` 现在是三层（从下到上 = **从可靠到不可靠**）：
1. **上一张**（`DisposableEffect(displayRequest) { onDispose { prev = displayRequest } }` 记下来的）
2. **同一张的系统缩略图**（1~2ms；首次进入、没有"上一张"时靠它）
3. **高清主图**（几十上百毫秒）

叠起来的效果就是"旧图还在 → 新图盖上来"，翻相册的手感。

⇒ **长期原则：'避免空档'比'尽快填满空档'更稳。**
凡是"背景是纯黑 + 内容异步就绪"的地方，
都应该让**旧内容留在原地**直到新内容可画，而不是清空再等。

另：捏合提示改成**独立时长**的淡入淡出（140ms 进 / 260ms 出），
不再跟捏合进度走 —— 进度一到 1 就跳页，跟进度走等于永远看不清。
