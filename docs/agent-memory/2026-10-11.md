**王波粒的核心设计论点（可直接复用到自研项目）**
1. 拒绝 Tinder 式「左滑删/右滑留」：照片整理不是二选一决策，照片不管它也在相册里，逼用户逐张判断与心智不符
2. 选手势原则：只用用户**已经会**的手势（左右翻页来自系统相册，上滑来自多任务界面）
3. 翻页动画：当前照片跟手左移，下一张**垫在下面**而非从右滑入 —— 眼睛不用等下一张停下，连滑几百张不累
4. 一次只看一种类型（不混合照片/视频/截图），避免大脑在多任务间切换
5. **视频刻意打破上述规则**：独立 Tab + 短视频 UI/手势，制造「刷自己人生短视频」的错位感
6. 不显示「还剩多少待处理」（todo list），只显示「已整理多少」（done list），消除心理压力
7. 随机顺序本身是核心创新：顺序删除像流水线（下一张可预测）所以枯燥

**手势冲突的标准解法（本文最大收获）**
上下滑被「切换视频」占用后，删除/收藏不能再押在滑动上 → 分层：导航归滑动，决策归双击 + 侧边按钮。这正是上一轮我提出的「手势冲突」问题的现成答案。

**关键工程决策（写进 README 了，后续改代码前必读）**
1. `minSdk = 30` 是刻意的：`MediaStore.createTrashRequest` / `createDeleteRequest` 都是 API 30 起。
   低于 30 需 WRITE_EXTERNAL_STORAGE 直接操作文件，是另一套路径。回留也只支持 11+。
2. **手势层最重要**：`ui/common/Gestures.kt` 里 `detectTapsWithoutConsuming` 全程不调 consume()。
   因为 `detectTapGestures` 内部 `down.consume()` 会让 VerticalPager 拿不到拖拽 → 视频流划不动。
   判定"其实是拖拽"靠 `positionChangeConsumed()`。
   坑：长按判定不能只看超时，用户拖到一半停住也会超时 → 用 `dragged` 标志放过。
3. 手势分层：导航(上下滑) / 临时动作(长按倍速) / 决策(双击收藏) / 危险动作(侧边按钮删除)。
   删除刻意不给手势 —— 越顺手越易误删。
4. 照片翻页：下一张**垫在下面原地露出**，不是从右侧滑入（去留的细节）。用 graphicsLayer 位移不用 layout offset。
5. 删除走「标记 → 一组后批量确认 → 系统授权框」。系统弹窗取消时 resultCode != RESULT_OK，该项不计入已删除统计。
6. **MediaStore 图片和视频的 _id 会撞号**（两张独立表各自自增）→ 收藏/已看集合必须用复合键
   `storeKey() = id * 2 + (video ? 1 : 0)`。这是个容易忽略的坑。
7. 回收站用系统的（`createTrashRequest`），不自己搬文件 —— 搬进应用私有目录卸载即丢失。
8. 视频页永远先渲染 Coil 抽的首帧，播放器叠上面 → 避免"先黑一下再出画面"。单页只养一个 ExoPlayer。

### 第五轮：真机试用反馈 → 三个修复，出 1.0.1

用户反馈「可以正常跑起来」（首次真机验证通过），提出三个问题，全部修复：

**1. 照片堆叠：下一张会提前透出来（尤其是细长的竖图）**
- 根因：`PhotoLayer` 用 `ContentScale.Fit` 完整显示照片（刻意不裁切用户自己的内容），
  横图上下会留黑边，而**留边区域原本是透明的** → 下层那张更细长的竖图从留边处透出来。
- 修法：每层加 `background(Ink)` 不透明底 + **不做缩放**。
- 重要教训：**不能给下层做缩放堆叠效果**。一旦下层比上层小，上层的边缘就会露出再下一层，
  屏幕上会同时出现两三张不同的图——正是用户抱怨的现象。所有层必须全屏 + 不透明 + 完全重叠。

**2. 左右滑都改成「下一张」**
- 原设计左滑前进 / 右滑回退（去留式双向翻页）。用户明确要求两个方向都前进。
- 随机流里回退确实没意义，且误触会打断节奏。
- 实现注意：`targetX` 要看 `x` 的符号决定朝哪边飞出，不能固定方向。
- `SwipeDecision.PREV` 保留在枚举里但已不可达（防御性保留，注释说明）。

**3. 收藏打通系统相册（重点）**
- **关键发现：`MediaStore.createFavoriteRequest` 是 `since="30"`，不是 API 33！**
  用 `platforms/android-35/data/api-versions.xml` 精确查证（正则提取 `<method ... since="N"/>`）。
  `IS_FAVORITE` 列也是 since=30。所以 Android 11+ 全支持，与 minSdk 30 正好一致。
- 核心约束：**系统不允许应用静默修改收藏标记，每次都要弹系统授权框**。
  所以绝不能在下滑收藏的瞬间调用（会毁掉手势体验），必须攒批提交。
- 实现：
  - `MediaRepository.requestFavorite(items, favorite)` → `createFavoriteRequest(...).intentSender`
  - 新增 `synced_favorites.txt`(IdSetStore) 记录已对齐项
  - `SessionRepository.favoriteSyncDelta()` 算差值：`toAdd = favs - synced`，`toRemove = synced - favs`
    （**取消收藏也要同步撤回**，否则两边长期不一致）
  - `pendingSyncCount()` 纯集合运算，可安全在组合中调用
  - AppRoot 里两个 launcher 串行推进（先 toAdd 后 toRemove），只有 `RESULT_OK` 才标记已同步
  - Prefs 加 `autoSyncFavorites`（默认开）；FavoritesScreen 加手动同步入口；SettingsScreen 加开关
- 排查顺序参考：先 toAdd 弹框 → 回调里再处理 toRemove。

**交付**：`qushe-v1.0.1-debug.apk`（33MB，versionCode 2 / versionName 1.0.1）。
assembleDebug + lintDebug 依然全绿（0 错误 0 警告）。
构建期只踩到一个小问题：AppRoot 缺 `androidx.activity.result.IntentSenderRequest` 的 import。

- **关键：`storeKey()` 无需改动**。截屏和照片同属 images 表，id 表内唯一，
  映射到同一键空间不会撞车 → **收藏/已看数据不需要迁移**
- **踩到的坑**：`reconcile()` / `favoriteItems()` / `favoriteSyncDelta()` 原来只取
  `all(PHOTO) + all(VIDEO)`，加了截屏后会漏掉截屏的收藏 → 被 `retainOnly` 误清！
  新增 `MediaRepository.allImages()`（一次拿照片+截屏，共用一份缓存）统一替换。
  **教训：新增枚举值时，要全局搜一遍只列举旧值的集合运算。**

**2. 双指缩放（ZoomableImage，通用组件）**
- 双指捏合 + 放大后单指平移 + 双击在 1x/2.5x 间切换
- **手势归属是核心**：只吃"双指"和"已放大后的单指"，其余放行。
  依据是子节点在 Main 阶段先收到事件，消费了父节点的 `awaitTouchSlopOrCancellation` 就放弃
- 用 `event.calculateZoom()` / `calculatePan()`（`androidx.compose.foundation.gestures`）

**3. 缩略胶片条（ThumbnailFilmstrip，通用组件）**
- **居中技巧**：给 LazyRow 加左右等宽的 `contentPadding = (屏宽 - 缩略图宽)/2`，
  这样 `scrollToItem(i)` 天然居中，不用自己算偏移量
- 当前项高亮描边 + 不压暗 + 放大 1.1x，其余项 alpha 0.55
- 默认收起，单击展开/收起（用户要求）；未展开时底部显示操作提示

**4. 动图**：加 `io.coil-kt:coil-gif:2.7.0`，在 QusheApp 注册
`coil.decode.GifDecoder` + `coil.decode.ImageDecoderDecoder`（API 28+ 管动态 WebP/HEIF）。
**类名已用 jar tf 核对 AAR 确认，不是猜的。**

**5. 实况照片（Motion Photo）—— 本轮最难的一块**
- **Android 完全没有官方 API**：核对过 `api-versions.xml` 和 `android.jar`，
  既无 IS_MOTION_PHOTO 列也无任何相关类。唯一线索是 `MediaColumns.XMP`（since=30）
- 实现：XMP 正则提 `MicroVideoOffset` → 拿到"距文件尾字节数" →
  流式抽取尾部 MP4 到 cacheDir → ExoPlayer 播放
- XMP 为空时退化：读文件头 64KB 嗅探。**只在查看某张时触发，不进列表查询路径**
- 交互：长按播放（对齐 iOS 相册习惯），角标"实况"，失败时明确提示不报错
- 只支持标准 MicroVideoOffset 格式（Google 系）；三星/小米变体可能识别不出

**6. 内层外层点击检测共存技巧**
ZoomableImage 内部处理双击、外层处理单击，两者都不消费事件 →
双击时单击回调也会触发一次。**但被触发的是幂等开关（胶片条显隐），切两次等于没切**。
用幂等操作吸收冗余事件，比做双击超时仲裁可靠得多。视频页的"单击暂停+双击收藏"同招。

### 第八轮：小米格式分支 + 进度条 bug → 出 1.0.4

用户反馈两点。**用户手机是小米。**

**1. 视频进度条从中间往两边长 —— 是 bug 不是设计**
- 根因：进度条父容器写了 `contentAlignment = Alignment.Center`（本意是让 2dp 细线
  在 26dp 触摸区里**垂直**居中），但 Compose 的 `contentAlignment` 是**两轴一起作用**，
  于是填充条也被横向居中 → 从中间展开。
- 修法：给填充条单独加 `.align(Alignment.CenterStart)`。
- **通用教训**：用 `contentAlignment` 做单轴定位的地方都有这个陷阱。
- 对照：`MediaPreviewOverlay.VideoProgressLine` 没写 contentAlignment（默认 TopStart），所以它一直是对的。

**2. 小米的实况照片格式（做了正经检索，不是猜的）**

查到三代格式，全部实现：
- **旧标准**：`GCamera:MicroVideoOffset` = "距文件尾字节数"。Google 早期 + 旧版 MIUI。
- **新标准**：`Container:Directory` → `Item:Semantic="MotionPhoto"` 那一项的 `Item:Length`。
  三星/Pixel 一直用；**小米从 HyperOS 3 起也切到这个**（这是关键情报）。
  ⚠️ 不能全局搜第一个 `Item:Length` —— 主图项也有 Length，取错会算出完全错误的偏移。
  实现是**按 `Container:Item` 切段，只在语义为视频的那段取值**。
- **无元数据兜底**：MP4 第一个盒子是 `[4字节长度]["ftyp"][主品牌]`，
  搜 `ftyp` 位置减 4 即视频起点。**不依赖任何厂商元数据**。
  三重校验防误报：盒子长度 16..1024、主品牌在 15 项白名单内、视频必须落在文件后半段；
  能读到紧邻的 JPEG 结束标记 `FFD9` 则直接确认。

**探测拆成两级（性能关键）**
- `probeMotion()`：廉价，只读 128KB 文件头，**不扫全文件**。每张照片切前台时调用，
  解决"MediaStore XMP 列为空就完全发现不了实况照片"的问题。
- `resolveMotionOffset()`：深度解析，元数据无果时才调 `findByMp4Signature()` 扫全文件，
  **只在用户长按播放时触发**。结果按条目缓存在内存。

**踩的坑（两次都是我自己造成的）**
1. 一次 Edit 把 `MediaRepository.all(kind)` 整个覆盖掉了 → 后续还要补回来
2. 旧版 `resolveMotionOffset` 没删干净，和新版**函数签名重复**（Conflicting overloads），
   连带 AppRoot 报 Overload resolution ambiguity
→ **教训：大段替换函数体时，务必确认旧函数被完整移除，而不是只换掉开头。**

**结果**：assembleDebug + lintDebug 全绿（0 错误 0 警告）。
`qushe-v1.0.4-debug.apk`（33MB，versionCode 5）。共跑 3 轮编译（2 轮修我自己的编辑错误）。

### 第九轮：严重回归 — 照片一张读不出来 → 出 1.0.5

**用户反馈**（附截图）：1.0.3 起「整理照片 = 0，整理截屏 = 0，但整理视频 = 8544」正常。
这是**我在 1.0.3 引入的 bug**。

**根因（很值得记）**
1.0.3 为了在查询阶段就识别实况照片，把 `MediaStore.MediaColumns.XMP` 加进了图片查询投影。
**这一列受 `ACCESS_MEDIA_LOCATION` 约束**（用于位置隐私脱敏），
**部分厂商的 MediaProvider（含小米）只要在投影里看到它就直接抛异常**。
异常又被 `runCatching(...).getOrDefault(emptyList())` 静默吞掉
→ 表现成"照片 0 张"，且完全看不出原因。
视频那条路径没加 XMP，所以 8544 正常 —— 这个"一半正常一半空"的现象是定位的关键线索。

**修法**
1. **把 XMP 从查询投影里彻底移除**。实况判定改为完全依赖 1.0.4 加的
   `MotionPhoto.probe()`（读 128KB 文件头），本来就不需要这一列也不需要额外权限。
2. **查询加两级投影兜底**：完整投影抛异常 → 自动退到 `MINIMAL_PROJECTION`
   （只留 _ID / DISPLAY_NAME / SIZE / DATE_ADDED / MIME_TYPE 这些任何版本都有的列）重试。
   以后任何一列在某个 Provider 上不可用，也不会退化成"整个相册是空的"。
3. **区分"确实没有内容"和"内容读不出来"**：`MediaRepository.lastQueryFailed` 标志
   → `SessionUi.Empty(kind, queryFailed)` → 空状态弹层分两种文案，失败时用 AccentDelete 标题直说。
   **这次排查难就是因为失败被伪装成了空。**
4. 实况角标改由文件头探测驱动：卡片切到即探；胶片条改 `motionKeys: Set<Long>` 参数 +
   整组预探测（十几张约 2MB）。

**教训（写进 README 了）**
- **永远不要 Query MediaStore 时把可疑列塞进投影**。MediaProvider 的实现差异很大，
  一列不可用就整条查询失败。要么只用最基础列，要么做分级兜底。
- **不要把异常静默吞成空数据**。`runCatching{}.getOrDefault(emptyList())` 在查询路径上
  极其危险 —— 用户看到的是"没内容"，实际是"读失败"，两者排查成本差一个数量级。
- 需要 XMP / EXIF 这类敏感元数据时，直接读文件头（`openInputStream` + ExifInterface 或字节搜索），
  不要走 MediaStore 投影。

**结果**：assembleDebug + lintDebug 全绿（0 错误 0 警告）。
`qushe-v1.0.5-debug.apk`（33MB，versionCode 6）。跑 2 轮编译（第 2 轮补 AccentDelete import）。

### 第十轮：四个 bug + 静音开关挪位 → 出 1.0.6

**用户反馈**（小米手机）：截屏时提示"正在随机抽取视频"；打开收藏不能立刻显示；
收藏点开跳外部播放器；建议把静音开关挪到侧栏并改图标。

**1. 截屏被当成视频（多处）**
- 直接原因：1.0.3 加 SCREENSHOT 时，好几处写的是 `if (kind == PHOTO) A else B` 的三元式，
  截屏落到 else（=视频）分支。
- 用 grep 全量排查 `== MediaKind.PHOTO` / `kind == MediaKind.VIDEO`，找到 4 处，全改成 `kind.isImage`：
  1. `SessionLoadingOverlay` 文案 → "正在随机抽取视频" ← 用户报的
  2. **`startSession` 的权限判断：截屏走的是 videoAllowed** ← 真 bug，
     只给图片权限的设备上点「整理截屏」会去申请视频权限
  3. 分享截屏的 MIME 给成 `video/*`
  4. 回收站列表把截屏标成"视频"
- **教训：新增枚举值时，必须 grep 一遍所有用 `== 旧值` 写死的二元分支。**

**2. 收藏打开慢 / 显示不出来**
- 根因：`favoriteItems()` = `allImages() + all(VIDEO)` → **全量扫描媒体库**再过滤。
  用户有 8544 条视频，扫完要好几秒，页面看起来就是空的。
- 修法：新增 `MediaRepository.byKeys(keys)`，用 `_ID IN (?,?,...)` 精确定位。
  storeKey 最低位编码了"是不是视频"，拆成 imageIds / videoIds 分别查两张表。
  **按 500 一批分块**（SQLite 旧版 `SQLITE_MAX_VARIABLE_NUMBER` 只有 999）。
- 改造范围：`favoriteItems()`、`favoriteSyncDelta()`、`reconcile()` **全部改走 byKeys**，
  三处都不再需要全量扫描。
- 顺手加了加载态（CircularProgressIndicator + 文案），即使慢用户也知道在读。
- 内部重构：`runQuery` 拆出 `parseItems(cursor, collection, defaultKind)` 复用，
  新增 `runSelectionQuery`（带 selection/selectionArgs）+ 同样的两级投影兜底。

**3. 收藏页跳外部应用** → 改用应用内 `MediaPreviewOverlay`（复用回收站那套），
底部操作区注入「移出收藏」。点击=预览，长按=移出。
顺手把 `PreviewAction` 提取成公共组件 `ui/common/PreviewActionButton.kt`，回收站和收藏夹共用。

**4. 静音开关挪到右侧操作栏 + 图标化**
- **core 图标库里没有音量图标**：已用 `find` 列出 material-icons-core 的全部 45 个图标确认。
  为两个图标引入 `material-icons-extended` 会让 debug 包体明显变大，不值。
- 自绘 `ui/common/VolumeIcons.kt`：喇叭本体（矩形+锥形的 fill path）+ 两道声波 / 一个叉。
- **踩坑：`PathBuilder` 没有 `cubicTo`**（也没有 quadraticTo）。已用 javap 核对。
  改用 4 点折线近似弧线 —— 圆头圆角描边在小尺寸下本来就会把折线糊成平滑弧，效果一样。
- 顶栏去掉文字后补一个 48dp Spacer，保证页码居中。

**结果**：assembleDebug + lintDebug 全绿（0 错误 0 警告）。

### 第十一轮：返回手势 + 收藏同步诊断 + 去冗余确认 → 出 1.0.7

用户反馈（小米 HyperOS 3.0.308.0）：收藏同步仍进不了系统相册；要收藏页加删除；
清零统计误触了要更隐蔽；返回手势多处不对；退出确认太繁琐。

**1. 返回手势三个问题（都修了）**
- **整理时返回，已标记的被丢弃**：`conclude(performDelete=false)` 把 `marked` 整个扔掉，
  用户看不出来。现在 `finish()` **无条件把 marked 交给系统删除流程**。
- **预览层没接管返回** → `MediaPreviewOverlay` 加 `BackHandler`。
- **非「整理」页返回直接退出应用** → `AppRoot` 加
  `BackHandler(enabled = tab != Tab.Review) { tab = Tab.Review }`。
  **关键：它必须声明在会话/预览之前** —— Compose 的 BackHandler 是后注册者优先，
  这样会话页和预览层的处理自然盖住它，层级才对。

**2. 删掉退出确认**
用户明确说多余。整个 `BatchReviewSheet.kt` 删掉了（连目录）。
理由：系统删除弹窗本身就是确认，中间那层是重复确认同一件事。
顺带把「退出即提交 marked」和「去掉确认」这两个需求合并成同一个改动 —— 否则
"不确认"+"标记丢弃"会导致用户标记的东西被无声吞掉。

**3. 收藏同步：小米不认 IS_FAVORITE（重点）**
- 检索确认：`createFavoriteRequest` 写的是 AOSP 标准的 `MediaStore.IS_FAVORITE`，

- **但更要紧的是：原来的代码根本没法证明是哪一步失败** ——

- 任何一步抛异常都在 `startFavoriteSync` 里 `onFailure` 出提示，不再静默。

**4. 收藏页预览加「删除」**：和「移出收藏」并排，走同一套系统删除流程 + launcher。

**5. 清零统计改隐蔽**：移到整页最底部、降到 `labelMedium`/`labelSmall` 层级、

**原则：入口越不起眼，越要保证"点到"≠"执行"。**

### 第十二轮：开组速度 + 滑动行程 + 精简确认 → 出 1.0.8

用户反馈：抽取随机照片/截屏要等很久，视频很快；左右滑行程偏长；移入回收站还要二次确认。

**1. 开组慢（根因很明确）**
`SessionRepository.buildSession` 里写死了：
```kotlin
val all = repo.all(kind, forceReload = true)   // ← 每次开组重扫整张表
```
**照片慢而视频快的原因**：照片数量本来多（视频 8544），且图片那条路径
每行还要跑 `looksLikeScreenshot`（字符串拼接 + lowercase + 7 次匹配）。

三处一起改：
- `buildSession` 改 `forceReload = false`（应用启动时 AppRoot 已经在后台把缓存 load 好了）
- `AppRoot.conclude` 的 `invalidate()` 换成 `dropFromCache(result.markedDelete)` **增量摘除**
  ← 这是关键：不然每次会话结束都会把缓存整个丢掉，下一次开组又变慢
- 新增 5 分钟 TTL（`SystemClock.elapsedRealtime()`，单调时钟不怕改时间）
- `TrashScreen.reload()` 里的 `invalidate()` 删掉 —— `trashed()` 本来就不走缓存，
  那里 invalidate 纯属把主缓存误伤
- `TrashScreen.fire()` 加 `dropped` / `restore` 参数：删除走 dropFromCache，恢复才 invalidate
- `looksLikeScreenshot` 去掉逐行 `lowercase()`，改一次拼接 + `contains(ignoreCase=true)`

**2. 左右滑行程 110dp → 72dp**（`hLimitPx`）。垂直的 140dp 没动（用户只说左右）。

**3. 精简确认**
- 删掉 `TrashScreen` 的「清空回收站」AlertDialog。系统删除弹窗已经是确认，
  两道确认同一件事。原有信息（可释放空间 / 2000 项上限提示）挪到按钮副标题。
- **用户问的"移入回收站为什么还要确认"——那个框是 Android 系统的，删不掉。**
  Android 11 起规定：删除非本应用创建的媒体必须先经 `createTrashRequest` 拿用户授权，
  系统弹窗就是授权流程本身。已写进 README 讲清楚。
- 现在三条删除路径（滑走标记后退出 / 清空回收站 / 收藏页删除）都只剩系统那一个弹窗。

**结果**：assembleDebug + lintDebug 全绿（0 错误 0 警告）。
`qushe-v1.0.8-debug.apk`（33MB，versionCode 9）。一次编译通过。

**通用教训（多次踩到，值得记住）**
**"为了保险而每次强制重新加载"是性能杀手。** 正确做法是：
缓存 + 精确的增量失效（知道删了什么就只摘什么）+ 一个时间兜底窗口。
`forceReload = true` 这种写法在数据量大 10 倍的表上代价会放大 10 倍，
而它换来的那点"新鲜度"通常根本不需要。

### 第十三轮：后台暂停 / 音量联动 / 信息补全 / 看完自动退出 → 出 1.0.9

**3. 调整系统音量就解除静音**
- **第一版做错了**：用 `MainActivity.dispatchKeyEvent` 拦音量键。
  **Lint 直接报 3 个 `RestrictedApi` 错误** —— `ComponentActivity.dispatchKeyEvent`
  是 AndroidX 的受限 API，不允许外部库覆写/调用 super。
- **改成的方案**：不拦按键，**直接观察系统音量**：
  ```kotlin
  LaunchedEffect(muted) {
      if (!muted) return@LaunchedEffect
      val audio = context.getSystemService(Context.AUDIO_SERVICE) as? AudioManager
      val baseline = audio.getStreamVolume(AudioManager.STREAM_MUSIC)
      while (true) {
          delay(500L)
          if (audio.getStreamVolume(AudioManager.STREAM_MUSIC) != baseline) { muted = false; break }
      }
  }
  ```
  好处：① 音量面板的滑块也能捕捉到（拦按键不行）② 不碰受限 API
  ③ 只在静音时轮询，解除后循环立即退出。
  同时删掉了 `SystemVolumeSignal.kt` 和 MainActivity 里的覆写。
