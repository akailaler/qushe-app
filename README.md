# 取舍 (Qushe)

对标 iOS「去留 linger」的 Android 实现。像刷短视频一样刷自己的相册：随机抽一组内容，  
顺手删掉废片、收藏想留的，过程中不断看到尘封的记忆。

照片用**卡片堆叠 + 上滑删除 / 下滑收藏**，视频用**抖音式上下滑 + 长按倍速 / 双击收藏**。

## 一、怎么跑起来

### 环境要求

| 项              | 版本                     |
| -------------- | ---------------------- |
| Android Studio | Ladybug 或更新            |
| JDK            | 17                     |
| Android SDK    | compileSdk 35          |
| AGP / Gradle   | 8.6.1 / 8.9            |
| Kotlin         | 2.0.21                 |
| 最低运行版本         | **Android 11（API 30）** |

`minSdk = 30` 是刻意选择，不是偷懒：系统回收站（`MediaStore.createTrashRequest`）和  
受控删除（`createDeleteRequest`）都是 API 30 起才有。低于 30 就必须申请  
`WRITE_EXTERNAL_STORAGE` 直接操作文件，是完全另一套代码路径，且安全性更差。  
「回留」同样只支持 Android 11+。

### 更新日志

**1.3.64**（收藏同步的副作用修掉 + 设置页手动同步 + 回顾计数拆成照片/视频）

1. **"收藏夹没有同步到系统"—— 找到根因：代码会偷偷关掉用户的同步开关**。
   `addSyncer` 回调里原本有一句 `autoSyncFavorites = false`：
   只要那次核对没读到任何 `IS_FAVORITE`，就**在用户不知情的情况下永久关掉同步**，
   提示语只说"这台设备的相册可能不使用它"。之后收藏再也不往系统写 ——
   用户看到的现象就是"收藏夹似乎没有同步到系统"。
   这和 1.3.52 删掉「上滑删除」那条设置是同一个病根：
   **替用户做决定 + 不告诉他**。现在只如实报事实，
   要不要继续由用户自己在开关里决定。
   同时设置页新增「**立即同步收藏到系统相册**」，走的是和自动同步**同一条链路**
   （`startFavoriteSync`），只是由用户点一下触发。
2. **回顾计数拆成照片 / 视频两格**（首页与设置页同步）。
   之前只有一个总数，看不出"刷了多少照片、多少视频" —— 而这两个是完全不同的习惯。
   新计数从这版开始累积，历史数据仍归在照片那栏（截屏也算照片）。

**1.3.63**（回收站按钮文案 + 换页等待缩短 + 手势起点修正）

1. **回收站预览里的按钮**：「恢复到相册」→ **「恢复」**（「彻底删除」保持不变）。
2. **"滑一张要等一下才能滑下一张"—— 等待就等于换页动画的时长**。
   `onDecision` 是在出场动画**跑完之后**才换 `index` 的（换早了照片会瞬移回正中），
   所以 `settleToPage` 用 `StiffnessMediumLow` 走完一整屏要 400~600ms
   —— 单次滑动感觉不出来，连续滑动就暴露了。
   改成 `StiffnessMedium` + `visibilityThreshold = 24px`：速度依然连续（还是弹簧），
   等待缩到 ~300ms。
3. **顺手修一个真 bug**：新一次手势的本地累加值原来从 **0** 起步，
   而此时上一段翻页动画可能还没停、`offsetX.value` 已经 -800 ——
   第一次 `snapTo(0 + 10)` 会把照片从 -800 **瞬间拽回 -10**（观感是"跳了一下"）。
   现在本地变量以 `offsetX.value / offsetY.value` 为基准，新手势从"照片现在在哪"接着走。

**这三处都不碰删除、返回那天、双击、放大等任何其它路径。**

**1.3.62**（长图照收藏页放开上限 + 三态循环修正 + 单击交回双击判定）

1. **长图还是拖不动 —— 根因是 `contentRatio` 把上限算成了"宽度铺满"**。
   传了 `contentRatio` ⇒ `snapScale = 容器 / Fit后绘制区`；长图 Fit 之后宽高都贴着
   容器，`cover` 只取到 1~1.25 ⇒ **上限只有一两倍**。而上限正好等于"宽度铺满"时，
   横向 `panLimit` 恰好是 0、纵向余量也只有几百像素 ⇒ 看起来就是"被锁死"
   （用户反馈"连左右拖动都不行了"）。**收藏页能拖是因为它不传 `contentRatio`。**
   现在长图也不传：上限回到 `maxScale`，边界用收藏页那套宽松估计。
   代价是可能拖出一丁点黑边 —— 那比"看不了细节"好得多。
2. **三态循环不完整**：原来拿 `filmstripVisible` 当前值当指针，而状态①和③
   在这个变量上**取值相同**（胶片栏都是收的），于是"③ 之后点一下"算成去②、
   回不到①（用户反馈"只在 2 和 3 之间切换"）。改成自己记一个 `chromeStage`。
3. **单击交回双击判定**：单击改挂 `ZoomableImage.onSingleTap` ——
   `detectTapsWithoutConsuming` 内置"延后 280ms 等第二击、双击时取消单击"。
   之前放在 `DraggablePhoto` 的"没拖过"分支里虽然"松手当帧"响应，
   但**每次双击都会先切一次 chrome 再切回来**（净效果为零，视觉上仍抖一下）。
   这正是用户要的模型：单击后先等 280ms，确认没有第二击才执行。

**1.3.61**（顶栏计数真正居中 + 长图放大上限不再被锁死）

1. **长图放大后还是不能看 —— 上一版只修对了一半**。
   1.3.60 修的是"父节点抢手势"（事件确实让出去了），但**放大上限本身是 1x**：
   `snapScale` 按 `cover = 容器 / Fit后绘制区` 算，而长图 Fit 之后
   **宽正好等于容器宽、高正好等于容器高** ⇒ `coverW = coverH = 1` ⇒ 上限 1x
   ⇒ 捏合被 `coerceIn(1, 1)` 夹住，**根本放不大**，也就永远进不了拖动分支。
   收藏页能拖是因为它**不传** `contentRatio` ⇒ 走的是 `maxScale`。
   现在补上兜底：`cover < 1.02`（1x 就已铺满）时回落到 `maxScale`。
   —— "吸边界"的本意是"别放大到看不清"，而长图放大到 2~3x 恰恰是看细节**需要的**。
2. **顶栏计数偏右**：原来左右各一个 `weight(1f)`，那只保证"扣掉两侧内容后的剩余
   空间"居中；左边关闭按钮 48dp、右边标记宽度随数字变（25~32dp），
   两边不等宽 ⇒ 计数必然偏右。现在左右两格都用**固定 56dp**，计数独占中间。
   右侧有没有标记都不再影响居中。

**1.3.60**（长图真的能拖了 + chrome 与胶片栏同进同退 + 角标去框）

1. **上一版"放大态放行"其实从没执行过**：`DraggablePhoto` 的

   `onTap` 同理。两者都改走 `rememberUpdatedState` 转发。

3. 回收站角标**去掉底色块**，只留文字；可读性靠文字自身的描边阴影。

**1.3.57**（回收站格子显示「还剩 xx 天」）

30 天保留是**系统定的**（MediaStore 回收站），应用侧拿不到"删除时刻"，
只有 `MediaStore.MediaColumns.DATE_EXPIRES` 这个"到期时刻"（API 30+），
所以显示的是**剩余**而不是"删于"。剩三天以内换成警示色，当天到期写「今天到期」。

这一列**只在回收站那次查询里投影**（`queryCollection` 加了 `extraProjection`）——
`projectionFor` 那条路上再加，等于让全工程每个查询都去冒"某厂商 MediaProvider
不认识这一列"的风险（`XMP` 那次就是这么炸的）。

**1.3.56**（撤回 pager 预组合 + 修侧边返回手势）

1. **撤回上一版的 `beyondViewportPageCount = 1`**。它确实能减轻"滑过去那一帧"的
   组合压力，但代价更大：启动时**同时**组合三页（喜欢 + 首页 + 收藏），
   其中两页都是缩略图网格、各自还要查一次 MediaStore ——
   后台一直在解码/查询，正要画的那一帧就得和它们抢资源。
   症状是"从喜欢页往右滑到首页"比以前更卡（用户反馈）。
   真正的解法是**把那几页本身做轻**（设置页已改成 LazyColumn），
   而不是靠多养一页来抢帧。剩下的网格页首屏成本需要录屏逐帧量才知道值不值得再动。
2. **侧边返回手势：底部导航栏回首页了，但上面的内容没回** ——
   原来写的是 `BackHandler { tab = Tab.Review }`：底栏读 `tab` 所以选中态立刻变了，
   而 **pager 根本没动**。现在改走 `goToTab(Tab.Review)`（`tab` + `scrollToPage` 一起做）。
   判据也从 `tab` 改成看 **pager 当前页**：停在「喜欢」那一页时 `tab` 本来就是 Review，
   用 `tab` 判断会让返回手势直接失效（应该回首页，而不是退出应用）。

**1.3.55**（首页左右滑卡顿优化）

1. **`HorizontalPager` 加 `beyondViewportPageCount = 1`：提前把相邻页组合好**。
   默认只组合当前页，于是"从首页滑向收藏页"这一下，收藏页的网格、
   设置页那一长列都要在**手势进行中**现组合 + 现测量 —— 掉帧就在这里。
   改成 1 之后这些成本挪到"你还没开始滑"的时候，滑动过程里只做绘制位移。
   5 页的规模，多组合一页的内存代价可以忽略。
2. **设置页从 `Column + verticalScroll` 改成 `LazyColumn`**。
   `verticalScroll` 的 Column 会**一次性组合全部内容**，这一页有二十几块设置项，
   是最重的一页。改成 `LazyColumn` 后只组合可见的那些。
   主体按"整理方式 / 删除 / 视频播放 + 位置 / 收藏 + 统计"切成 4 块 `item` ——
   不是每个设置项一个 item（item 太多、每个都太矮），也不是整页一个 item
   （那就等于没改）。

**1.3.54**（大图 chrome：单击能来回切 + 放大时即时隐藏）

1. **"单击之后 chrome 都隐藏了，再单击没回来"—— 是我上一版引入的**。
   上一版把 `onZoomedChange` 改成无条件 `chromeVisible = !isZoomed`，
   而 `ZoomableImage` **每次手势结束都会报一次**。于是 1x 下单击时：
   `clickable` 先把 chrome 切掉 → 紧接着这次回报又把它写成"显示" →
   下一次单击再切掉、再被写回显示 ⇒ **净效果就是"只收不回来"**。
   现在只在**状态真的跨过 1.01** 时才动 chrome，两条路各管各的：
   单击归 `clickable` 切显隐，放大/缩回归 `onZoomedChange` 收起/显示。
2. **放大时 chrome 改成"放大的同时就隐藏"**：`ZoomableImage` 原来只在
   手势结束时报缩放变化，于是"放大时收起 chrome"会晚一整段时间 ——
   图都铺满了、chrome 还杵在上面。现在在**越过 1.01 那一帧**就报出去
   （只在跨越时报，调用方不必自己去重）。整理照片页那边同步受益
   （它的 `chromeHidden = isZoomed` 本来就是这个语义）。

**1.3.53**（删除动线与整理页逐字一致 + 修大图 chrome 不稳定）

1. **「上滑之后没有正常消失、经常残留红色底」= 我在调用方多此一举地过滤了列表**。
   `DayViewScreen` 自己就有一套删除动线：`markedKeys` → `removedFlags` →
   `CellSlot` 把宽度收到 0 ⇒ 格子飞出去、同排左移补位（整理照片页一直走这条）。
   我在 `FavoritesScreen` 里又用 `filterNot { in dayMarked }` 把项从 `items` 里剔了一遍，
   等于**换成了另一套删除机制**：整排会重新布局，偶发留下收不干净的红底。
   现在改成和整理页**逐字一致**的用法：`items = dayItems`，`markedKeys = dayMarked`。
2. **大图里顶部/底部的图标和小字不稳定 —— 单击被切了两次**。
   外层 `Box.clickable` 切一次，`ZoomableImage.onSingleTap` 在双击判定窗口（280ms）结束后
   又切一次 ⇒ **净效果为零**，观感就是"按了没反应"。
   现在 `onSingleTap` 不再传，单击切 chrome 只由外层 `clickable` 一条路负责；
   双击只触发"喜欢"，不会连带把 chrome 切两次。
3. **放大 / 缩回的 chrome 规则改成可预期**：
   - 放大 ⇒ 收起
   - 缩回 1x ⇒ **强制显示**（不是 toggle —— 否则"放大前收起过"的用户缩回来还是收着的）
   - 单击 ⇒ 切换显隐

**1.3.46**（圆角改成盖遮罩 + 严格轴锁滑动 + 下滑不再顿 + 系统收藏反向导入）

1. **圆角回来：这次用"在图上盖四角遮罩"的画法**。1.3.44/45 两次失败都是因为
   为了裁到图片四角，把变换层 `aspectRatio` 缩小了 —— 而那个盒子一变小，
   **整条链的尺寸基准就跟着变**，用户看到"图片会自动放大"。
   现在完全不动布局：在所有图**之上**、变换层**之内**画四条路径
   （每条 = 角上的方块减去一个四分之一圆），填页面底色。
   排在变换层内 ⇒ 跟着照片一起缩放平移，圆角始终长在图片四角上。
   只画四个角、不画"图片以外整片" ⇒ 上下黑边留透明，翻页时不会挡住
   底下正在淡入的下一张。圆角半径继续用 `rememberContentCorner()`，和瀑布流一致。
2. **整理照片页的滑动改成严格水平或垂直**。原来两个轴同时动，斜着划会走成斜线，
   还会同时命中"翻页"和"删除"两个判定。现在越过 touchSlop 的那一刻按主方向
   **把轴定死**，整串手势只能往那一个方向走，另一轴恒为 0。
   判定也随之简化成"只看那一个轴"。用户问是不是更简单更节约资源 ——
   **是**：位移向量恒有一个分量为 0，边界/回弹/提示都退化成单轴，
   少一次比大小猜方向，也不会出现两个动作同时触发。
3. **下滑退出"拖一点点就顿住"**：根因是 `snapTo(currentValue + delta)` ——
   读的是挂起写出来的当前值，而每帧都要 `launch` 一次；后一次把前一次取消掉时，
   **那一段增量就丢了**。改成在手势内用本地变量累加、每次 `snapTo` 写**绝对值**，
   丢不掉。整理页的拖拽有同样的隐患，一起改了。
4. **设置页新增「同步系统收藏到这里」**（反向导入）。查 `IS_FAVORITE = 1`
   把系统相册里已收藏的内容收进本应用的「收藏」。**只加不删** ——
   系统里没有的不代表用户不想留。导入的同时标记成"已同步"，
   否则"待同步"会一直提示用户把这些再写一遍系统。
   空结果会明确说清两种可能（这台设备的相册不用这一列 / 本来就一个都没标），
   不让用户猜。

**1.3.45**（下滑返回的动画拆层 + 整理页滑动改成 pager 手感 + 撤掉失败的圆角）

1. **下滑返回不丝滑的真正原因：淡出和位移绑在同一层**。
   退场时 `dismissY` 一路涨到 `屏高 × 1.15`，而 alpha 是按
   `dismissY / 阈值` 算的 ⇒ 照片在动画前 20% 就淡没了，
   剩下那一百多毫秒屏幕上什么都没有，观感就是"啪一下消失然后卡一下"。
   现在拆成三层，各管一件事（顺序 = 绘制顺序）：
   ① 黑色底只淡出 → ② 照片只位移+缩小、**全程可见**地飞出去 → ③ chrome 只淡出。
   （chrome 必须排在照片**之后**，否则返回键和底部胶囊会被整屏照片盖住、点不到。）
   收尾动画也换成和整理页「上滑删除」**完全同一套**：
   `flingTo`（tween 200ms + FastOutLinearInEasing）出场、
   `spring(StiffnessMediumLow)` 回弹 —— 之前用的是默认 spring，更硬、手感发木。
2. **整理照片页的滑动改成回收站那种"完全按照轨迹"**。回收站那边的预览走
   `HorizontalPager`，而 pager 从不转图 —— 手指往哪走画面就严格平移到哪。
   原来这里横移时照片会跟着歪最多 8°，用户说的"随心所欲的自由滑动"就是它，已去掉。
   另外翻页判定加上**速度线**（1100px/s）：位移过阈值**或**甩得够快都算成立，
   熟练之后的快速一甩不再被弹回去。纯速度判定会让斜向上滑删除被误判成翻页，
   所以横速那条额外要求"确实往一个方向走过一点"。
3. **圆角撤掉**。1.3.44 那版要让圆角落在图片四角上，就得先把变换层缩到
   图片 Fit 之后的真实矩形（`aspectRatio`）—— 而这个盒子一变小，
   整条链的尺寸基准就跟着变了，用户反馈"图片会自动放大"。
   为一个装饰效果去动布局基准不划算，这版回到 1.3.42 的行为（无圆角）。
   真要做的话得换成"在图上盖四个角遮罩"的画法，完全不碰布局和缩放。

**1.3.44**（下滑返回修好 + 四处显示问题）

1. **下滑返回"触发不了"——根因是只判距离、不判速度**。
   快速一甩时手指在屏幕上其实没走多远就松手了，`dismissY >= 阈值` 判不出来，
   于是每次都弹回去。现在改成**距离够 _或_ 甩得够快**（1200px/s，用
   `VelocityTracker` 量）—— 滑动类手势的通行判据，本来就不该只看其中一个。
   顺带修掉两个隐患：`pointerInput(Unit)` 只在首次组合捕获闭包，
   `var zoomed` 在里面永远读到 false（改成 `rememberUpdatedState` 转发）；
   阈值也是首帧那次算的（此时容器高度还是 0），改成键里带 `boxHeightPx`。
   距离阈值也从 140dp 放宽到 120dp。
2. **瀑布流放大后底部的小字从"照片"改成文件夹**。
   "照片"在放大看单张时没有信息量（用户已经知道自己在看照片），
   "在哪个相册里"才是他不展开 `i` 就想知道的。取不到 bucket 才退回类型标签。
3. **修掉"第一张下面露出第二张的图片"**。
   顶层照片是 `ContentScale.Fit` 画的，竖图在长屏上上下留出很宽的黑边，
   而垫在下面那张是常驻的全屏图 ⇒ 黑边里一直能看到下一张。
   现在它**按拖动/收走的进度淡入**：静止时不可见，手一动就出来，
   不动就淡回去 —— 防翻页闪黑的那层底牌保留，但不再自己露脸。
   （原来还画了 `index + 2` 那张，它和 `index + 1` 位置尺寸完全一致、
   被后者整张盖住，永远看不见，白白多解一张图，一并删掉。）
4. **整理照片页的圆角一直没生效** —— 不是忘了加，是**加错了地方**。
   圆角原本裁在整屏盒子（变换层 `fillMaxSize`）上，而主图是 Fit 画在里面的：
   竖图上下那些黑边被裁、照片自己的四角根本不在裁剪区边上 ⇒ 用户看到的就是"没圆角"。
   现在给 `ZoomableImage` 加了 `clipAspect`，把变换层缩到
   **Fit 之后的真实矩形**（`aspectRatio(matchHeightConstraintsFirst = true)`
   正好是 Fit 的算法），圆角才落在图片四角上。
   这个参数**刻意和 `contentRatio` 分开**：后者还管缩放上限、拖动边界、
   放大时的解码尺寸，推广到所有照片会连带改掉那三件事的行为。

**1.3.43**（捏合进「回到那天」的跳变修复 + 放大后下滑返回瀑布流）

1. **修掉捏合进入那一刻的跳变**（用户报了四轮，前几版都修错了地方）。
   整屏淡入以前是**一进页面就开跑**（560ms），而飞入动效要等
   ① 那一天的内容读出来、② 焦点格的位置稳定 —— 两条动画错位 100~400ms。

   然后才突然冒出来开始飞。
   现在反过来：**淡入等"焦点格能飞"才启动**。等待期间这一层 alpha 恒为 0，
   底下整理页那张照片原样留在原地，转圈根本不会被看到 ——
   空档被藏在了透明里，而不是塞东西去填它。另配 1.2s 保险丝，
   万一回调没来也不会让界面永久停在透明。
2. **瀑布流里放大看单张之后，往下一划就能回到瀑布流**（iOS 相册 / 「去留」的手势）。
   照片跟着手指往下走、稍微缩小，整层一起渐隐；越阈松手就飞出去关掉这一屏，
   没越阈弹回原位。**只在 1x 时认领** —— 放大后竖直拖动是 `ZoomableImage`
   在看局部（事件已经被它消费掉了），而且放大状态下随便划一下就退出，
   等于把"仔细看"和"退出"混在一起。

**1.3.42**（照片页：去掉黑底，只留图片本身带圆角）

1. **修正 1.3.41 的理解偏差**。上一版做成了"给那片黑底加圆角"，
   而用户要的是"**去掉黑底**、图片本身带圆角"——
   黑底留着的话，照片平移时仍然会带着一整块方方正正的暗色一起走
   （圆角只裁得住"这一层里画的东西"，那片底在视觉上还是独立的一块）。
   现在 `ZoomableImage` 那一层是**完全透明**的：图之外什么都不画，
   露出来的是页面自己的黑底（`MediaPreviewOverlay` 根容器上的 `background`），
   它**不跟着照片动**。

**1.3.41**（照片加圆角 + 提示跟着一起淡出）

1. **整理照片页的单张大图加了圆角，和瀑布流共用同一套算法**。
   原来它是**方角**的，左右滑的时候观感是"一整块方图连着它那片黑底一起平移"，
   很硬（用户要求"就像瀑布流里的那样"）。
   圆角抽成了 `ui/common/Shapes.kt` 的 `rememberContentCorner()`
   ——两处本来就该看起来是同一个东西，各写一份迟早漂移。

   顺带修了一个**同一处的隐藏问题**：`background(Ink)` 原来画在
   **圆角外面**（外层 Box 上），圆角裁不到它 ——
   所以就算加了圆角，外面还是会留一圈**方角黑底**跟着照片动。
   现在黑底挪到圆角**之内**（内层、clip 之后）。

   圆角也和缩放/位移一样提到了"包住全部四层"的那一层 ——
   它得同时裁住四层垫底图，只裁主图的话垫底层会从圆角外露出来。

2. **捏合提示跟着 chrome 一起淡出**（用户观察："胶囊被飞行的图片盖住了"）。
   进入「回到那天」后 `pinchToDateProgress` 不再更新、一直停在 1，
   那颗"继续捏合"的胶囊就**一直挂在屏幕上**，直到被日期视图完全盖住 ——
   中间飞行的焦点图会从它上面划过去。现在它跟着 `chromeAlpha` 一起淡掉。

**1.3.40**（"跳变"和"小方块"各自的根因）

1. **捏到触发阈值那一刻的"跳变"**：手势循环里 `lowerBound` 一开始是
   `PINCH_TO_DATE_MIN_SCALE`（0.72，允许照片跟着手指缩小），
   而 `pinchTriggered` 一旦翻成 true 它就变回 `1f` ——
   于是 `coerceIn(1f, …)` 在**触发的那一帧**把已经捏到 0.85 的照片
   **硬抬回 1.0**。画面就在"刚好捏够"的一瞬间猛地弹大一下。
   更糟的是飞入动效的起点是按 0.85 算的，两边还对不上。
   现在触发之后**不再碰 scale**，让它停在触发时的大小，交给飞入动效接着走。

2. **"很小的方形块"是那颗提示胶囊的空壳**。
   `DecisionOverlay` 在 `decision == NONE` 时只把文案变成空字符串 ——
   那个 `Row` 照样画出来：底色 `Surface3`、带 22×14 内边距、
   里面既没图标也没字，屏幕上就是一个**深灰色的小方块**。
   出现的时机也和用户描述吻合：
   上滑删除松手回弹、捏合松手没够，都会经过 `NONE` 这个状态；
   平时它被"删除"/"继续捏合"那颗有内容的胶囊盖着，所以"不确定什么时候出现"。
   现在 `NONE` 且不是捏合提示时**整个不画**。

**1.3.39**（"小方块"和"残留"同一个根因：变换只挂在了一层上）

1. **捏合缩放 / 长图拖动时那个"很小的方形块"和边缘"残留"，是同一个 bug**：
   `graphicsLayer { scaleX = scale; translationX = offset.x }` 原来**只挂在主图那一层**上。
   后果有两个（用户都报了）：
   - **捏合缩小时**：主图缩成中间一小块，而底下三层垫底图**没缩** ——
     四周露出一圈没缩的旧图，看起来就是"中间出现一个很小的方形块"；
   - **拖动长图时**：主图在动、垫底层不动，边缘留下没跟着走的残影 ——
     "缩放自由移动的时候会有残留"。

   现在把变换提到**包住全部四层**的那一层，四层永远同步。
   上滑删除时来回弹的那一下也会看到同样的方块 —— 同一个原因，一起没了。

**1.3.38**（长图不再是"糊图一闪" + 捏合提示至少显示一整个动效时长）

1. **长图插了一层"中间图"**。上一版已经做到了"不闪黑"，但长图还剩"糊图一闪"——
   用户这次明确说是"糊"不是"黑"，说明链路对了、只是**占位太糊**：
   系统缩略图会把整张长图压成 46×512 那种，铺到全屏等于放大二十多倍。
   现在 `ZoomableImage` 在"系统缩略图"和"高清主图"之间插一层
   **按容器尺寸解码**的图（只对长图这类 `decodeSize` 明显更大的才建），
   清楚得多、解码只要几十毫秒。层序变成：
   ① 手上的 Bitmap（零延迟）→ ② 系统缩略图（1~5ms）
   → ③ 容器尺寸的中间图（几十 ms，长图专用）→ ④ 高清主图。

2. **捏合提示"至少显示一整个动效时长"**（用户要求）。
   原来松手就跟着进度归零，而熟手一捏就到底 —— 提示来不及读。
   现在**只要捏过就一直显示，松手之后再留一整个 `DAY_INTRO_MS`（560ms）**。
   这个时长和飞入动效**共用同一个常量**（`ui/common/Motion.kt`）——
   它们本来就是同一个动作的两半，两边不一致会显得"提示还没读完人就飞走了"。

**1.3.37**（缩略图必须是"已经拿在手上的"才算数）

1. **撤掉 1.3.36 那个"上一张垫底"**。它的硬伤用户一句话点出来了：
   第二张下面是**第一张**而不是第三张，划走第二张时背景还要再变一次 —— 更突兀。
   （"旧图还在 → 新图盖上来"只在**前后是同一内容**时成立，翻页不成立。）

2. **真正的做法：缩略图要"提前读成 Bitmap 拿在手上"**。
   方向一直是对的（用低分辨率缩略图当初始画面），但前面几版都差最后一步：
   - 系统缩略图**走 Coil 请求** → 要 1~5ms IO + 一帧回调；
   - 预加载相邻页 → 要解码时间；
   - **都还是在赌"来得及"**。

   现在 `PhotoSessionScreen` 在 index 变化时，把**当前 + 前后各一张**的缩略图
   `loadThumbnail` 直接读成 `ImageBitmap` 存进一个 map；
   `ZoomableImage` 新增 `placeholderBitmap` 参数，把它画在**最底层** ——
   那是**同步绘制**，没有 IO、没有解码、没有等回调那一帧，真正的零延迟。
   高清解出来之后自己盖上去。滑远的会从缓存里丢掉，不会一直长。

   `ZoomableImage` 现在的层序（从下到上 = 从可靠到不可靠）：
   ① 拿在手上的 Bitmap（零延迟）→ ② 系统缩略图（1~5ms，首次进入用）
   → ③ 高清主图（几十~上百毫秒）。

**1.3.36**（换思路：不让画面出现空档，而不是往空档里塞东西）

1. **"闪一下黑"改了方向解决**。前几版都在做同一件事：
   往"图还没就绪"的那一两帧里塞点东西（系统缩略图、预加载相邻页）——
   但**都是在赌"来得及"**：解码只要慢一点，那一两帧照样是空的，
   而背景是纯黑，空 = 黑。
   现在换个做法：**根本不让画面出现空档** ——
   新图没就绪之前，把**上一张**继续画在最下面。它已经在内存缓存里，
   组合完第一帧就有（不需要 IO、不需要解码），比任何"提前请求"都可靠。
   新图就绪后把这里盖住，视觉上就是"旧图还在 → 新图盖上来"，
   和翻相册一个手感。上一层是同一张图的系统缩略图（首次进入、没有"上一张"时用它顶），
   最上面才是高清主图。
   ⇒ 这三层叠起来的顺序是"**兜底从可靠到不可靠**"：
   缓存里的上一张 > 1~2ms 的缩略图 > 几十上百毫秒的高清。

2. **捏合提示改成独立时长的淡入淡出**（用户要求）。
   原来 alpha 直接跟捏合进度走，而捏合是"一捏就到底"的短动作 ——
   提示刚浮现就跟着归零。现在一捏就快速显现（140ms），
   松手没够时慢慢淡出（260ms）；那段淡出是**白送**的阅读时间。

**1.3.35**（预加载相邻页 + 提示看得清 + 飞入不变形）

1. **滑到动图/超长图不再闪**：整理照片页的翻页是**自己实现**的
   （拖拽 + 换 index），**没有 pager 的"预加载相邻页"** ——
   每张都是"滑到才开始请求 + 解码"，那一两帧画面是空的，背景又是纯黑，
   看起来就是"闪一下黑"。
   现在 `ZoomableImage` 多了一个 `preloadNeighbors`：
   在 index 变化时把**前后各一张**提前请求好（只请求不显示），
   尺寸用**它自己算出来的那个**（`decodeSize ?: container`），滑过去直接命中缓存。
   动图不给 size（`ImageDecoderDecoder` 会翻成 `setTargetSize()`，
   对动画源不安全）—— 和主请求的 cache key 同样"无 size"，也对得上。

2. **"继续捏合进入「回到那天」"看得清了**（用户报"一闪而过"）。
   提示的 alpha 原来直接跟进度走，而进度一到 1 就立刻跳页 ——
   永远停在"刚开始看清就没了"。现在进度到**两成**就完全显现，
   后面八成的时间才是真正给用户看的。

3. **横屏照片飞上去不再变形**（用户报"衔接不顺畅"）。
   两头（照片页那张图 / 焦点格）的宽高比不一定严丝合缝 ——
   格子宽度有上下限，极端比例会被夹一下。分别按宽、高算两个缩放比例的话，
   飞行途中图片会被**拉变形**。现在取两个比例的**几何平均**当统一缩放，
   图全程不变形，位置仍按中心对齐。

**1.3.34**（"黑屏一下"的真正根子：背景画在了 alpha 层外面）

1. **`DayViewScreen` 的纯黑背景原来画在 `graphicsLayer { alpha }` 的\*\*外面\*\***。
   `Modifier.background` 只影响**它之后**的那截链 —— 它写在 `graphicsLayer` 前面，
   就等于画在了 alpha 层之外，**从头到尾都是不透明的**：
   进场第一帧就把底下的整理页整个盖住，`alpha = 0` 等于没设。
   把 `.background(Ink)` 移到 `graphicsLayer` **之后**，它才真正跟着淡入 ——
   底下的照片会一路透到被盖住为止。
   用户报了三轮"捏合进去黑屏一下"，根子其实在这儿
   （他那句"因为背景是黑色，所以闪一下都是黑屏"是对的）。

2. **`ZoomableImage` 垫了一层系统缩略图**。高清图解码要时间
   （超长图几十上百毫秒，动图更慢），这段时间画面是空的 —— 而背景是纯黑，
   "空"看起来就是"黑屏闪一下"。系统缩略图 1~2ms 就能拿到，
   垫住这段空档，闪的就只剩"清晰度"而不是"有没有"。
   对动图尤其关键：动图**不能给 size**（`ImageDecoderDecoder` 会翻成
   `setTargetSize()`，对动画源不安全），只能按原分辨率解，是最慢的一类；
   而缩略图是静态的，正好绕开那条路。
   （用户猜"超长图是不是因为重新解码了更高的清晰度"——对的，那正是 1.3.26
   为"放大要看清楚"引入的，现在用垫底把它造成的空档补上了。）

**1.3.33**（动图黑屏的真正根因 + 时间轴方向 + 提示加图标 + 起手再收一道）

1. **动图"黑屏一下"的真正根因**（用户问"这次和之前原因一样吗"）：
   原因**一样**，但 1.3.23 那次**没修对**。
   当时是靠 Uri 的扩展名判动图 —— 可 MediaStore 的 Uri 是
   `content://media/external/images/media/12345`，`lastPathSegment` 就是一串数字，
   `endsWith(".gif")` **永远不会成立**。也就是说"动图请求关掉 crossfade"
   这件事从来没生效过，黑屏也就一直在。
   现在由**调用方**把 `MediaItem.isAnimated` 传进来（它知道真实类型），
   三个调用点都补上了。

2. **时间轴方向**：排序改为**升序**（`DATE_TAKEN ASC`）——
   往左滑是更早、往右滑是更晚，和读日期的方向一致（用户要求）。

3. **瀑布流的上滑提示加了图标**：删除给回收站、收藏给心，
   和整理照片页那颗胶囊同一个构成（那边是"红底 + 图标 + 删除"，
   这里受格子尺寸限制做不了胶囊底，但图标不能少 ——
   一眼认出"这是删除"靠的就是它）。

4. **起手黑屏再收一道**：`photoRequestSize` 原来没和"是哪一张"绑定 ——
   换照片时 `ZoomableImage` 的容器会先归零、下一帧才填上新值，
   中间那一小段它还是**上一张**的尺寸。快速滑到某张立刻捏合，
   焦点格就会拿着上一张的尺寸去请求 ⇒ 缓存必然 miss ⇒ 又要重新解码。
   现在和 uri 一起记，对不上就退回格子尺寸（宁可慢一点，也不要撞一个必然 miss 的缓存）。

**1.3.32**（飞行途中就显示照片墙 + 按拍摄时间排序）

1. **飞行的同时就能看见照片墙**（用户要求，对齐「去留」的录屏）。
   之前给焦点格以外的格子排了"前 55% 完全透明、后 45% 才淡入"——
   那半秒画面里只有一张在飞的图，就是用户说的"还是黑屏了一下"。
   但「去留」的录屏里，飞行途中**照片墙的画框已经在屏幕上了**（只是暗），
   不是"飞完才出现"。现在删掉那段延迟，其余格子跟着整屏的淡入一起出现：
   画框先到、图片解码完自己填进来。（顺带省掉了它们每帧读动画进度的开销。）

2. **列表改为按拍摄时间排序**（用户报"标题日期一直在来回变"）。
   根因是排序用的是 `DATE_ADDED DESC` —— 那是**文件被扫描进 MediaStore 的时间**，
   老照片被复制进手机、微信里收下来的图，那个时间都跟拍摄时间对不上。
   于是同一天的图顺序和拍摄时间错乱，屏幕正中那一格的日期自然在两天之间来回跳。
   现在按 `DATE_TAKEN DESC`（拍摄时间），再挂 `DATE_ADDED` 当 tie-breaker
   （同一秒拍的多张要有稳定顺序）。

**1.3.31**（起手闪烁根治 + 日期跟着滚动走 + 图标淡入淡出 + 飞入更慢）

1. **起手那一下的闪烁根治了**。对照「去留」的录屏抽帧看，
   它的转场全程是"同一张照片、同一份像素"在连续缩放位移 —— **不换图源**。
   我们换：照片页那张按**容器尺寸**解码，焦点格按**格子尺寸**请求，
   Coil 的 memory cache key 对不上 ⇒ 必然 miss ⇒ 重新解码。
   上一版垫的系统缩略图正是闪烁来源（高清 → 512px 糊图 → 高清）。
   现在 `ZoomableImage` 把**实际用的解码尺寸**回调出来，一路传给日期视图的焦点格
   ⇒ 同 uri + 同 size ⇒ **缓存直接命中** ⇒ 第一帧就是同一张高清图。

2. **日期跟着滚动走**（用户要求）。删掉了"· 前后各一天"那句静态说明 ——
   范围带着前后各一天，写死在标题里反而容易和眼前的画面对不上。
   现在按屏幕**正中那一格**算日期（二分查 `cumPx`），滑到前一天/后一天时日期自己就变。
   只在算出来的日期真的变了才写 state，不会每帧重组。

3. **照片页的图标改成淡出**（用户要求："消失的图标做淡出、新出现的做淡入"）。
   顶栏、底栏、照片上的类型角标原来都是 `if (!chromeHidden)` 的瞬间消失，
   现在常驻组合、alpha 淡出（260ms）；日期视图那一侧本来就跟着整屏淡入。
   顺带把"放大看局部"也变成淡出 —— 同一个开关，没必要两种手感。

4. **飞入动效放慢**：380ms → **560ms**（用户要求"弄久一点"）。

**1.3.30**（回到那天扩到三天 + 按钮文字恒定 + 收藏页删除改为退出时结算）

1. **「回到那天」现在是三天**（用户要求）：焦点图那天 + 前后各一天。
   只看一天的话一晃就滑到头了（一天往往就十几张），而"那天"的记忆本来就是
   连着的——头天晚上拍的、第二天早上拍的，在人的印象里属于同一件事。
   标题缀上"· 前后各一天"，免得用户奇怪"怎么还有昨天的照片"。
   实现是 `allImagesOnDay(day, dayRadius = 1)`，默认 0 时行为完全不变。

2. **rail 上的按钮文字恒定，状态只交给图标**（用户要求）。
   上一版把"已标记"改成了"取消删除"——用户否定：**颜色变了就够了**。
   现在 `删除` / `收藏` / `喜欢` 三个字都不随状态变
   （原来会变成 `已标记` / `已收藏` / `已喜欢`），状态一律由图标颜色表达。
   一列按钮里只有某一颗在变字，反而更乱。

3. **收藏页 / 喜欢页的删除改为"退出浏览时统一结算"**（用户要求）。
   喜欢和收藏是可逆的，当场生效没问题；删除不是——它会弹系统窗、
   真的动到相册里的文件，而浏览时一张张点过去很容易手滑点中旁边那颗。
   现在浏览期间只记在 `pendingDelete` 里（图标变红表示待删、再点一下取消），
   **退出浏览时才一次提交**：弹一次系统窗、一次确认，既不容易误删，也少几次打断。
   `delete()` 相应改成收 `List`，批量走同一个弹窗。

**1.3.29**（飞入起点按捏合大小算 + 视频页删除可撤销 + 瀑布流滑动提示重做）

1. **修掉飞入"起手到飞行之间"那一下跳变**（用户报）。
   起点原本按照片**1x 时**的矩形算 —— 可捏合触发的那一刻，照片已经被捏小了
   （`scale` 在 0.7~1 之间）。焦点格于是先按 1x 的大小出现，再"啪"地缩到
   画面里那张的大小。现在 `onPinchToDate` 把**触发时的缩放**一起带出来，
   起点按它围绕中心缩一下，和画面上那张严丝合缝。

2. **整理视频页的删除可以撤销了**（用户要求）。
   原来只进不出：按一下变红、标上"已标记"，想反悔却没有出口。
   而这里的标记本来就只是记账（退出时才走系统弹窗），中间完全来得及反悔 ——
   现在同一个按钮按第二下就撤销。文字也跟着改成按下去会做的事：
   `已标记` → **`取消删除`**（原来那个写的是状态不是动作，
   而且按下去的结果正好相反）。

3. **瀑布流的上滑提示重做**（用户报"意思不对、设计也不对"）。
   - **文案**：去掉"松手"两个字。实际行为是"滑够就删"，没有"松手"这一步，
     那句话是在描述一个不存在的动作。现在就是 `删除` / `收藏` / `取消收藏`。
   - **位置**：从格子正中挪到**画框内偏下**——手指正在往上滑，
     提示落在下缘才不会被指尖压住。
   - **字号**：`labelMedium` → `titleMedium` + Bold。
     原来那个字号在一格缩略图上几乎读不出来，对齐整理照片页那颗胶囊的醒目程度。
   - 顺带：焦点格**开了淡入**（`crossfade`）。它垫着系统缩略图，
     缩略图切高清是"从糊到清"——硬切会像闪了一下，淡入过去就自然了。
     其余格子仍然关着（46dp 的缩略图上淡入本就看不出来，纯付开销）。

**1.3.28**（捏合更容易触发 + 飞入不再黑屏、衔接更连贯）

1. **捏合进入「回到那天」不再"要试好几次"**（用户报）。
   触发量原来是**逐帧累加** `(1 - zoom)`，往外张的帧再扣回去。
   问题是真实手势根本不单调：手指落下、调整姿势的过程里有一堆往外张的帧，
   它们把攒起来的量一次次扣掉，于是"明明捏了半天却没反应"。
   现在改成拿**两指间距**和起手间距比 —— 这是个**单调量**，中间怎么抖都不影响。
   阈值也顺势从 12% 降到 10%（那个数本来就是在"会被扣分"的算法下调出来的，
   换成间距基准后 10% 就是实打实的 10%：两指从 500px 收到 450px 就到了）。
   起手判定也从 `scale <= 1.001f` 放宽到 `1.01f`，和别处"是否放大"的判定对齐 ——
   浮点残留不该让整串手势作废。

2. **飞入不再"黑屏一下"**。两个原因叠在一起：
   - 日期视图那一层原来是**瞬间完全不透明**的（有飞入时直接给 `alpha = 1`），
     一点下去整屏"啪"地全黑。现在改成**从透明淡入**，底下那张照片会一路
     透到被盖住为止 —— 起点处两张图本来就重合，看起来就是同一张。
     （顺带：有飞入时只淡入、**不缩放不位移**，否则两层变换叠加，
     焦点格的起点位置和大小都会算不准。）
   - 焦点格的高清图要几十毫秒才解出来，而飞入第一帧就开始了 —— 这段时间
     格子里是空的。现在给焦点格垫一张**系统缩略图**（相册早就生成好的，
     1~2ms 就能拿到），高清到了 Coil 自己淡入，交接是平滑的。
     只给焦点格垫 —— 其余格子是在动画后半段淡入的，那点解码时间被动画盖住了。

**1.3.27**（真正修好焦点定位 + 「回到那天」飞入动效 + 胶片条长图角标 + 操作栏左右选择）

1. **焦点定位偏左偏右的**真正原因**找到了**（前两版都没修对）。
   两排共用同一个 `ScrollState`，而**两排都在做进场定位、互相覆盖** ——
   最后停在哪完全取决于谁的 effect 后跑，于是"有时候偏左、有时候偏右"。
   下排在 `DayFilmstrip` 调用处一直传着 `focusItem` + `ownsFocus = true`
   （注释里写的是"下排传 null"，代码没这么做），而 `seededTarget` 里还留着一个
   「焦点图不在本排就按 `focusIndex / 2` 折算一个对应格」的 else 分支 ——
   那是旧版 `index % 2` 交错分排时代的遗留，分排改成按宽度贪心均衡之后，
   折出来的根本不是对应的那一张，只是碰巧落在下标范围内。
   现在：下排传 `null` + `ownsFocus = false`，`seededTarget` 只认本排的焦点格。
   另外进场定位也从"推一次"改成**每帧检查、没对上就再推**（上限 20 帧）——
   不再依赖 `maxValue` 什么时候就绪。

2. **「回到那天」的飞入动效**（用户要求，参照上滑删除那条动线）。
   做法刻意**不是**"另画一张会飞的图"：那要再解一次码，解码一慢于动画，
   就会看到"格子已经到位、飞行图才刚出现"的错位。
   这里是让**焦点格自己**从照片页那张图的位置和大小开始，一路插值回自己的位置 ——
   全流程一份图、一次解码，交接是天然的。
   起点由整理照片页给出（它知道那张图 1x 时占多大，用 `ContentScale.Fit` 算），
   终点是焦点格自己上报的布局矩形，两个都用窗口坐标。
   其余格子在动画前 55% 完全透明、后 45% 淡入 —— 就是"飞过去成为焦点图，
   然后加载两边的图"。有飞入时**不再叠加**原来那套整屏缩放（两层变换会打架）。

3. **胶片条也有了长图角标**（用户要求）：`长`。顺带把截屏的 `截` 也补上，
   优先级和瀑布流那边对齐：视频 ▶ > 实况 > 动图 > 长图 > 截屏。
   实况/动图排在前面是因为它们在静态缩略图上完全看不出来，信息量更大。

4. **设置里的「操作栏放在右侧」改成「操作栏放在哪」**（用户要求）：左右两个胶囊，
   和下面「双击画面做什么」同一个形式 —— 开关只能表达"是不是右边"，
   用户还得在脑子里把"关闭"翻译成"那就是左边"。

**1.3.26**（长图放大看得清 + 焦点定位不再偏 + 瀑布流删除有了"飞出去"的动线）

1. **长图放大之后不再糊**（用户报"整理照片页长图放大之后看不清"）。
   根因：`AsyncImage(model = uri)` 会自动挂 `ConstraintsSizeResolver`，
   请求尺寸 = **容器尺寸**。可放大是 `graphicsLayer` 做的缩放，**解码器完全不知道** ——
   长图 1x 只显示成两百多 px 宽，Coil 按这个算采样率、解出来就是两三百 px 的小图；
   放大到铺满屏幕等于把这个小 Bitmap 硬拉四五倍。
   现在按 **容器尺寸 × 放大上限** 请求（`decodeSize`）：放大到顶时正好 1:1。
   不会因此爆内存 —— Coil 的解码输出只会不低于请求尺寸、但绝不会超过原图。
   拿不到宽高比时不猜（退回原来的路径）：那种情况推不出真正的上限，
   `snapScale` 会退回 `maxScale`（8），照着算就是"容器 ×8"的白解一张巨图。

2. **进场定位不再偏左偏右**（用户报："焦点图还是偏，有时候偏左有时候偏右，
   点一下定位按钮倒是能回到中间"）。
   这个反差就是答案：`scroll.scrollTo(x)` 内部走 `scrollBy`，会被
   `ScrollState.maxValue` 夹 —— 而进场那一刻布局还没落地，`maxValue` 还是 **0**
   （或另一排布局完留下的值）。于是 `scrollTo(5000)` 的结果是 0，
   也就是"完全没滚动"；布局顺序换一下又夹到另一个值，就成了"有时左有时右"。
   **点定位按钮时布局早已稳定，所以那一下总是准的。**
   现在等到 `maxValue` 涨到目标值以上再滚（带 500ms 超时兜底）。

3. **瀑布流的上滑删除改成"看着它飞出去"**（用户要求，和整理照片页一致）。
   原来是滑够就当场标记、格子立刻被剔除，照片"啪"地消失、没有交代。
   现在先播一段 200ms 的向上飞出（默认值取格高的 1.1 倍，整张滑出格子），
   落地后再真正标记删除。
   两个关键细节：① 触发之后**一次都不许再写 `slide`** ——
   手指还在按着，跟手的 `snapTo` 会把飞出动画取消掉、把照片拽回来；
   ② `markDelete` 放进 `finally` —— 万一这一格在动画中途被移出组合，
   协程取消会让普通写法把这一滑**白滑掉**。

**1.3.24**（提示残留收尾 + 视频缩略图提速 + 收藏/喜欢页操作栏统一）

1. **退出「回到那天」后，照片上不再残留"继续捏合进入「回到那天」"**（用户二次报）。
   1.3.23 用 `LaunchedEffect(index) { progress = 0f }` 清零，**实测无效**：
   退出日期视图回来 `index` 还是同一张，effect 根本不重跑。

   一进日期视图就归零；之后手势因 `pinchTriggered` 不会再写，

**1.3.23**（捏合提示只留一句 + 修焦点图偏左 + 动图不再黑一下 + 「回到那天」含照片与截屏）

   照片与截屏混在一起、各自 kind 正确的结果。视频不并入（视频走抖音式整理页）。

   - `DayCell` 的图片请求尺寸改用 `cellWidthForRatio`（和布局同一个公式）——

**1.3.17**（两排不再分开动 + 末尾闪退加固 + 取整规则全链统一）

1. **两排分开动 / 末尾闪退：两排总宽不同 + 共用一个 ScrollState**。
   每排的 `horizontalScroll` 都按**自己那排**的内容宽去夹 `scroll.value`，
   两排总宽不同 ⇒ 两个 `maxValue` 不同 ⇒ 滑到接近末尾时
   **短的那排先到顶停住、长的那排还在走**；共享状态被两排反复夹来夹去，
   也是闪退的来源。
   修法：把**较短的那排用尾部垫片补到统一总长**（`padToPx`），
   两排 `maxValue` 恒等 ⇒ 谁都不可能先到顶，同步成为结构保证。
   垫片放在端部垫片之外，不参与 `cumPx`，所以不干扰定位与可见区间。
2. **末尾闪退的第二处根因**：`focusRowItem` 改成在本排 `indices` 里查找后
   可能是 **-1**，而 `BooleanArray.getOrElse(-1)` / `FloatArray.getOrElse(-1)`
   会抛下标异常。现在用 `focusRowValid = focusRowItem in indices.indices`
   做双重守卫，任何一项不成立直接给 0。
3. **取整规则全链统一**：视口宽、半视口、错位半格、单格全宽全部改用
   `roundToPx`，与 `cumPx` 保持同一规则 —— 模型与真实布局逐格恒等，
   不留亚像素漂移。

**1.3.16**（定位居中 + 焦点图恒在上排 + 刻度条光标稳定 + 长条图吸合时机纠正）

1. **定位"没严格居中"的根因：对齐的是格子左边缘，不是中心**。
   `cumPx[k]` 是第 k 格的**左边缘**，直接拿它当"落在屏幕正中"，
   实际效果是整张图**偏左了半个格子宽**（格子宽 100~500px，肉眼明显）。
   现在补上该格宽度的一半：`cumPx[k] + w/2` 才是它的中心。
2. **焦点图恒在上排**：分排原本固定 `index % 2`，焦点图序号为奇数时天然落在下排 ——
   「在上排」和「在正中」互斥，约一半序号踩中。
   现在**哪一组排在上排由焦点图决定**（奇数组上排/偶数组上排），
   组内顺序、格宽、间距、砖墙错位全不变，只是换了哪几张在上排。
   相应的局部序号也从写死的 `focusIndex / 2` 改成在本排 `indices` 里查找
   （前者只在"偶数在上排"时成立）。
3. **刻度条光标乱跳**：`scroll.maxValue` 是两排共用一个 ScrollState 的产物，
   而两排总宽不同（照片比例不同 ⇒ 格宽不同），Compose 每次布局都用
   "最后那排"覆盖 maxValue ⇒ 它在两排两个值之间来回跳，指针跟着跳。
   改成两排各自上报总长、外层取**较大者**做稳定分母。
   另外拖动从 `animateScrollTo` 改为 `dispatchRawDelta` 瞬时定位：
   动画会让实际滚动位置追着手指跑，**松手那一刻指针从手指位置切回真实位置 ⇒ 猛跳**。
4. **长条图吸合的时机纠正（上一版改错了）**：用户要的是"**放大之后**才吸合"，
   上一版却让 1x 就走 `ContentScale.FillWidth` —— 长图一进来就是放大且溢出，
   上下滑被图片吃掉、**上滑删除直接失灵**。现在 1x 一律 `ContentScale.Fit`
   （完整显示、上下留黑边），1x 时**一个事件都不消费**（放行给上滑删除与左右翻页）；
   `contentRatio` 只用来在放大后按实际绘制矩形算平移边界。
   关键区分：**显示比例属于"没放大时"，吸合属于"放大后"**，不能混成一条。

**1.3.15**（间距横竖统一 + 定位偏移根因修复 + 长条图吸合修复）

1. **同排左右间距 = 上下间距**：原来上下用写死的 `ROW_GAP = 8.dp`、
   左右用屏宽 2.0%，是两套独立数字。现在两者都取自同一个 `DayMetrics.gap`
   （屏宽 2.2%）—— **横竖一致是结构保证，不是两个数字碰巧接近**。
2. **进场定位"往右偏"的真正根因**（同时也是横滑卡顿与两排错位的根因）：
   `CellSlot` 写的是 `Modifier.width(w).padding(end = gap)`，
   但 **padding 在盒子内部** —— 总宽被 `width(w)` 钉死成 `w`，gap 只是把图片压窄，
   总宽一点没变。而 `cumPx` 的模型是「每格步进 = 宽度 + gap」。
   两边对不上 ⇒ 第 k 格实际位置比模型少了 `k × gap`，误差还是
   `(k − 区间起点) × gap` 这种**随可见区间平移而跳变**的量：
   · 进场定位滚过头 → 照片落在中心偏右；
   · 可见区间每平移一格，整排横跳一个 gap → 「左右滑时卡一下」；
   · 两排的区间起点不同、偏移量也不同 → 「上下排小小错位」。
   修法：外层盒子占 `w + gap`、内层盒子放图片，真实步进与模型恒等。
   另把 `cumPx` 的取整改成 `roundToPx`，与 Compose 布局的实际取整规则一致，
   消除每格零点几像素、累积几十像素的亚像素漂移。
3. **长条图「一进来就吸死」**：`clamp()` 里有一条 `if (scale <= 1.001f) return Offset.Zero`，
   而手势分支在长条图 1x 时**照样消费了事件** —— 事件被吃掉、位移却被当场抹零，
   于是上下左右都动不了。删掉那条特例：边界完全由实际绘制矩形的溢出量决定，
   不溢出那一轴的自然边界就是 0。同时长条图 1x 的单指拖拽**只吃竖直轴**、
   横向放行给外层翻页（否则左右翻页会被抢）。

   焦点序号为奇数（落**下**排）时，上排用自己的累计偏移算出的目标对它毫无意义，
   所以表现为"偶发"（约一半概率）。现在按 `focusParity` 由焦点所在那排自己定位，
   并用 `seedOffset` 广播实际落点，避免另一排闪一下再跳。
4. **修动图进入「回到那天」闪退**：`ImageRequest.size()` 会被 Coil 的 `ImageDecoderDecoder`
   翻译成 `ImageDecoder.setTargetSize()`，对动画源不安全。现在动图不给目标尺寸，
   只有静态图才走降采样。
5. **修瀑布流横滑图片偶发左右卡顿**：与用户的判断一致 —— 圆角原先是每个格子各自现算的
   `RoundedCornerShape`，比例值一变所有格子的 `clip()` 都要重建裁剪节点。改为在
   `DayMetrics` 里一轮布局只造一次，所有格子共享同一实例。
6. **「回到那天」放大页加喜欢 / 收藏**：直接复用整理照片页那一对组件
   （`FavoriteButton` 心形 = 只记在本应用；`StarButton` 星形 = 写进系统相册收藏夹），
   状态与整理页共用同一份仓库数据，点完自增 tick 触发重组让选中态翻过来。
7. **长条图放大后自动居中并吸合**：根因是 `ContentScale.Fit` 下长条图只占中间一条，
   而平移边界却按"图铺满容器"推算，于是滑到头也吸不住。现在 1x 即按宽度铺满
   （`FillWidth`），边界按实际绘制矩形计算，图小于容器的那一轴边界归零（不许拖出黑边），
   缩放变化后重新夹取；纵向溢出时自己消费单指拖拽，双击放大回到 `Offset.Zero` 即自动居中。

**1.2.9**（修预览里视频偏下 —— Dialog 内容框与屏幕不重合）

1. **预览里所有"居中"的元素不再偏下**（用户报的"看这些视频都有点偏下、一直存在"）。
   根因不是播放器、不是宽高比，而是**这个 Dialog 窗口的内容框并不与屏幕重合**：
   实测（小米 HyperOS，1080×2400）内容框从状态栏下沿（≈104px）开始、还越过屏幕下沿，
   于是框的中心落在 ≈1300 而不是屏幕中心 1200 —— 所有 `fillMaxSize + Center`
   的元素（视频画面、暂停按钮、快进胶囊、全屏胶囊）整体偏下约 100px。
   - **顶栏 / 底栏看着正常是个巧合**：窗口下移的距离恰好等于状态栏高度，
     而 Dialog 里 `statusBarsPadding()` 读到 0，两者正好抵消；
   - 全屏胶囊的位置公式本来就按"框顶 == 屏幕顶"写的，所以它也是偏下 100px；
   - **修法是量出来而不是写死常数**：读内容视图在屏幕上的真实位置与高度，
     和屏幕中心比一下得到校正量，作用在"居中层"，chrome 不动。
     窗口真居中时校正量为 0（什么都不做），换 ROM / 机型 / 横竖屏也会自动对上。
   - 整理视频页在 Activity 里、不受 Dialog 窗口影响，本来就居中，不用改。

**1.2.8**（全屏按钮回归 + 上滑收藏改缩放淡出 + 手势误抢修复 + 实况闪帧修复）

1. **修回「整理视频页」竖屏视频偶发长出「全屏观看」按钮**（1.2.3 只修了预览页，
   整理页漏了）。根因还是那个：判断依据用了 MediaStore 的 `WIDTH/HEIGHT`，
   它记的是**编码存储尺寸、不带 rotation** —— 竖着拍、按横幅格式存的视频
   列里是 1920×1080，于是被误判成横屏。现在整理页也改成**优先用播放器
   解码出的真实 videoSize**，胶囊位置同步改用解码尺寸（避免就绪瞬间跳一下）。
   全仓扫过同类判断：其余位置都是照片的比例 / 信息展示，不受影响。
2. **上滑收藏改为「原地缩放淡出」**（用户选定方案 A）：原来收藏是向下飞出
   1.2 个屏高 —— 上滑触发却往下飞，反馈"先往上然后又往下"很怪。
   现在收藏 = 回正 + 缩到 0.85 + 淡出（约 300ms），和删除的"向上飞出"
   彻底区分开；「回到那天」里收藏本来就是绿闪不消失，两边语义一致。
3. **「回到那天」带子手势误抢修复**：格子的竖直判定阈值从写死的 6px 改成
   **系统 touchSlop**。6px 远小于 slop，横滑起手一丁点向上抖就会被判成
   竖直手势并消费掉事件，而 scrollable 的 slop 检测一看到被消费的事件
   就取消整次拖拽 —— 1.2.7 日志诊断证实这就是"直接拖动偶尔完全没反应"
   的成因（85 次拖动里 5 次死在这）。
4. **「回到那天」滑不动问题诊断结论**（1.2.7 日志实证）：85 次直接拖动中
   **80 次实际产生了滚动** —— 直接滑动基本是工作的，此前"滑不动"的体感
   主要来自 (a) 上述误抢 (b) 被底部刻度条带到右边缘后往前滑没有内容。
5. **修长按播放实况照片时闪一帧上一张照片**：实况播放视图是常驻挂载的
   （只用 alpha 控制显隐），而播放器全会话共用一个 —— TextureView 里一直
   留着上一段实况的最后一帧；长按下一张时 alpha 立刻变 1，新视频首帧还没
   渲染出来，那一帧就把上一张照片露了出来。现在加**首帧门控双钥匙**
   （`motionPlayKey` / `motionReadyKey`），和视频整理页、预览页同一套。
   全仓查过：三处播放器视图只有实况这一处缺门控，另两处本来就有。

**1.2.4**（瀑布流性能重构，修「回到那天」进入卡顿）

1. **修掉「回到那天」进入卡一段时间、滑动大多没反应的回归**（1.2.3 引入）。
   根因是结构性的，不是某一个函数慢：瀑布流那一排把**全部**格子一次组合出来，
   每格还各挂一层动画测量节点，几百张图的量级下首次进场和每次滚动都在
   主线程上堆成本。这一版做了三件事：
   - **组合层虚拟化**：按滚动偏移用二分查找算出可见区间，只组合视口 ± 一屏的
     约 25 格，屏幕外改用等宽 `Spacer` 占位 —— 总宽度、每格位置、刻度条完全不变；
   - **`key(global)` 绑定状态身份**：区间平移时循环位置会错位，没有 key
     `Animatable` 和图片请求会漂到另一张图上，每越过一格边界整屏请求重来；
   - **收缩动画只给被标记的格子建**：删掉 `animateContentSize` 那层每格都有的
     测量开销，改成 `Animatable` 显式驱动，被标记的格子才参与。
   进场定位也随之内移（`scroll.maxValue` 是快照状态，首次布局前为 0 时
   不会再把 `located` 置 true 静默失败）。

**1.2.3**（瀑布流上滑删除 + 两个视频预览的修正）

1. **「回到那天」瀑布流支持上滑删除**：某一格往上滑即标记删除。
   - **滑动过程中有明确反馈**：整格随手势加深泛红，文字从"上滑删除"
     变成"松手删除" —— 松手之前就能判断出后果；
   - 松手后这一格连同它自带的间距一起收缩消失，
     **同一排后面的照片跟着左移补上空位**（另一排不动）；
   - 刻意**不做跨排重排**：删掉一张让整屏照片重新排布是一次不必要的视觉地震，
     只在同排内填补最自然；
   - 真正的删除仍在退出这一组时统一交给系统弹窗处理，
     界面上消失 ≠ 立刻删文件。
2. **修掉竖屏视频长出「全屏观看」按钮的偶发 bug**。
   根因不在判断写错，而在**依据本身不可靠**：原来用 MediaStore 的
   `WIDTH / HEIGHT` 判断横竖屏，但那两列记的是**编码存储的尺寸、不带 rotation** ——
   手机竖着拍、按横幅格式存（再靠 rotation 元数据转回来）的视频存的是 1920×1080，
   `width > height` 于是把**竖屏视频误判成横屏**。现在改成优先用
   **播放器解码出来的真实 videoSize**（一定已含 rotation），
   播放器尚未就绪时才退回 MediaStore 那组数做初判。
3. **预览里的视频播放时自动收起左下角信息**，只留进度条，暂停再显示出来。
   「纯观看」的核心正是：**画面才是主体，说明文字不是** ——
   而且那些信息本就不需要一直读，想知道的时候停一下就有了。
   用淡入淡出而非显隐：空间仍然保留，**进度条不会上下跳**。

**1.2.2**（「回到那天」第七版：直接横滑 + 刻度改指针 + 放宽间距）

1. **版本号不再原地打转**。上一轮在同一个版本号上迭代了七次，
   交付物之间无法区分、真机上也无法确认装的是哪一版。现在每次有可交付的
   改动就递增：`versionCode` 40 / `versionName` 1.2.2。
2. **瀑布流可以直接左右滑了**。上一版为了挡住下层照片的拖拽，
   把这一层的指针事件**全部消费掉了**，连带把两排带子的横滑也吃掉了 ——
   结果只能靠底部的刻度条拖动。现在改成**按方向判断**：
   在 `PointerEventPass.Initial` 阶段看本帧位移的主方向，
   竖直分量大才消费（拦住下层照片），**水平分量大则放行**给 `horizontalScroll`。
   判断必须发生在 `Initial` 阶段：指针事件先过父节点的 Initial、再给子节点、
   最后才回父节点的 Final —— 等到 Final 再消费，子节点早就把横向拖拽收走了。
3. **间距放宽、圆角加大**：同排格子间距 `4dp → 10dp`、两排之间 `6dp → 12dp`、
   缩略图圆角 `6dp → 12dp`。参照「去留」——那里的缩略图是一张一张**分开**排布的，
   靠留白把每张框出来，而不是挤成一堵墙；留白本身就是"这是一张独立的照片"的信号。
4. **刻度条改成「刻度不动、指针动」**。上一版是"指针固定、整排刻度平移"，
   用户明确改口为标尺不动、读数移动。这个说法更准：**刻度是标尺（位置绝对、不动），
   指针是读数**。标尺跟着手指跑会让人失去"一共多长"的稳定参照 ——
   和更早那次"背景在刻度条上滑动"的抱怨是同一个病根：**参照物不该动**。
   - 刻度是静止平铺的短竖线，位于一条固定轨道上；
   - 绿色指针（3dp × 26dp）按滚动比例在轨道上左右移动；
   - 轨道两端各留 14dp 内边距，指针不会贴到屏幕边缘；
   - 手指在**整条轨道任何位置**按下/拖动都能定位（不要求精确点中细指针）。
5. **进场定位改用真实测量值**。原来用写死的"平均格子宽度"估算，
   但一天里横图竖图混着，估算偏差很明显。现在由 `FilmstripRow` 把
   **每个格子左侧的累计偏移**上报，外层据此把正在看的那张精确推到屏幕正中。
   定位只执行一次 —— 用户随后自己滑走了不会被重新拽回去。
6. 顺带修掉的隐患：`Row` 会一次性组合整排全部格子，一天几百张时首次进入必卡。
   现在**只组合"当前视口 ± 一屏"内的格子**，屏幕外按算出来的相同宽度放空白占位 ——
   总宽度、每张位置、两排对齐、刻度映射全都不变，只是屏幕外的不再加载图片。

   心形 / 星形的大图标，下面写清楚动作与结果（"喜欢 · 已添加"），
   侧栏图标同步变化。反馈是必需的：这两个动作语义不同
   （喜欢只记在本应用、收藏会进系统相册），用户必须能一眼分清刚做的是哪个。
   - 默认给「喜欢」：双击是高频且无提示的手势，落在"一秒就能撤销、
     不碰系统相册"的动作上最安全；
   - 设置 →「视频播放」→「双击是喜欢」可切到收藏。
2. **「回到那天」不再让用户选日期，直接跳到当前这张所属的那天**。
   原来捏合之后弹一个日期列表让人自己挑 —— 但用户是在看某张照片时起的念头，
   他关心的是**这一张的那天**，答案是现成的。把问题抛回去是识别错了意图。
   现在捏合 → 直接进整屏日期视图（版式参照「去留」）：
   - 顶栏 `←` / 居中两行「回到那天」+ 大号日期 + 星期与条数 / `✓`；
   - 内容是当天照片的**双列瀑布流**（不是逐张浏览）——
     "原来这天拍了这么多"的纵深感本身就是信息；
   - 点任意一张进全屏预览，可左右翻；
   - `✓` 用这一天开一组整理（不结束当前会话，已标记 / 已收藏保留）；
     `←` 原样回到刚才那张，什么都没变；
   - 整屏视图会拦截指针事件 —— 只加不透明背景是挡不住下层的，
     底下的拖拽检测照样会收到事件，划一下照片就跟着飞走了。
3. **预览页的顶栏 / 底栏修好遮挡，并降低视觉重量**。
   "被挡住一半"的根因：宿主 Activity 开了 `enableEdgeToEdge()`，
   但 `Dialog` 窗口默认仍是 `decorFitsSystemWindows = true` ——
   这种半个 edge-to-edge 的状态下 `statusBarsPadding()` 读到 0，
   顶栏就紧贴屏幕顶边被状态栏压住。现在显式关掉它。
   同时把渐变从全黑压到 `0x99`、文字降到次级 / 三级色：
   浏览场景里这两条栏只需要"找得到"，不该在每张照片上抢注意力。
4. 数据层：`dayStartOf` 从 `MediaRepository` 提为 `core` 顶层函数，
   与界面共用同一套日期换算（两处各写一份 Calendar 会在时区边界上分叉）。

**1.1**（屏幕级单视图播放器 + 「回到那天」）

1. **屏幕级单视图播放器** —— 这是"上下滑闪一下"与"离屏留一块旧帧"那个取舍的第三条路。
   两个画面（整理视频页、收藏 / 回收站预览）都改成：
   **全局唯一一份 PlayerView 挂在屏幕层，永不建 / 毁，位置跟着分页偏移走**：
   - 每页各挂一个 → 离屏页的 TextureView 保留最后一帧，残留在屏幕上；
   - 视图随页面建 / 毁 → 切页瞬间重绑 Surface，闪一下；
   - **屏幕级唯一一份** → 既不建 / 毁、也没有离屏副本，两个问题一起消失。
   
   跟随算法：`translation = -currentPageOffsetFraction × 页面尺寸`，
   **在 `graphicsLayer { }` 的绘制阶段读取** —— 滑动时只失效绘制、不触发重组，跟手且不掉帧。

   底部「移出收藏 / 删除」、横屏视频的全屏胶囊实际上是隐形的。
   现在两个画面统一成 **页面 → 播放器 → 信息层**。
3. **「回到那天」按天开组**。手势阶梯补上最后一级：
   照片页**双指放大 → 缩回初始大小 → 继续捏合**进入日期视图。
   - 只有"从初始大小开始的手势"能触发，来回试探会把累计量退回去，不误触发；
   - 进入某天**不结束当前会话**：已标记 / 已收藏保留，退出时一起收尾；
   - 数据层：`dayHistogram` 与 `itemsOnDay` 的统计口径严格对齐
     （照片 / 截屏分流 + `DATE_TAKEN` 为空时按 `DATE_ADDED` 退回）。

**1.0.16**（实况照片兜底修复 + 收藏视频上下滑 + 位置自检抽样纠偏）

1. **修掉实况照片检测里的一处逻辑错误**，这是它一直"不支持"的真正原因：
   ```kotlin
   if (!probe.isMotionPhoto) return null      // ← 早退
   val scanned = MotionPhoto.findByMp4Signature(...)   // 永远跑不到
   ```
   `MotionPhoto` 里本来写了三层检测，第三层是**不依赖任何厂商元数据的  
   MP4 签名扫描**（直接在文件里搜 `ftyp` 盒子）—— 它恰恰是为  
   "厂商的 XMP 认不出来"这种情况准备的。但那句早退把它挡在门外：  
   **XMP 认不出来 ⇒ `isMotionPhoto` 为 false ⇒ 直接返回，兜底完全没机会执行。**

   现在改成：元数据拿不到偏移量就**无条件扫签名**。
2. **`probe` 也加了一层尾部扫描**。原来只有"读文件头解析 XMP"一条路，  
   厂商不写 XMP 就完全没辙。现在头部没有（或只有标记没有偏移）时，  
   会再读一次**文件尾部**找 MP4 签名 —— 实况片段一定追加在文件末尾，  
   所以视频的 `ftyp` 盒子必然落在尾部窗口内。这样既不必读整个文件，  
   又能覆盖"元数据完全不可用"的机型。  
   （`findByMp4Signature` 因此多了 `fromOffset` 参数，传 0 仍是全文扫描。）
3. **收藏页的视频改成上下滑**。全是视频时用 `VerticalPager`，和视频整理页手感一致；  
   混着照片时仍是左右滑 —— 竖着翻照片会让人下意识以为在翻列表。
4. **位置自检的抽样纠偏**。原来写的是 `idsOf(kind).take(30)`，  
   那只会取到**最旧的 30 张**，而最旧的往往是截图和下载图，全都没有位置信息 ——  
   结论是假的。改成随机抽 60 张。

**1.0.12**（开组重构 + 六项调整）

1. **彻底重构开组的取数方式，照片/截屏不再需要等待**。  
   之前 1.0.8 只是"不再每次强制重扫"，但只要缓存过期（5 分钟）或应用重启，  
   仍然要把整张 images 表读进来 —— 几万行 × 10 列，光填充 CursorWindow 就要一两秒。  
   这次换了根本做法（`MediaRepository`）：
   - 每个分类只缓存 **ID 列表**，查询只投影 `_ID` 一列（列数少一个数量级，快得多）
   - 截屏 / 照片的区分**下推到 SQLite** 的 `LIKE` 条件，不再在 Kotlin 里逐行拼字符串匹配
   - `sampleItems()` 直接在 ID 列表上洗牌抽十几条，**只对这十几条取完整信息**
   - 于是"开组"的代价与媒体库有多大**彻底解耦**
   - 顺带用 `Mutex` + 双检锁住缓存填充，避免启动预热和用户点开组并发跑两次全量查询
2. **收藏页把照片和视频分开**（顶部两个分类胶囊），并新增**纯观看模式**：  
   打开后预览里不再出现「移出收藏 / 删除」，长按也不会移除，只用来安静地翻看。  
   状态记在设置里。
3. **修掉横滑时误触发缩略图栏**。根因在 `detectTapsWithoutConsuming`：  
   它靠 `isConsumed` 判断"这是拖拽不是点击"，但**父节点的拖拽检测在 Main 阶段  
   是后于子节点拿到事件的**，所以子节点读到的 `isConsumed` 还是 false ——  
   横滑被误判成点击。现在额外自己算位移（超过 touchSlop 就算拖拽），  
   不再依赖事件消费的可见性。
4. **切后台暂停、切回来自动接着播**。但前提是"切后台之前本来就在播"——  
   用户自己按了暂停的，回来不会被强行恢复。
5. **视频页新增左右滑动快进 / 快退**，跳转量与滑动距离成正比  
   （满屏宽 ≈ 跳转整个视频，长视频封顶 3 分钟），拖动时有居中提示显示目标时间。  
   竖直方向仍然归 Pager 翻页，两者互不干扰。
6. **删掉旋转功能，改成横屏视频的全屏播放**。全屏按钮**只对横屏视频出现**  
   （竖屏视频本来就撑满，没有全屏的意义）：点击把 Activity 转成横屏并隐藏系统栏，  
   再点一次还原；离开这一页一定会还原方向和系统栏，不会把整个应用卡在横屏。

**1.0.11**（拍摄地点）

1. **视频左下角显示拍摄地点**。取「省 市 区」三段并去重，比完整地址好读。  
   几个必须说清楚的前提：
   - Android 会对媒体里的位置信息做**隐私脱敏**，读取经纬度需要单独的  
     `ACCESS_MEDIA_LOCATION` 权限。**这个权限在进入视频整理时才申请** ——  
     和用户当下的动作直接相关，比在应用启动时弹一个莫名其妙的框要好。
   - `LATITUDE` / `LONGITUDE` 是**受该权限约束的敏感列**，性质和之前踩过坑的  
     `XMP` 完全一样。所以绝不放进主查询投影，只在看某一条时单独查它的 Uri，  
     全程 `runCatching` 兜底 —— 拿不到就当作"没有位置信息"，绝不影响浏览。
   - **下载来的视频通常本来就没有位置信息**（相机拍摄的才有），  
     这种情况下这一行不会显示。
   - 地名反查用 `Geocoder`，按坐标缓存 —— 一次旅行里几十段视频往往在同一个地方。  
     设备的地理编码服务不可用时返回空，同样不显示。
   - 设置里可以关掉。拒绝权限也不影响任何其他功能。

**1.0.10**（操作栏换边、旋转、消除闪烁、双击不再闪暂停）

1. **操作栏可放左或右**。设置里新增开关，收藏 / 删除 / 分享 / 旋转 / 静音整组一起换边。  
   惯用左手、或者习惯用左手滑视频的人会更顺手。
2. **视频页新增顺时针旋转按钮**。每点一次转 90°，转一圈回到原位。  
   用途：横屏视频在竖屏里只占中间一条，转 90° 后反而能撑满屏，把手机横过来就是满屏。  
   实现是给「缩略图 + 播放器」整层加 `rotationZ`，两者始终对齐。  
   图标复用了 core 里的 `Refresh`（本身是逆时针），横向镜像后就是顺时针。
3. **修掉上下滑时的闪烁**。两个原因一起修：
   - 换页时 ExoPlayer 要重新 `prepare`，这段空窗里播放器是空白的。  
     现在监听 `Player.Listener.onRenderedFirstFrame()`，  
     **首帧就绪之前把播放器透明掉，露出下面的缩略图**，就绪后再显示 ——  
     由于首帧内容和缩略图是同一帧，切换是无缝的。
   - 新增 `beyondViewportPageCount = 1`，提前组好相邻一页，  
     让它的缩略图先 load 起来，快速滑动时不会看到空白。
4. **修掉"双击收藏总会先闪一下暂停"**。根因在 `detectTapsWithoutConsuming`：  
   双击的第一下会被当成单击**当场执行**（切换播放状态），第二下才识别为双击。  
   过去的补偿写法是"双击时再切回来一次"，但那一放一收本身就是一个可见的停顿。  
   现在改为：**只要注册了双击处理，单击就延后到双击判定窗口结束再执行**，  
   第二下到来时直接取消挂起的单击。  
   代价是单击（暂停/播放）会晚 280ms 生效 —— 存在双击手势时这是无法回避的取舍，  
   用一次可感知的延迟换掉每次双击都闪一下，是划算的。

**1.0.9**（后台暂停、音量联动、信息补全、看完自动退出）

1. **切到后台自动暂停视频**。整理视频页和全屏预览都加了生命周期监听  
   （`LifecycleEventEffect(ON_STOP)`）—— 之前退到后台视频会继续播，既费电又会突然出声。
2. **调整系统音量就自动解除静音**。视频默认静音播放，但用户一旦动了音量，  
   说明他此刻想听，这时不该再要求他回界面点一次静音开关。  
   实现上**没有去拦音量键**，而是直接观察 `AudioManager` 的音量：
   - 音量面板的滑块同样能改音量，拦按键拿不到那种情况
   - `Activity.dispatchKeyEvent` 在 AndroidX 里是 `@RestrictedApi`，  
     从应用侧覆写会被 Lint 判错（这条第一版就踩了）  
     只在「当前是静音」时轮询，一旦解除静音循环立即退出，开销可忽略。
3. **视频整理页左下角补上拍摄日期和文件大小**，和照片页保持一致  
   （原来是文件名 + 文件夹 + 时长）。
4. **看完一组自动退出**。之前滑到最后一张之后会停在一屏纯黑上不动，  
   看起来像卡死。现在：
   - 照片：最后一张飞出的动画播完（320ms）后自动收尾
   - 视频：在最后一屏继续上滑时收尾（用 `NestedScrollConnection` 检测  
     "还有滑动意图但没有可滚动余量"）  
     两处都加了 `finishing` 标志位，避免连续触发弹出多个系统弹窗。
5. **「清零统计」的二次确认**在 1.0.7 就已加入，本次把确认按钮的文案改成  
   「确认清零」让它更明确。

**1.0.8**（开组速度、滑动行程、精简确认）

1. **修掉照片/截屏开组要等很久的问题**。根因是 `buildSession` 里写死了  
   `repo.all(kind, forceReload = true)` —— **每次开组都把整张表重新查一遍**。  
   照片慢而视频快，是因为照片数量本来就多，而且图片那条路径每行还要做截屏判定  
   （字符串拼接 + 7 次匹配）。三处一起改：
   - 开组不再强制重查，直接命中缓存（应用启动时已经在后台把缓存load好了）
   - 删除后不再 `invalidate()` 丢掉整个缓存，改成 `dropFromCache(被删的那几条)` **增量摘除**
   - 缓存加 5 分钟 TTL，兼顾"新拍的照片要能出现"
   - 顺带把截屏判定的逐行 `lowercase()` 去掉，改成一次拼接 + `contains(ignoreCase)`
2. **左右滑的判定行程从 110dp 缩到 72dp**。翻页是高频动作，每次都要划过小半个屏幕  
   才生效会很累。72dp 仍是明确的主动位移，不会和手滑混淆。
3. **精简确认：删掉「清空回收站」的应用内确认框**。  
   紧接着的系统删除弹窗本身就是确认，两道确认同一件事只是啰嗦。  
   原有的信息（可释放多少空间、2000 项上限）挪到了按钮的副标题上，信息没丢。

> **关于「移入回收站为什么还要确认」**
>
> 那个确认框**不是本应用的，是 Android 系统的**，而且删不掉。  
> Android 从 11 起规定：应用要删除或移入回收站**不是自己创建的**媒体文件，  
> 必须先通过 `MediaStore.createTrashRequest` / `createDeleteRequest` 拿到用户授权，  
> 系统弹的那个框就是授权流程本身。没有它，系统不允许任何应用静默改动别人的照片。
>
> 所以本应用能做的是**保证自己不再额外加一层确认** —— 目前滑走标记、退出、  
> 清空回收站三条路径，都只有系统这一个弹窗。

**1.0.7**（返回手势、收藏同步诊断、去掉冗余确认）

1. **返回手势全面适配**。三个问题一起改：
   - **整理照片/视频时返回，已标记的项被丢弃** —— 过去返回走的是  
     `performDelete = false` 分支，整批标记被静默扔掉，用户完全看不出来。  
     现在退出**直接把已标记的项交给系统删除流程**。
   - **预览层没有接管返回**（在收藏页看视频时按返回会直接退回桌面）。  
     `MediaPreviewOverlay` 加了 `BackHandler`。
   - **非「整理」页按返回直接退出应用**。`AppRoot` 加了一层：  
     不在整理页时先退回整理页。返回回调是后注册者优先，所以会话页和预览层  
     各自的处理仍然盖在它上面，层级正确。
2. **去掉了退出时那道多余的确认**。原来一组结束后会弹「删除 / 保留」，  
   问完才是系统的删除弹窗 —— 两次确认同一件事。现在直接进系统弹窗，  
   系统那个框本身就是确认。`BatchReviewSheet` 已整个删除。
3. **收藏同步现在会核对结果并给出结论**。系统的收藏写入是  
   「弹窗 → 用户确认 → 写 `MediaStore.IS_FAVORITE`」，但**点了"允许"不等于真的落库了**：  
   各家厂商对"收藏"的实现不一样，部分相册应用根本不读这个标记。  
   所以现在写入之后会**读回来核对**：
   - 核对通过 → 提示「已同步 N 项」
   - 核对该项仍为未收藏 → 提示「系统没有记录收藏标记，这台设备的相册可能不使用它」，  
     并**自动关闭自动同步**（否则每轮都白弹一次窗）
   - 请求或启动弹窗失败 → 直接说出失败原因，不再静默
4. **收藏页的预览里加了「删除」**，和「移出收藏」并排。
5. **「清零统计」改得更隐蔽**：移到整页最底部、降到最小的文字层级，  
   并写明"只归零计数，不动任何照片视频"，另外加了二次确认。  
   入口越不起眼，越要保证"点到"不等于"执行"。

**1.0.6**（四个 bug + 一处交互调整）

1. **截屏整理时提示"正在随机抽取视频"**。1.0.3 加截屏分类时，有几处判断写的是  
   `kind == PHOTO` 的三元表达式，截屏就落到了 else 分支。已全部改成 `kind.isImage`。  
   顺带排查出**同一类的另外三处**，其中一处是真 bug：  
   **开始截屏整理时检查的是视频权限** —— 只给图片权限、没给视频权限的设备上，  
   点「整理截屏」会跑去申请视频权限。  
   另外两处：分享截屏时的 MIME 类型给成了 `video/*`；回收站列表把截屏标成"视频"。
2. **打开收藏不能立刻显示**。根因是 `favoriteItems()` 会把**整个媒体库**扫出来再过滤 ——  
   在几万条视频的设备上要等好几秒，页面看起来就是空的。  
   新增 `MediaRepository.byKeys()`，用 `_ID IN (...)` 精确定位（按 500 一批分块，  
   避开 SQLite 的 IN 参数上限），代价只和收藏数量相关，与库的大小无关。  
   收藏读取、收藏同步差值计算、已看/收藏的失效清理**全部改走这条路**，  
   同时加了加载态提示 —— 即使慢，用户也知道是在读，而不是"空的"。
3. **收藏页点击跳外部应用**。改成应用内全屏预览，复用回收站那套 `MediaPreviewOverlay`  
   （左右滑动切换、双指缩放、单击收起信息栏），底部直接给「移出收藏」。  
   在收藏夹里点开只是想再看一眼、顺手决定去留，被丢到另一个 App 会完全打断节奏。
4. **视频页的静音开关挪到右侧操作栏**，和收藏/删除/分享放在一起，并改成图标  
   （喇叭 / 喇叭加叉）。视频整理时手本来就在右侧，比顶栏好按得多。  
   图标是自绘的：`material-icons-core` 里没有音量图标（core 一共只有 45 个，已核对），  
   为两个图标引入 `material-icons-extended` 会让包体明显变大，不划算。

**1.0.5**（修复 1.0.3 引入的严重回归：照片一张都读不出来）

1. **根因**：1.0.3 为了在查询阶段就识别实况照片，把 `MediaStore.MediaColumns.XMP`  
   加进了图片查询的投影。但**这一列受 `ACCESS_MEDIA_LOCATION` 约束**（用于位置隐私脱敏），  
   部分厂商的 MediaProvider（**包括小米**）只要在投影里看到它就**直接抛异常**。  
   异常又被 `runCatching(...).getOrDefault(emptyList())` 吞掉，于是表现成  
   「照片 0 张、截屏 0 张，但视频 8544 正常」—— 视频那条路径没加 XMP，所以幸免。  
   修法：**把 XMP 从查询里彻底移除**。实况判定本来就该读文件头  
   （1.0.4 加的 `MotionPhoto.probe()` 正是干这个的），既不需要这一列，也不需要额外权限。
2. **查询加两级投影兜底**。完整投影失败时自动退到最小投影（只留任何 Android 版本、  
   任何厂商都一定提供的那几列）重试一次。以后再有某一列在某个 Provider 上不可用，  
   也不会退化成"整个相册是空的"。
3. **区分「确实没有内容」和「内容读不出来」**。空状态弹层现在分两种文案：  
   读取失败时用醒目颜色直说读取失败，而不是含糊地提示"可能没授权"。  
   这次排查之所以费劲，就是因为失败被静默伪装成了空。
4. 实况角标改由文件头探测驱动 —— 卡片切到即探，胶片条则整组预探测一遍  
   （一组十几张，总读取量约 2MB），所以角标依然准确。

**1.0.4**

1. **修掉视频进度条「从中间往两边长」的问题**。这不是设计，是个 bug：  
   进度条的父容器为了让 2dp 的细线在 26dp 的触摸区里垂直居中，写了  
   `contentAlignment = Alignment.Center` —— 但那同时也把子元素**横向**居中了，  
   于是填充条从中点向两侧展开。加一句 `.align(Alignment.CenterStart)` 按回左边，  
   现在是从左到右。
2. **实况照片补齐小米和通用格式**。原来只解析了旧标准，现在三代格式全部覆盖：
   - **旧标准** `GCamera:MicroVideoOffset` —— 直接给出「距文件尾字节数」。  
     Google 早期机型、旧版 MIUI 用这个。
   - **新标准** `Container:Directory` 里 `Item:Semantic="MotionPhoto"` 那一项的  
     `Item:Length` —— **小米从 HyperOS 3 起切换到了这个**，三星 / Pixel 一直在用。  
     注意不能全局搜第一个 `Item:Length`：主图项也有 Length，取错了会算出一个完全错误的偏移，  
     所以实现是按 `Container:Item` 切段、只在语义为视频的那一段里取值。
   - **无元数据兜底**：嵌入的视频一定是 MP4，而 MP4 第一个盒子是  
     `[4字节长度][f t y p][主品牌]`。直接在文件里搜 `ftyp`，位置减 4 就是视频起点，  
     完全不依赖厂商元数据。带三重校验防止被 JPEG 数据里偶然出现的字节骗到：  
     盒子长度合理、主品牌在白名单内、视频必须落在文件后半段  
     （能读到紧邻的 JPEG 结束标记 `FFD9` 则直接确认）。
3. **实况探测拆成两级，兼顾覆盖面与性能**。原来只信 MediaStore 的 XMP 列，  
   而部分设备这一列是空的 —— 那样就完全发现不了实况照片。现在：
   - 浏览时做**廉价探测**（读 128KB 文件头），所以 XMP 列为空也能发现
   - **只有真正长按播放**时才可能扫全文件找 MP4 签名，避免翻看照片时反复读几十 MB
   - 结果都按条目缓存在内存里

**1.0.3**

1. **新增「整理截屏」分类**。截屏单独成组后删起来极快 —— 大部分截屏看一眼就知道没用。  
   识别靠 bucket / 相对路径 / 文件名三个维度匹配（`screenshots`、`截屏`、`截图` 等），  
   因为 **Android 并没有「这是截屏」这种元数据**，只能启发式判断。  
   截屏与照片共用同一张 images 表，复用原有的 `storeKey()` 键空间，**收藏和已看记录不需要迁移**。
2. **照片支持双指缩放**。捏合放大看长图细节，放大后单指平移，双击在 1x / 2.5x 之间切换。  
   手势归属是这里的难点：它只吃「双指」和「已放大后的单指」，其余一律放行给外层，  
   否则整个上滑删除 / 左右翻页会瘫痪。
3. **底部缩略胶片条（对齐 iOS 相册）**。横向触摸滚动、点击直接跳到那张、  
   当前项用高亮描边 + 不压暗标记且自动居中。  
   居中靠的是给 LazyRow 加左右等宽的 `contentPadding` —— 这样 `scrollToItem(i)` 天然居中，  
   不需要自己算偏移量。
4. **胶片条默认收起，单击弹出、再单击收起**。未展开时底部有一行操作提示。
5. **动图支持**：加 `coil-gif`，注册 `GifDecoder` + `ImageDecoderDecoder`（API 28+），  
   GIF 和动态 WebP 都会真正动起来。不加依赖只会停在第一帧。
6. **实况照片（Motion Photo）支持**。Android **完全没有官方 API** ——  
   既没有 IS_MOTION_PHOTO 列，也没有任何相关类（已核对 android-35 的  
   `api-versions.xml` 与 `android.jar`）。实现路径是：
   - 查 `MediaStore.MediaColumns.XMP` 列（API 30+）找 `MicroVideoOffset`
   - XMP 为空时按需读一次文件头自己找（只在看某一张时触发，不进列表查询路径）
   - 把追加在 JPEG 尾部的 MP4 流式抽取到缓存，用 ExoPlayer 播放
   - **长按播放**，与 iOS 相册的习惯一致；卡片上有「实况」角标
   - 识别不出或抽取失败会明确提示，按普通照片处理，不报错

**1.0.2**

1. **回收站支持全屏预览**。点任意一项进入全屏预览，左右滑动看下一项/上一项；

2. **新增「清空回收站」**。一键批量彻底删除，显示总项数和可释放空间，  
   点击前有二次确认（这是全应用最不可逆的操作）。系统对单次删除请求有 2000 项上限，  
   超出时会明确告知本次处理多少、剩余的可再次清空。
3. 预览能力抽成了通用组件 `ui/common/MediaPreviewOverlay.kt`，  
   底部操作区通过参数注入，之后收藏夹等场景可以直接复用。

**1.0.1**（真机试用后的三个修复）

1. **修掉「下一张照片提前透出来」**。照片用 `ContentScale.Fit` 完整显示，横图上下会留黑边，  
   而留边区域原本是透明的，下层那张更细长的竖图就从留边处透了出来。  
   现在每一层都带**不透明背景且不缩放**，任何时刻屏幕上只会有一张图。  
   （这里刻意没有给下层做缩放堆叠效果 —— 一旦下层比上层小，上层的边缘就会露出再下一层的内容，  
   屏幕上会同时出现两三张不同的图，正是要避免的情况。）
2. **左右滑统一为「下一张」**。原来左滑前进、右滑回退，随机流里回退没有意义，  
   而且误触会打断浏览节奏。现在两个方向都前进，卡片朝划走的方向飞出。
3. **收藏打通系统相册**。通过 `MediaStore.createFavoriteRequest` 写入系统的  
   `IS_FAVORITE` 列（**API 30 起提供**，与本工程 minSdk 一致，Android 11+ 全支持）。  
   系统的收藏标记应用无法静默修改，每次都要用户点系统弹窗确认 ——  
   所以实现上**不允许**在收藏手势里直接调用，而是攒成一批提交：
   - 默认每轮整理结束自动同步一次（设置里可关）
   - 收藏页有「同步 N 项到系统相册」的入口，可随时手动跑
   - **取消收藏也会同步**：应用里取消后，系统相册里那条的收藏标记会一并撤回，  
     否则两边会长期不一致  
     同步进度记录在 `synced_favorites.txt`，只有用户在系统弹窗里点了确认才会标记为已同步；  
     点取消不算，下次还会提示。

## 三、几个关键设计决策

这部分比代码本身重要。如果你想改这个项目，先读这里。

### 1. 手势分层：导航归滑动，决策归点击

这是整个 App 最核心的一个决定，也是从去留的公开设计思考里学到的。

**上下滑已经被"切换视频"占满了**。如果删除也做成上滑、收藏也做成下滑，  
三者会互相打架，谁都用不痛快。解法是把手势分成两层：

| 层级   | 动作       | 承担     |
| ---- | -------- | ------ |
| 导航   | 上下滑      | 切换内容   |
| 临时动作 | 长按       | 2 倍速快进 |
| 决策   | 双击       | 收藏     |
| 危险动作 | **侧边按钮** | 删除     |

删除刻意**不用手势**。本地文件删掉不可逆，而"顺手"恰恰是本 App 鼓励的状态，  
越顺手越容易误删 —— 危险动作必须要有一点摩擦。

### 2. 不消费事件的点击检测器

`ui/common/Gestures.kt` 里的 `detectTapsWithoutConsuming` 是整个项目技术上最麻烦的一块。

现成的 `detectTapGestures` 内部会 `down.consume()`。一旦按下事件被消费，  
同一个区域上的 `VerticalPager` 就拿不到拖拽，**视频流会直接划不动**。  
这两者是互斥的，必须有一个让路 —— 让路的应该是点击检测。

所以那个检测器全程不调用 `consume()`：拖拽照常传给 Pager，  
点击 / 双击 / 长按由它自己判定。判定"这次手势其实是拖拽"的依据是  
`positionChangeConsumed()` —— Pager 开始滚动时会消费位移，看到这个信号就放过。

> 踩过的坑：长按判定不能只看"超时"。用户拖到一半停住不动也会超时，  
> 那种情况必须放过，否则每次滑动到一半都会误触发倍速。  
> 代码里用 `dragged` 标志处理了这一点。

### 3. 下一张要"垫在下面"，不是"滑进来"

照片翻页时，当前张跟手左移，**下一张原地露出来**，而不是从右边滑入。  
这样眼睛不需要等下一张停稳就能看清内容，连滑几百张也不会累。  
这是从系统相册的翻页手感里抠出来的改进。

实现上就是把 `items[index+1]` 和 `items[index+2]` 用完全相同的位置渲染在底层，  
顶层卡片用 `graphicsLayer.translationX/Y` 位移 —— 用 graphicsLayer 而不是 layout offset，  
拖拽过程不触发重新布局，只走绘制阶段。

### 4. 删除必须"标记"与"执行"分离

浏览时上滑只做**标记**，一组结束后统一弹二次确认，再走系统授权对话框。

原因有两个：一是系统删除请求每次都弹框，逐条删会被弹窗淹没；  
二是本地文件彻底删除不可逆，批量确认是唯一的人工闸门。

用户在系统弹窗里点"取消"时，这些项**不计入**"已删除"统计 ——  
`StartIntentSenderForResult` 的 `resultCode` 会告诉你是 `RESULT_OK` 还是 `RESULT_CANCELED`。

### 5. 只用 done list，不出现 todo list

界面上没有任何"还剩 N 项待处理"。全是"已回顾多少 / 已删除多少 / 瘦身多少"。

去留的作者讲过这个道理：照片清理这件事让人抗拒的原因是它像家务，  
而家务的本质是"你还没做完"。所以整条产品线都不给你算剩下的量。

### 6. 图片和视频的 `_id` 会撞号

MediaStore 里图片和视频是**两张独立的表**，各自的 `_id` 都从 1 开始自增。  
"图片 100"和"视频 100"完全可能同时存在。

所以收藏集合和已看集合都用复合键存储（`Models.kt` 里的 `storeKey()`，  
把类型编进最低位），否则收藏一张图会让某个视频也莫名变成已收藏。

### 7. 回收站用系统的，不自己搬文件

`MediaStore.createTrashRequest` 走的是系统回收站，保留 30 天。  
如果自己把文件搬到应用私有目录，**卸载 App 就全丢了**，反而更不安全。

### 8. 缩略图垫在播放器底下

视频页永远先渲染 Coil 抽的视频首帧，播放器叠在上面。  
因为缩略图就是第一帧，播放器接管的瞬间几乎无视觉跳变 ——  
避免了"先黑一下再出画面"。这需要在 `QusheApp` 里注册 `VideoFrameDecoder`。

单个页面只养**一个** ExoPlayer，翻页时换 `mediaItem`。  
本地文件 prepare 几乎瞬时，不需要为相邻页面各开一个解码器（那是 OOM 的经典来源）。

### 9. 缩放和滑动的手势归属

加了双指缩放之后，同一块区域上叠了两套手势，必须明确谁在什么时候让路。  
规则是：**缩放组件只吃两种事件 —— 双指，以及"已经放大之后的单指"**。  
其余一律放行。

这样做的依据是子节点在 Main 阶段先收到事件：`ZoomableImage` 消费了，  
外层 `detectDragGestures` 内部的 `awaitTouchSlopOrCancellation` 就会放弃启动拖拽，  
上滑删除 / 左右翻页自然失效 —— 这正是放大状态下想要的效果（此时用户是在看局部，  
不是在切照片）。而没有消费时，外层照常工作。

### 10. 内层和外层的点击检测可以共存

`ZoomableImage` 内部处理双击（缩放复位），外层处理单击（展开胶片条）。  
两者都不消费事件，所以双击时**单击的回调也会被触发一次**。

这不是 bug：被触发的是一个开关（胶片条显示/隐藏），切两次等于没切，自然抵消。  
用幂等操作吸收冗余事件，比引入复杂的双击超时仲裁要可靠得多 ——  
视频页的"单击暂停 + 双击收藏"用的也是同一招。

## 四、已知限制

1. **只做过编译期验证，没有跑过真机。** 工程已构建通过（零错误零警告）并通过 Lint 检查，  
   但运行期行为（手势手感、系统删除弹窗、回收站读写）必须在真机上才能确认。
2. **工程路径不能含中文。** 见第一节，目前靠 `android.overridePathCheck=true` 绕过，  
   彻底解法是挪到纯英文路径。
3. **只读系统相册（MediaStore），不是文件浏览器。**  
   和去留 / 回留一样，它看不见下载目录里未入库的视频文件。  
   如果你的视频是用下载工具存到文件夹、没进系统相册，这里看不到。  
   要支持任意文件夹需要走 SAF（`ACTION_OPEN_DOCUMENT_TREE`），是另一个模块。
4. **随机顺序，不是顺序播放。** 这是刻意的 —— 但如果你想要的是"按顺序刷完一个文件夹"，  
   本项目不是那个东西。
5. **未实现全部子分类**。目前有照片 / 截屏 / 视频三类。  
   「自拍」「实况」「动图」这些子分类同样可以按同样的方式加（改 `MediaKind` +  
   在 `looksLikeScreenshot` 旁边加判定），但需要先想清楚它们和照片的重叠关系。
6. **截屏判定是启发式的**。Android 没有「这是截屏」这种元数据，  
   本项目按 bucket / 相对路径 / 文件名匹配关键词（`screenshots`、`截屏`、`截图` 等）。  
   如果你把截屏放在自定义目录且名字里没有这些词，就不会被归到截屏分类。
7. **实况照片已覆盖三代格式**（旧标准 MicroVideoOffset、新标准 Container Item:Length、  
   以及不依赖元数据的 MP4 `ftyp` 签名扫描）。如果仍然识别不出，  
   说明该机型的封装方式超出了这三种 —— 长按时会明确提示，不会静默失败。  
   角标由文件头探测驱动，与查询阶段无关。
8. **`MediaStore.MediaColumns.XMP` 不能放进查询投影**。  
   这一列受 `ACCESS_MEDIA_LOCATION` 约束，部分厂商的 MediaProvider 会在投影里出现它时  
   直接抛异常，导致**整个媒体集合读不出来**。需要 XMP 时只能直接读文件头。  
   这个坑在 1.0.3 踩过一次，代价是"照片 0 张"且极难定位 —— 详见更新日志。
9. **部分厂商 ROM 未实现系统回收站接口**，回收站页面会降级显示空列表。  
   这种情况微信/QQ 等应用也会有同样的限制。
10. **视频用 `RESIZE_MODE_FIT`（完整显示）而不是裁切成 9:18。**  
    去留为了让竖屏视频更有沉浸感会裁切，但裁切会切掉用户自己拍的内容。  
    这里选择了不切。
11. **只支持 Android 11（API 30）及以上。**

### 构建过程中修掉的真实问题

记录一下，因为都是文档里不显眼、但会直接导致编译失败或运行异常的点：

1. **`MediaStore.createTrashRequest` / `createDeleteRequest` 返回的是 `PendingIntent`，不是 `IntentSender`。**  
   必须先取 `.intentSender` 才能交给 `ActivityResultContracts.StartIntentSenderForResult`。
2. **`PointerInputScope` 并不继承 `CoroutineScope`**（它只继承 `Density`）。  
   所以 `Modifier.pointerInput { ... }` 内部拿不到 `launch`，  
   要在里面启动协程必须自己从外部带一个 `rememberCoroutineScope()` 进来。
3. **`withTimeoutOrNull` 是 `AwaitPointerEventScope` 的成员方法**，  
   不是 `androidx.compose.ui.input.pointer` 包下的顶层函数，所以不能 import，直接调用即可。
4. **运行期 bug：在 Android 11~12 上申请 `READ_MEDIA_IMAGES` 不会有任何反应。**  
   这两个权限是 Android 13 才引入的，11~12 要申请的是 `READ_EXTERNAL_STORAGE`。  
   已抽出 `permissionsFor(kind)` 按系统版本分流。
5. **Media3 的 `PlayerView` / `AspectRatioFrameLayout` 标注了 `@UnstableApi`**，  
   不写 `@OptIn(UnstableApi::class)` 的话 Lint 会直接判错（不是警告）。
6. **`<adaptive-icon>` 必须放在 `mipmap-anydpi-v26`，不能放在无版本限定的 `mipmap-anydpi`。**  
   实测挪过去后 aapt2 会报 `resource mipmap/ic_launcher not found`，  
   而 Lint 恰恰会建议你"去掉多余的 v26 限定" —— 这条建议对自适应图标是错的，  
   已在 `app/build.gradle.kts` 里关掉 `ObsoleteSdkInt` 并附上原因。
7. **Android 14+ 的"选择部分照片"授权**：已声明 `READ_MEDIA_VISUAL_USER_SELECTED`，  
   用户只授权选中内容时应用依然可用（看到的范围小一些），而不是被直接拒绝。
8. **进度条从中间往两边长**：父容器用 `Alignment.Center` 只是想让 2dp 细线  
   在 26dp 触摸区里垂直居中，但 Compose 的 `contentAlignment` 是**两个轴一起作用**的，  
   于是填充条也被横向居中，看起来就像从中间展开。子元素需要单独 `.align(Alignment.CenterStart)`。  
   凡是用 `contentAlignment` 给子元素做单轴定位的地方，都要留意这个陷阱。

## 五、后续可以做的

按性价比排序：

1. **相似内容去重** —— 感知哈希（pHash / LSH）聚类连拍与重复下载。  
   「回留」的做法是 LSH 局部敏感哈希，6 万张秒级。这是目前最缺的一块。
2. **更多子分类** —— 自拍 / 录屏 / 动图 单独成组，机制和截屏分类一样。
3. **接 SAF 文件夹来源** —— 让下载目录里未入库的文件也能整理。  
   注意：这一块和现有架构有冲突（SAF 文件不能用 MediaStore 的受控删除，  
   也没有系统回收站），需要先设计好删除语义再动手。
4. **边看边标记"待删 / 保留"再看一轮** —— 对超大相册比逐条决定更省力。
5. **只看收藏流** —— 把收藏夹变成一个可以连续刷的 Tab。
6. **深浅色主题切换**。目前全站强制深色（沉浸式媒体应用的合理默认值）。

## 七、致谢

手势设计与产品思路来自王波粒关于「去留 linger」的公开设计思考：

- 照片用人们通常浏览照片的手势，视频用人们通常浏览视频的手势
- 拒绝 Tinder 式左滑删除 / 右滑保留 —— 照片整理不是二选一决策，  
  照片不管你也在相册里，逼用户逐张判断与心智不符
- 不用"还剩多少待处理"，只用"已完成多少"
- 随机顺序本身就是产品价值：顺序删除之所以枯燥，是因为下一张可以猜到

「回留」在 Android 侧先行验证了「抖音式上下滑 + 侧边按钮收藏/删除/分享」这套组合的可行性。

本项目是独立的 Android 实现，与上述两者没有代码或授权关系。
