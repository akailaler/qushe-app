## 1.3.40（★ 跳变 + 小方块，两个独立根因）

**用户给的线索是关键**："跳变的时机是捏到触发阈值那一刻" ✓

1. **跳变**：手势循环里 `lowerBound` 一开始是 `PINCH_TO_DATE_MIN_SCALE`(0.72)，
   而 `pinchTriggered` 一翻成 true 就变回 `1f` ⇒
   `coerceIn(1f, …)` 在**触发那一帧**把已经捏到 0.85 的照片**硬抬回 1.0** ⇒
   画面猛地弹大一下。而且飞入动效的起点是按 0.85 算的，两边还对不上。
   修：`val nextScale = if (pinchTriggered) scale else (scale * zoom).coerceIn(...)`
   —— **触发之后不再碰 scale**，停在触发时的大小交给飞入动效。
   ⇒ **教训：状态机切换时要检查"为旧状态算的约束"会不会在新状态下造成跳变。**

2. **"很小的方形块"= 提示胶囊的空壳**：
   `DecisionOverlay` 在 `decision == NONE` 时只把 label 变成空字符串，
   那个 `Row` **照样画** —— 底色 `Surface3` + 22×14 内边距、无图标无字
   ⇒ 屏幕上就是一个**深灰色小方块**。
   上滑删除回弹、捏合没够都会经过 `NONE`，平时被有内容的胶囊盖着
   ⇒ 用户"不确定什么时候出现" ✓ 全部对上。
   修：`if (decision == SwipeDecision.NONE && !isPinchHint) return`（整个不画）。
   ⇒ **教训："内容为空"不等于"不画"——带背景/内边距的容器会留下空壳。**

## 1.3.42（圆角修正 + ★ 跳变根因分析 + 收藏同步机制）

1. **圆角理解纠偏**：我做成"给黑底加圆角"，用户要的是"**去掉黑底、图片本身带圆角**"。
   黑底留着的话，照片平移时仍带着一整块方角暗色走
   （圆角只裁得住"这一层里画的东西"，那片底在视觉上是独立的一块）。
   修：`ZoomableImage` 那一层**完全不画背景**，露页面自己的黑底
   （`MediaPreviewOverlay` 根容器的 `background(Color.Black)`）—— 它不跟着照片动。

2. **★ 跳变根因（用户要求"先别动，多研究分析"）**：
   `DayViewScreen` 的 `enter`（整屏淡入）**在 `LaunchedEffect(Unit)` 里立即启动**，
   而 `items` 还在异步加载 —— **`items == null` 时那个分支画的是
   `CircularProgressIndicator` + "正在取这一天的照片…"，位置就在屏幕正中**。
   于是时间线是：
   ① 触发 → `enter` 从 0 涨，照片页的图被逐帧压暗；
   ② 同时**屏幕正中淡入一圈转动的进度环**（用户正盯着那儿看）；
   ③ `loadDayItems` 完成（100~500ms，`dayRadius=1` 三天范围更慢）→
      **转圈突然消失 + `DayFilmstrip` 组合 + 焦点格出现** ⇒ **亮度和内容同时突变**。
   **"跳变"的真身是那个加载转圈，不是飞行动效。**

   方案（待用户确认）：
   - **捏合到 ~50% 时就预加载**那天（`loadDayItems` 提前跑）⇒ 触发时数据已就绪；
   - **`enter` 等焦点格就绪再启动**（`introAnim.to != null`）兜底；
   - loading 分支**不要画在正中**（或干脆不画转圈）。

3. **收藏同步机制**（讲解，未改代码）：
   - **写**：`MediaStore.createFavoriteRequest(resolver, uris, favorite)`

   - **读**：查 `IS_FAVORITE = 1`（普通列，不需要授权框）。`systemFavoriteKeys()`

   - **反向同步可行**：查全库 `IS_FAVORITE = 1` 合并进本应用的 favorites 集合。
     注意厂商差异（拿不到就是空）、冲突策略（应用有而系统无的**不能自动删**）、
     时机（启动/打开收藏页/ContentObserver）。

## 1.3.42 之后：跳变根因（分析定案，未改代码）

用户报"捏到触发阈值那一刻跳变"。1.3.28/32/40/42 修的都是**别的**不连续点，
真正的根因有两个，都在 `DayViewScreen`：

1. **焦点格在 settle 期间整格 alpha=0**（`CellSlot.graphicsLayer`：`introTo == null` ⇒ `alpha=0f`）。
   `introTo` 要等"连续两帧读到同一矩形"才定格（`INTRO_SETTLE_FRAMES=20`），
   而进场定位本身也在逐帧推 scroll ⇒ settle 实际 3~20 帧（50~330ms）。
   这几帧里转圈已经没了、焦点格还没出现 ⇒ **用户刚捏小的那张照片"消失"了**。
2. **转圈 → 照片墙是一帧瞬间切换**（`when { loading||items==null -> spinner; else -> DayFilmstrip }`，无淡出）。

时间线：T0 触发 → items 约 20~80ms 到（`allImagesOnDay` 在 IO 线程，
adb 实测 3 天区间查询本身只要 ~15-30ms，12 万行全表扫描约 0.7s 但与本查询无关）
→ settle 50~330ms → 飞入 560ms。而 `enter` 淡入是 **一进页面就开始跑**（`LaunchedEffect(Unit)`），
560ms 就结束了 ⇒ 两条动画错位 100~400ms。

**修法（待用户确认）**：把 `enter` 绑到"焦点格可飞"（内容就绪门控，对应旧结论
"异步内容+立即启动的进场动画=亮度跳变"），并把 settle 的信号从"连续两帧相同矩形"
换成定位循环自己的 `positioned`（+1 帧）。转圈随之根本不会出现。

### adb 新发现（推翻旧结论）
- **`adb shell input` 这次是可用的**（KEYCODE_WAKEUP 把 Dozing→Awake 实证）。
  之前"被 HyperOS 拦"的结论需要重测。`input motionevent` 支持 `DOWN x1 y1 x2 y2`
  多指，理论上能注入捏合 —— 但本次真机在锁屏（NotificationShade），没法复现。
- `content query` 的列名要用 **`datetaken`**（`date_taken` 会报 Invalid column）；
  单次 `content` 调用有 **~1.05s 的 app_process 启动开销**，测查询耗时必须先用
  0 行查询把基线扣掉，否则结论全是错的。

## 1.3.44（已构建 + 已装机）

### 下滑返回修好：根因是"只判距离不判速度"
快速一甩手指在屏幕上没走多远就松手 ⇒ `dismissY >= 阈值` 判不出来 ⇒ 每次弹回去。
**滑动类手势的判据必须是"距离 或 速度"**（`VelocityTracker`），缺一半就有一半手势不响应。
另外两个隐患：`pointerInput(Unit)` 的闭包只在首帧捕获 ⇒ `var zoomed` 永远读到 false
（必须 `rememberUpdatedState`）；依赖布局结果的量（容器高度）不能放进这种固定键的闭包，
否则拿到的是首帧的 0 ⇒ 键里带 `boxHeightPx`。

### ★ "圆角没生效"多半是裁错了矩形
`ContentScale.Fit` 画在**整屏**盒子里时，圆角裁在整屏盒子上等于裁在黑边上。
正解：给 `ZoomableImage` 一个**只管几何**的 `clipAspect`，把变换层
`Modifier.aspectRatio(clip, matchHeightConstraintsFirst = true)` 缩到 Fit 后的真实矩形，
再 clip。**刻意和 `contentRatio` 分开** —— 后者还管缩放上限/拖动边界/解码尺寸，
推广到所有照片会连带改掉这三件事的行为（普通照片放大上限会从 8x 掉到"铺满即停"）。

### 垫底那层要"跟着拖动淡入"，不能常驻
顶层照片 Fit ⇒ 竖图上下留黑边 ⇒ 常驻的全屏垫底图会在黑边里露脸
（"第一张下面会有第二张"）。按 `max(|dx|,|dy|,dismissProgress*limit)` 淡入即可，
既保留防闪黑的底牌，又平时干净。
另外 `index+2` 那层和 `index+1` 位置尺寸完全一致、被整张盖住 ⇒ 纯浪费，已删。

## 1.3.45（已构建 + 已装机）

### ★ 淡出和位移绑在同一层 = 退场"卡一下"
`alpha = 1 - dismissY/阈值` 而退场要把 `dismissY` 涨到 `屏高*1.15`
⇒ 照片在动画前 20% 就淡没了，剩下 100+ms 屏幕全空。
正解**拆层**：黑底只淡出 / 照片只位移（不淡出）/ chrome 只淡出。
**chrome 必须画在照片之后**，否则返回键被整屏照片盖住点不到。
拆的时候顺手把 chrome 抽成独立 composable（需要 `BoxScope` 才有 `align`）。

### 收尾动画要"跟参照物用同一套参数"
用户参照的是整理页上滑删除，那就直接复用 `flingTo`（tween 200 FastOutLinearInEasing）
+ `spring(StiffnessMediumLow)`。默认 `spring()` 更硬，手感发木 —— 同类动画必须对齐。

### "随心所欲的自由滑动"多半是 rotation
`rotationZ = (offsetX / 80f).coerceIn(-8f, 8f)` 让照片横移时跟着歪。
pager 从不转图 ⇒ 用户要"完全按照轨迹"就是指去掉它。
同时补上速度线（`VelocityTracker`）：位移够 **或** 甩得够快都算翻页；
纯速度判定会把斜向上滑删除误判成翻页，横速那条要额外要求 `|x| > slop*2`。

### 教训：装饰性效果不要动布局基准
为了"圆角落在图片四角"而把变换层 `aspectRatio` 缩小，改变了整条链的尺寸基准
⇒ 用户看到"图片会自动放大"。**布局基准是别人的隐式依赖**，
装饰效果应该用"盖遮罩/画形状"这种不碰布局的做法。

## 1.3.46（已构建 + 已装机）

### ★ 圆角的最终解法：不碰布局的"盖遮罩"
三次尝试：① 裁整屏变换层 → 裁到黑边；② `aspectRatio` 缩到图片真实矩形再 clip
→ 圆角准了但**布局基准变了、用户看到"自动放大"**；③ **在图之上、变换层之内画四条角路径**
（每条 = 角上方块 − 四分之一圆，填页面底色）→ 圆角准、跟着缩放平移、布局零改动。
**只画四个角、不画"图片以外整片"** —— 后者会把黑边也填上，挡住正在淡入的下一张。

### ★ "拖一点点顿住" = 增量式 snapTo 会丢帧
`snapTo(currentValue + delta)` 读的是挂起写出来的当前值，每帧 `launch` 一次；
后一次取消前一次时那一段增量就丢了。正解：**手势内本地累加、每次写绝对值**。
（`DraggablePhoto` 和 `DayZoomView` 的下滑都有这个隐患。）

### 轴锁定顺带简化了判定
越过 touchSlop 时按主方向定死轴 ⇒ 位移向量恒有一分量为 0 ⇒ 判定只看那一个轴，
不会"斜着划同时命中翻页和删除"，也少一次比大小猜方向。

### 反向同步系统收藏
`allSystemFavoriteKeys()` = 两个 collection 各查 `IS_FAVORITE = 1`，
映射成 `storeKey`（`id*2 + 是否视频`）。`importSystemFavorites` **只加不删**，

## 1.3.47（已构建 + 已装机）

### 垫底"下一张"：淡入阈值太小 ⇒ 改成真翻页
淡入 alpha 绑在"翻页判定线"的 18% 上，而判定线只有 72dp ⇒ 手指走十几像素
下一张就整个糊上来（用户报"稍微滑一下就立刻呈现"）。
正解 = **停在旁边一整屏 + 和当前这张同速移动**（`translationX = dx - dir*屏宽`）：
静止时在屏幕外、拖动时滑进来、回弹时滑回去、翻页成立时正好归位。
配套：出场目标从 1.3 屏改成**正好 1 屏**（甩过头会把下一张带过 0.3 屏）。
纵向不是翻页，仍淡入，阈值放宽到 1.2 行程。

### 圆角统一：值统一，手法按载体分两种
`rememberContentCorner()` = 屏宽 × 2.3%、上限 14dp ⇒ 全 App 唯一来源。
- **格子**（瀑布流 / 收藏 / 喜欢 / 回收站）：`clip(rememberContentShape())`
  —— 格子本身就是那个矩形，clip 最便宜
- **大图**（整理页 / 瀑布流放大 / 三处预览）：四角**遮罩路径**
  —— Fit 画在整屏盒子里，clip 整屏只会裁到黑边

`swipeUpDeletes=false` 时上滑只弹提示、什么都不做。

## 1.3.48（已构建 + 已装机）

### ★ "比 pager 突兀"的根因：tween 是定时的，spring 才继承速度
出场用 `tween(200ms 走完一整屏)` = 5400px/s 恒定；而翻页判定线只有 72dp，
轻扫时手指可能只有 1000px/s ⇒ **松手瞬间速度跳 5 倍**。
换成 `spring(StiffnessMediumLow)`（`PagerDefaults` 同款）后，
`Animatable.animateTo` 会把它自己记录的当前速度当弹簧初速度 ⇒ 速度连续。
**语义决定用哪个**：翻页要"接住手指"用 spring；删除是"扔掉"用 tween。

### 会骗人的设置项直接删
「上滑画面做什么」的 FAVORITE 分支从来没调用 `onDecision` ⇒ 关掉时上滑只弹提示、
什么都不做。**选项存在但选中它就失效 = 比没有更糟**。偏好值保留（老配置读得出）。

### 跨页复用组件时，起点必须"实测"不能"估"
收藏/喜欢页的预览里，照片被 pager 平移过还带居中偏移；
用容器尺寸估起点会有偏差，而飞行动画第一帧就看得出来 ⇒ 用 `boundsInWindow()`。

### startDaySession：按那天开一组不随机抽
从收藏捏进「回到那天」再点 ✓，要的是"那天的全貌"，随机抽会毁掉这个前提。

## 1.3.54（已构建 + 已装机 + 已入库）

### ★★ "只收不回来"= 两个写者轮流写同一个 state
1.3.53 把 `onZoomedChange` 改成无条件 `chromeVisible = !isZoomed`，
而 `ZoomableImage` **每次手势结束都报一次** ⇒ 1x 下单击时

否则调用方要自己判重）。整理页的 `chromeHidden = isZoomed` 同步受益。

### ★ 优化手段本身可能成为新的卡顿源
`beyondViewportPageCount = 1` 减轻了"滑过去那一帧"的组合压力，

## 1.3.59（已构建 + 已装机 + 已入库）

### ★ 父节点抢手势，子节点的"放大后拖动"就废了

## 1.3.60（已构建 + 已装机 + 已入库）

### ★★ pointerInput 闭包捕获：换 key 也救不了，要 rememberUpdatedState
1.3.59 给 `DraggablePhoto` 加了"放大态放行单指"，`if (zoomed)` 直读参数 ——
而 `pointerInput(item.storeKey())` 的闭包**只在换照片时重启**，
读到的永远是**首次组合的 false** ⇒ 那段代码从没执行，长图放大后照旧拖不动。
**通则：只要闭包里要读"会变的值"，一律 `rememberUpdatedState` 转发；
把值放进 pointerInput 的 key 只能覆盖"偶尔重启"的情况，
而 key 不变时（换 key 才重启）根本救不了。**
`onTap` 同病。

### 两个开关 ≠ 一个功能
`chromeHidden`（图标）与 `filmstripVisible`（胶片条）原本各自为政，
单击只动一边 ⇒ 用户看到"没反应"。**同一件"想安静看图/想看全貌"的事，
应该由一个开关统一驱动**，而不是两个半联动。

### 挂 onSingleTap 的东西在有双击判定时会变慢
`detectTapsWithoutConsuming` 注册了 `onDoubleTap` 后，`onTap` 必然延后 280ms。
要"松手当帧响应"的单击，只能放在父层"没拖过"分支里。

## 1.3.61（已构建 + 已装机 + 已入库）

### ★ 长图放不大：snapScale 的 cover 在"1x 已铺满"时算成 1
`snapScale = 容器 / Fit后绘制区`。长图 Fit 之后宽=容器宽、高=容器高
⇒ coverW = coverH = 1 ⇒ 上限 1x ⇒ 捏合被 `coerceIn(1,1)` 夹住、
**永远进不了 `scale > 1.01` 的拖动分支**。收藏页能拖是因为它**不传 contentRatio**。
**兜底：`cover < 1.02`（1x 就铺满）时回落到 `maxScale`** ——
"吸边界"是"别放大到看不清"，而长图放大 2~3x 正是看细节**需要的**。
**教训：同一个现象可能有两个原因（父节点抢手势 + 上限算错），修一个不等于修好。**

### 两个 weight(1f) 不等于居中
`Row { 内容A; Spacer(weight 1f); 标题; Spacer(weight 1f); 内容B }`
只保证"扣掉 A、B 之后的剩余空间"居中。A=48dp、B 宽度随数字变 ⇒ 标题偏。
**要真正居中：A 和 B 各自套一个等宽的 `Box`。**

## 1.3.62（已构建 + 已装机 + 已入库）

### ★ 长图拖不动：contentRatio 把"吸边界"算成了"宽度铺满"
传 `contentRatio` ⇒ `snapScale = 容器 / Fit后绘制区`。长图 Fit 之后宽高都贴着容器
⇒ cover 只取到 1~1.25 ⇒ **上限只有一两倍**；而上限正好等于"宽度铺满"时，
横向 `panLimit = 0`、纵向余量也只剩几百 px ⇒ 表现为"被锁死"。
**收藏页能拖是因为它不传 `contentRatio`。** ⇒ 长图也不传（上限回 `maxScale`，
边界用宽松估计，代价是可能拖出一丁点黑边）。
**教训：精确的边界估计不等于更好的体验 —— 它可能把功能锁死。**
同一个现象（长图拖不动）我连着查了三轮，前两轮都只修了一半。

### 状态机不能用"投影"当指针
三态循环里拿 `filmstripVisible` 当前值推下一态，而状态①和③在这个变量上**取值相同**
⇒ ③ 之后点一下会算成去②、回不到①。**必须自己记 stage。**

### 单击 + 双击共存：交给有双击判定的那一层
`DraggableImage.detectTapsWithoutConsuming` 内置"延后 280ms 等第二击、双击取消单击"。
把单击放在父层"没拖过"分支里虽然"松手当帧"，但**每次双击都会先切再切回**（抖一下）。
用户要的就是前者那种语义。

## 1.3.63（已构建 + 已装机 + 已入库）

### ★ 出场动画的时长 = 换页的等待时间
`onDecision` 在 `coroutineScope { 两个动画 }` **之后**才换 `index`
（换早了照片会瞬移回正中 ⇒ 跳变）。于是 `settleToPage` 走完一整屏要多久，
用户就得等多久。`StiffnessMediumLow` = 400~600ms，单次滑动看不出来，
**连续滑动就变成"滑一张要等一下"**。
改成 `StiffnessMedium` + `visibilityThreshold = 24px`（仍是弹簧，速度连续）→ ~300ms。
**通则：任何"动画跑完才 commit 状态"的设计，动画时长就是用户的感知延迟。**

### 手势本地累加值的起点必须是当前值，不能是 0
新一次手势里 `var dragX = 0f`，而上一段翻页动画可能还在跑、`offsetX.value` 已 -800
⇒ 第一次 `snapTo(0+10)` 把照片从 -800 **瞬间拽回 -10**（"跳了一下"）。
正解：`var dragX = offsetX.value` 作基准。
