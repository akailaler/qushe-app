## 优先级 1：视频闪烁 / 残留（「取舍」1.0.36 状态）

**当前状态**：1.0.36 已打包，编译与 Lint 全绿。
**两个现象是一组取舍，不是没修完的 bug：**

| 做法 | 结果 |
|---|---|
| 每页常驻挂载播放器 | 不闪，但离屏页留下旧帧（画面正中一块上一个视频，**且是上一个视频的尺寸**） |
| **只挂当前页**（1.0.36 现状） | 没有残留，但视图随页面建/毁 → 轻微闪 |

**已排除的原因（别再重复排查）**
- ❌ 不是 SurfaceView 合成问题（1.0.22 已换 TextureView）
- ❌ 不是首帧未渲染 / 缩略图未预载（1.0.10 已加 `onRenderedFirstFrame` + `beyondViewportPageCount`）
- ❌ 不是宽高比未定时的填满帧（1.0.32 已加 `firstFrameReady` 门控，**用户确认已解决**）
- ⚠️ `AndroidView.update` **不是响应式的**，只在重组时执行 ——
  **绝不要在那里设 `visibility`**（1.0.33 踩过：画面被首图盖住、声音还在走）。
  显隐一律用 `graphicsLayer { alpha = ... }`（带 lambda 的，绘制时读状态）。

**推荐解法：屏幕级单视图（抖音那条路的简化版）**
把 PlayerView 提到**屏幕级**（不放进 pager 的页里），全局只有一份，永不建/毁；
位置/尺寸跟着 `pagerState.currentPage` + `currentPageOffsetFraction` 走。
→ 没有建/毁 = 不闪；没有离屏副本 = 不残留。两个问题一起消失。

关键词位置：
- 视频页 `ui/video/VideoSessionScreen.kt` — `VideoPage` 里的 AndroidView、
  `playerVisible`、屏幕级的 `player` 与 `firstFrameReady`
- 预览页 `ui/common/MediaPreviewOverlay.kt` — 同构，Dialog 里也有一个 Pager

## 2. 预览页顶栏/底栏"被挡住一半、太显眼" ✓

**根因**：宿主 `MainActivity` 开了 `enableEdgeToEdge()`，但 Compose `Dialog`
的窗口默认仍是 `decorFitsSystemWindows = true`。这种"半个 edge-to-edge"状态下
`statusBarsPadding()` 读到的 insets 是 0（或只有一部分），顶栏就紧贴屏幕顶边
被状态栏压住 —— 正是"被挡住一半"。

**修法**：`DialogProperties(usePlatformDefaultWidth = false,
decorFitsSystemWindows = false)`，显式关掉它。

**降视觉重量**：顶栏渐变 `0xD9000000 → 0x99000000`，关闭图标 `TextPrimary → TextSecondary`，
计数 `bodyMedium/TextSecondary → labelMedium/TextTertiary`，内外边距一起收紧。
浏览场景里这两条栏只需要"找得到"。

Column { Row { FilmstripRow(weight 1f); Spacer(width); FilmstripRow(weight 1f) } }

## 第 5 版实现要点

**布局（`DayFilmstrip`）**：
- `Column { FilmstripRow(weight 1f); Spacer(ROW_GAP); FilmstripRow(weight 1f); DayScrubber }`
- `FilmstripRow` 用 `BoxWithConstraints` 拿实际高度 → `cellHeight = maxHeight - VERTICAL_PAD*2`，

- **正中间一根固定绿色指针**（2dp 宽、30dp 高），刻度在它下面平移；
- 靠近指针的刻度**更高更绿**（18dp vs 11dp），形成聚焦层次；
- `pointerInput` **按手指位置**驱动（`seek(x) = x/width * maxPos`），拖动时 `dragging` 状态；
- 下方一行「共 N 张」。
- **为什么用 Canvas 而不是摆一堆 Box**：一天可能几百张，摆 Box 会在拖动时反复组合/布局。

## ★ 核心技术决定：两条带子共用**同一个 `ScrollState`**

上一版两条 `LazyListState` 各管各的 → 各滑各的、速度还不一样。
这一版改成：**两条带子由同一个 `scroll` 驱动**，各自用一个
`Row` + `horizontalScroll(scroll)`。因为"滑到哪"只有一份数据，
**想不同步都做不到**；而且拖动直接改这一个偏移量，没有跨列表同步损耗
（这也是"左右不好滑"的根因 —— 原来两条列表在抢同一个手势）。

- 两端各垫 `maxWidth / 2` 的 `Spacer`，首尾两张能滑到屏幕正中（等同
  原来 `contentPadding` 半视口的效果）。
- 初次定位：`LaunchedEffect(focusIndex)` 里按 `focusIndex/2 * 估算格宽`
  直接 `scrollTo`。估算值不准没关系，用户随即会自己微调。

## ★ 「保留图片比例」的正确做法

第 5 版**固定行高、只让宽度变** → 比例其实被压扁了（竖图变"矮胖"）。
正确做法：**宽高比严格等于原图**。
```
widthAtRowHeight = rowHeight * ratio
若 > CELL_MAX_WIDTH → cellW = CELL_MAX_WIDTH, cellH = CELL_MAX_WIDTH / ratio
否则               → cellW = widthAtRowHeight(≥ CELL_MIN_WIDTH), cellH = rowHeight
```
竖图顶到行高、超宽横图顶到最大宽度，两者都保持原比例。

## ★ 刻度条「背景在动」的根因

用户说"背景不动、刻度条在背景上滑动" —— 根因是**刻度层带了可见的底色**，
看起来就像一整块背景在平移。改法：
- `Ticks` 的 `Canvas` **只画刻度线，不画任何背景色**；
- 固定的绿色指针**不放在 Canvas 里**（在 Canvas 之上的一层独立 `Box`），
  所以它绝对不动，刻度从它下面过；
- 另外给运动加上了"实时跟随"：`settledFraction` 由
  `scroll.value / scroll.maxValue` 推导（`derivedStateOf`），
  滑带子时刻度同步走；拖动中则用 `draggingFraction`。

# ★ 第八次会话：1.2.1 内第 7 版（自己发现的隐患，主动补）

用户第六轮四条反馈已交付并装机。本轮**没有新的用户反馈**，
而是把两个"用户一上手就会撞到"的结构性隐患提前处理掉：

## ★ 隐患：`Row` 全量组合 = 一天几百张必卡

第 6 版为了让两排共用同一个 `ScrollState`（"天生同步"），
用的是 `Row` + `horizontalScroll`。代价是**一次性组合整排的全部格子** ——
一天几百张就是几百个 `AsyncImage` 同时挂上去，首次进入必卡。

**为什么不能直接换 `LazyRow`：**
`LazyListState` 是每个列表自己的、不共享。真用两个 `LazyRow`，
就得一边滚一边把位置镜像给另一边，一帧的延迟在快速滑动时肉眼可见 ——
这正是第 5 版"两排各滑各的"的另一种翻版。

**最终做法：保留共用 `ScrollState`，手动做可见区间裁剪。**
- 先用纯函数 `cellWidthDp(item, rowHeight)` 把**每个**格子的宽度算出来
  （和真实布局用同一套算法，两边不一致整排会越滚越歪）；
- `visibleRange` 由 `derivedStateOf { scroll.value }` 推导：
  只有落在 `[scroll.value - 1屏, scroll.value + 2屏]` 的格子才真正组合；
- 区间外用**等宽 `Spacer`** 占位 —— 总宽度、每个格子的位置全都不变，
  滚动条 / 刻度条 / 两排对齐照旧，只是屏幕外的不再组合图片。

**注意**：估算里没算两端垫的 `halfViewport`，区间整体偏半个视口；
但窗口左右各留了一整屏余量，半个视口的偏差被完全覆盖，不会露出空白。

## ★★ 最重要的一条：指针拦截的方向判别

**上一版的 bug**：为了挡住下层照片的拖拽，`DayViewScreen` 顶层那个
`pointerInput` 在 down 之后**把后续每一个事件都 consume 掉**。
结果连带把两排带子的横滑也吃掉了 —— 用户只能靠底部刻度条拖动。
（这正是"你放了 WebSocket 但没人订阅"那一类错误：**保护过度，把正常的功能也挡在外面**。）

**改法：按本帧位移的主方向决定谁拿。**
```kotlin
val dx = abs(change.position.x - lastX)
val dy = abs(change.position.y - lastY)
if (decided == null && (dx > 3f || dy > 3f)) decided = dy >= dx
if (decided == true && change.pressed) change.consume()   // 竖直 → 上层拦
                                                          // 水平 → 放行给带子
```
**必须在 `PointerEventPass.Initial` 阶段判断**（`awaitPointerEvent(PointerEventPass.Initial)`）：
- 指针事件的顺序是：**父 Initial → 子节点 → 父 Final**；
- 如果在 Final 才消费，子节点（`horizontalScroll`）早就把横向拖拽收走了，等于没拦住竖直的。
- 阈值 3px 是为了让"单指按下还没动"不被判成手势，避免吞掉点击。

## ★ 进场定位：从估算改成真实测量

原来：`scroll.scrollTo(focusIndex / 2 * (估算120px + 11px))` —— 写死的平均宽度。
**一天里横图竖图混着，平均宽度这个假设偏差很大**，用户看到的就是"没对准"。

现在：`FilmstripRow` 新增 `onLayout` 回调，上报
**每个格子左侧的累计偏移 `FloatArray`** + 视口宽度（px）。
外层据此算出目标格位置后 `scroll.scrollTo(left - viewportPx / 2)`，把它推到正中。
- 回调要套 `rememberUpdatedState` —— 每次重组都是新 lambda，不套会成为 effect 的依赖把定位反复触发；
- 累计偏移要**加上左端垫的半个视口**（`halfViewport.toPx()`）；
- 用 `located` 标志保证**只定位一次**，用户随后滑走了不会被重新拽回去。

## ★ 刻度条：「刻度不动、指针动」

推翻上一轮的形态（上一轮是"指针固定、整排刻度平移"）。
用户的说法更准：**刻度是标尺（位置绝对、不动），指针是读数**。
标尺跟着手指跑会让人失去"一共多长"的稳定参照 ——
和更早那次"背景在刻度条上滑动"的抱怨是**同一个病根：参照物不该动**。

实现要点：
- `Ticks()` 不再接收 `fraction`，静止平铺短竖线（间距 8dp），**不带任何底色**；
- 指针：`BoxWithConstraints` 里 `.offset(x = 14.dp + usable * fraction)`，3dp × 26dp 绿色；
- 轨道两端各留 **14dp 内边距**，指针不会贴到屏幕边缘；
- 拖动手势的热区是**整条轨道**，不要求精确点中那根 3dp 的针 —— 细指针太难抓了；
- `seek()` 的坐标映射要和指针的 `offset` **用同一套 inset**，否则手指位置和针位置对不上。

# ★ 第十次会话：**1.2.3**（上滑删除 + 两个视频预览修正）

## ★ 需求 1：瀑布流上滑删除（最难的一条）

**踩到的第一个坑：手势被上一轮的自己挡住了。**
上一轮为了"水平放行给带子、竖直拦住下层"，我在顶层 `pointerInput` 的
**Initial 阶段**做方向判别并消费竖直事件 —— 结果这一版加上 DayCell 的
上滑手势时，**父节点在 Initial 就抢先吃掉了，子节点根本没看到**。

改法（最终的手势分工）：
- **DayCell 的 `pointerInput`** 认领"竖直向上" → 触发删除，并 `consume()`；
- **两排的 `horizontalScroll`** 认领"水平"；
- **顶层 `pointerInput` 改为 `PointerEventPass.Final` 兜底**：
  `if (!change.isConsumed) change.consume()`。
  三个 pass 顺序是 Initial → Main → Final，到 Final 时能准确看出
  "这个事件到底有没有人要"，没人的事件一律吃掉 ——
  **兜底不能省**：Hit-test 链会一路走到被盖住的整理界面，
  它上面的 `detectDragGestures` 会认领竖直拖拽，于是空白区域一划下面照片就飞走。

写成三条口诀：**谁先 child 谁优先，父只做 Final 兜底；
识别了才 consume，方向不对就撒手。**

**踩到的第二个坑：`Arrangement.spacedBy` 的间距不属于格子。**
用它排格子时，某一格删除后宽度收到 0，**那段 gap 还留在原位**，
后面的照片补过来时会缺一截、补不满。
改法：**间距改为每个格子自己带的尾 padding**（新增 `CellSlot` 组件），
`removed` 时 `width` 和 `padding(end)` 一起变 0 → `animateContentSize` 平滑收起，
连带间距一起消失，填补才是真正无缝的。

**刻意不做跨排重排**：原来的布局是"偶数索引上排、奇数下排"，
一旦从 items 里真的移除某项，奇偶全乱、整屏照片重新站位 ——
那是一次不必要的视觉地震。所以 items 保持不动，只用 `markedKeys`
控制"界面上不再出现"，**只在同排内填补**。这也正好贴合"标记删除"的语义
（真正的删文件仍在退出时统一走系统弹窗）。

## ★ 需求 2：竖屏视频长出「全屏观看」按钮

**根因不是判断写错，是依据本身不可靠。**
原来：`MediaPreviewOverlay` 里用 `current.width > current.height` 判断是否横屏。
但 **MediaStore 的 `WIDTH / HEIGHT` 记的是"编码存储的尺寸"，不带 rotation** ——
手机竖着拍、按横幅格式存（再靠 rotation 元数据转回来）的视频，
列里是 1920×1080，于是**竖屏视频被误判成横屏**。这就解释了"偶发"：
只有这类编码方式的视频才会出错。

修法：**优先用播放器解码出来的真实 `videoSize`**（`onVideoSizeChanged`），
它一定已经把 rotation 算进去了；播放器尚未就绪时才退回 MediaStore 初判。
胶囊位置也改用解码尺寸计算，避免就绪瞬间位置跳一下。

## ★ 需求 3：预览视频播放时收起左下角信息

`MediaPreviewOverlay` 底栏：视频在播 → 文件名 / 日期 / 大小淡出；
暂停或照片 → 淡入。**用淡入淡出而不是显隐**：空间仍然保留，
进度条位置不会上下跳（跟着内容蹦的那一下很廉价）。

3. **`CellSlot` 去掉 `animateContentSize`**，改 `Animatable` 显式驱动收缩，

4. 进场定位从外层 `onLayout` 回调**内移**进 `FilmstripRow`，
   键用 `scroll.maxValue`（快照状态，反汇编证实）—— 首次布局前 maxValue=0

5. 下排 `focusItem = null`（两条带子共用一个 scroll，都定位会互相覆盖）；
6. `DayCell` 去掉 `removed` 参数（被标记的格子根本不会组合到这里）。

## ★ 「回到那天」直接左右滑失效（1.2.2 起就存在，未修完）

**历史澄清**：用户说"横滑手感不错"指的是 **1.2.1 的 LazyRow 版**；
1.2.2 改成两条带子共用 `ScrollState` + Row/horizontalScroll 之后，
用户当轮反馈就是"想直接滑，不想必须用刻度条"—— 也就是说
**直接横滑从共用 ScrollState 那一版起就没真正好用过**，用户后来基本靠刻度条。

**本轮静态排查（全部反汇编验证，结论是"理论上应该能滑"）**：
- `ScrollingLayoutNode.measure`：横向 scrollable 给子节点 **maxWidth=Integer.MAX_VALUE**
  → Row 内容可以是全宽 → maxValue 必然 >0（"maxValue=0 所以不能滑"的假设被证伪）；
- `awaitTouchSlopOrCancellation` 读 **Main** pass、遇消费即取消；顶层 Final 兜底
  消费者发生在 Main 之后，**不阻断** horizontalScroll（再次证实此前的结论）；
- `detectTapAndPress`（clickable 的手势）主体 **零 consume 调用**，不会吃掉拖拽；
- DayCell 的 pointerInput 横向分支 `return@awaitEachGesture` 前不消费；
- `currentPageOffsetFraction` 公式 = (snap位置 - 当前页offset)/pageSize，

# ★ 第十九次会话：**1.3.3**（换掉内建滑动手势 + 回收站网格 + 图标圆按钮 + 单张圆角卡片）

## ★ 1. 「滑不动」的根治：换掉内建 scrollable 的手势

用户描述的新症状是决定性的：**"隔一会儿又可以划一下，然后又滑不动了"** ——
间歇性、可恢复。这与"格子抢先消费导致 slop 检测被取消"完全吻合：
横滑起手只要带一点向上分量，格子（Main pass 先于父级）就先 `consume()` 掉，
内建 scrollable 的 `awaitTouchSlopOrCancellation` 一看到已消费就**取消整次拖拽**。

**改法（在 FilmstripRow 的 Row 上）**：
- **保留 `.horizontalScroll(...)`** —— 它仍然负责"给子节点无界宽度 + 裁剪"这两件事；
- **在它外面（更靠父级）加自己的 `.pointerInput`**，方向判定跑在 **`PointerEventPass.Initial`**
  —— 父级先于子节点拿到事件，判成横向当场 `consume()` 认领，判成竖直立刻 `return`
  把整串事件让给格子的上滑手势；
- 滚动**走 `scroll.dispatchRawDelta(-dx)`** —— 不经过 Mutex，任何时刻按下都立刻跟手；
- 松手惯性用投影 + `animateScrollTo`（放在 `scope.launch` 里，job 存 state），
  **新手势一按下就先 cancel 上一次惯性**。

**这条改动的通用结论：父级要认领某一方向的手势时，必须在 Initial pass 判方向 +
consume；只判不 consume（或判在 Main）都会被子节点抢先。**（和早期的教训 14 一致，
那次是"父不要在 Initial 抢所有事件"，这次是"父要抢就抢一个方向、且必须在 Initial"。）

## 2. 回收站改成缩略图墙

# ★ 第二十五次会话：**1.3.9**（跟手第二轮：让格子可跳过重组）

版本 **57 / 1.3.9**，已装机。

## 机理回顾（为什么之前"不跟手"）

可见区间跨格边界平移时，那一整排几十个格子的函数体全部重跑 ——
因为格子的参数里有 `MediaItem`（带 `Uri`，编译器判为不稳定）⇒ **整个格子不可跳过**。

## 改法：两个稳定类型替掉不稳定参数

```kotlin
@Immutable class DayCellUi(uri, kind, durationMillis, storeKey, ratio)
@Stable    class DayCellActions(pick, markDelete, markFavorite, favorite)
```

- **`DayCellUi`** 抽走 `MediaItem`：格子只认这几个字段；
- **`DayCellActions`** 把回调与收藏查询**包成 `@Stable` 的类** ——
  关键是"参数类型稳定"就够了，里面 lambda 捕获了什么（`AppContainer` 之类）无关紧要；
- 回调参数一律换成 `storeKey` / 序号，不再搬不稳定对象；
- 两个对象都在 `DayFilmstrip` 里用 `remember(items)` 建一次 ⇒
  **同一格在两次重组之间拿到的是同一个实例**，`equals` 成立 ⇒ 可跳过 ✓。

**为什么用普通 class 而不是 data class**：跳过判定靠 `equals`，
而实例本身是 remember 的（同一个对象）⇒ 默认的**同一性相等**就够，
不必再为逐字段比较付出代价。

## 链路改动

`DayFilmstrip` 建 `cells` / `actions`（新增）→ `FilmstripRow(cells, actions)` →
`CellSlot(cell, index, actions)` → `DayCell(cell, index, actions)`；
`DayViewScreen` 的对外 API **没变**（原始回调仍在它那一层）。

`@Immutable` / `@Stable` 在 `androidx.compose.runtime`，`Uri` 在 `android.net.Uri`
（漏导入各踩一次）。

一停下来就直接戛然而止"。

**病因**：上一版的惯性只是"投影 0.13 秒 + 动画"，等于松手就停。
**改法**：按 iOS `UIScrollView` 的减速率做**指数衰减滑行** ——
速度每毫秒 ×0.998（`decelerationRate = .normal`），
每帧算这一帧该走的位移、直接 `dispatchRawDelta` 进去
（不吃 Mutex、不经过动画 ⇒ 随时按下都能立刻接住，`flingJob` 在按下时 cancel）。
掉帧时按真实帧间隔补位移（`withFrameNanos` 拿时间戳），不会把速度算成固定 16ms。
阈值：|v| > 200px/s 才启动，衰减到 60px/s 收手。

## 2. "滑动时小图加载迟缓"的根因：**没给 Coil 尺寸提示**

`AsyncImage(model = uri)` 不给 size 时，Coil 按**原图分辨率**解码 ——
一张 4000×3000 的照片就是 48MB 位图，滑过每张都解一次这么大的图。
**改法**：在 `DayCell` 里用 `ImageRequest.Builder(...).size(wPx, hPx).build()`，
尺寸取单元格的像素尺寸（wPx 由行高 × 宽高比推出，**不用动画中的宽度**，
否则收缩动画每帧都会重建请求）。key 用 `(uri, cellH, density)`，稳定不churn。

**同类位置（还没做）**：收藏/喜欢页网格、回收站网格、整理页底部胶片条 ——
都是 `AsyncImage(model = uri)`，同样受益于加 size 提示。

## 3. 图标改成标准字形（用户贴了截屏）

上一版两个图标是手绘描边（一段弧 + 几条线），放大看是**残缺的半成品**
（"有点不够完整，不好看"）。现在：
- `RecenterIcon` = Material **refresh** 的实心字形（带缺口的圆环 + 箭头）；
- `UndoIcon` = Material **undo** 的实心回弯箭头。
实心字形没有描边断口，小尺寸下干净。

**教训：自绘图标要用"实心字形"的路子（直接抄 Material 的标准 path），
不要用描边拼 —— 描边在小尺寸和圆头笔画下很容易显得残缺。**
