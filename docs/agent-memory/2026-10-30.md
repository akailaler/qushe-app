### ★ 限频的真正根因（最值钱的一条）

`backup_task_interval`（默认 3 秒）**只间隔"页"请求**。但一页 20 条微博里，
带长文或转发了别人的微博的，每条都要再发一次 `statuses_show` 取全文 ——
**这些请求是背靠背发的**，没有任何间隔。日志里能直接看到：撞墙前连续十几次
`statuses_show` 418，然后 `profile_statuses` 也 418。
⇒ **真实速率是设想的数倍**，所以 149 位只能跑 40 位。

修法：`weiback/src/api/rate_gate.rs` —— **所有请求共用一道节流闸**
（static `LAST_REQUEST: Mutex<Option<Instant>>` + `GAP_MS: AtomicU64`，
基础 700ms，被 418/429 后 ×1.5 放宽、上限 5s、本会话不收窄）。
⚠️ **判限频只能看错误文本**：SDK 错误类型不是我们的 `Error`，
状态码只在 `to_string()` 里（"HTTP status client error (418 I'm a teapot)"），
所以 api 层用 `rate_gate::looks_throttled(text)`，我们自己的 `Error::is_rate_limited()`
留给上层。

### new 角标时有时无

`recent_new_posts` **在每个任务开始时被整表清空** ⇒ 跑完备份再跑一次清理/导出，
角标就没了。改成**只 prune 3 天前的记录**（`prune_recent_new`）。
角标定义同时改为与「今天更新」一致（今天 0 点后入库的才算）。

### 筛选
- 「仅看更新」→「今天更新」/「昨天更新」，按**下载时间**（`recent_new_posts.added_at`）
- `PostQuery.only_new: bool` → `added_from` / `added_to`（Unix 秒）
- SQL 用 `CAST(strftime('%s', added_at) AS INTEGER)` 比对 epoch，
  **避开 RFC3339 文本格式差异**（后端 `+00:00` vs 前端 `toISOString()` 的 `Z`）
  ——字符串直接比会错

## ★★★ 2.11.0（commit 769fed0）—— 三个"我自己造成的"坑，比功能本身更值得记

### 坑 1：同步脚本漏目录 ⇒ 2.8.0–2.10.0 的安装包「导出 HTML」全坏

构建目录 `C:\wb-build` 是从源仓库拷的，我**只拷了 `weiback/src/` 和 `weiback/migrations/`**，
**从来没拷 `weiback/templates/`**。模板在 2.4.0 就修好了（Tera 2.x 不认 `is object`
改成 `is defined`），但构建目录那份是旧的 ⇒ 那几个安装包一导出就报
`Unknown test 'object'`。**单测在源目录是绿的、在构建目录是红的**，就是这个信号。

⇒ 新增 `sync-build.sh`：**整目录同步 + 删源已删文件 + 逐目录 diff 校验**，
少一个目录就报错。**规则：拷目录，不拷手挑的子树。**

### 坑 2：`cmd | tail -N` 吞掉失败码 ⇒ 旧前端被打进安装包

`npx vite build 2>&1 | tail -3` 的退出码是 **tail 的 0**，前端构建失败我完全看不见，
于是 `tauri build` 拿着**上一版的 dist** 打了包。
⇒ 新增 `build-installer.sh`：全程 `set -euo pipefail`，**任何管道都不接构建命令**。

### 坑 3：桌面端 safe-delete shim 按"轮次"累计计数

- 单轮删除 >50 个文件 → `SAFE_DELETE_BULK_CONFIRM_REQUIRED`
- **分批没用**（同一轮里所有删除加起来算），必须分轮
- `vite build` 清空 `dist` 就是删 116 个文件 → 必挂
- 解法：**把旧 dist 移走**（`mv dist dist.old.<时间戳>`），
  目标名**必须带时间戳**：`mv dist dist.old` 在 dist.old 已存在时会**合并**进去，
  旧文件还在 → vite 照样失败

### 坑 4：cargo 静默挂十几分钟

`weibosdk-rs` 是 **git 依赖**，cargo 会尝试刷新 github.com，本网络不通 →
build 卡住十几分钟无输出。⇒ 构建脚本加 **`CARGO_NET_OFFLINE=true`**。

## ★★★ 构建 Rust 时的终极坑（花了 3 小时，记死）

**症状**：改完 Rust 代码要重新打包，`cargo build` 就在 aws-lc-sys 上
**卡住不动**：CPU 0%、对象文件数不变（283）、半小时不报错也不结束。

**根因链**：
1. Git Bash（MSYS）会把 export 的 `INCLUDE` 里的 Windows 路径改写：
   `C:\Program Files (x86)\Microsoft...` → `C://Program Files (x86)//Microsoft...`
   ⇒ cl.exe **找不到 stdint.h**，link.exe **找不到 kernel32.lib**
2. 本来想用 `vcvars64.bat` 解决，但**它调用 reg.exe，被桌面端安全策略拦截**
   （"PROGRAM BLOCKED BY SECURITY POLICY"）⇒ INCLUDE/LIB 根本没设上
3. C 编译失败时，cargo 的 build script 卡在读子进程管道上
   ⇒ 表现为"卡死"而不是"报错"

**解法**（`build-installer.cmd`，纯 ASCII）：
在 cmd 上下文里**显式写死** INCLUDE/LIB（MSVC include + SDK ucrt/um/shared/winrt），
**不要用 vcvars64.bat**。改完 10 秒内正常报错 → 2 分钟打完包。

**排查这一类问题的方法（可复用）**：
1. 手工跑 cl 编译同一个文件，看 stderr 全文 → 发现 `stdint.h` 找不到
2. 对比 cargo 传给 cl 的命令行 vs 自己跑的命令行（参数完全一样，差别只在环境）
3. `printenv INCLUDE` 看有没有被改写 ⇒ **MSYS 改路径这个坑要记牢**

**连带记住**：
- `cargo test --release` 会改变依赖特征集 ⇒ **之后 `cargo build --release` 要重编所有 C 依赖**。
  测试要用**独立的 target dir**（别和 release 共用）
- `CARGO_PROFILE_RELEASE_DEBUG=0`：去掉 PDB 依赖（cl 等 mspdbsrv 会挂）
- `NUM_JOBS=1`：并发 cl.exe 在这台机器上会互卡
- `CARGO_NET_OFFLINE=true` **不要开**：git 依赖的 source id 会变 ⇒ 全量重编
